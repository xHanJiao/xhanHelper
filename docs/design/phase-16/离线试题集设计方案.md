# 离线试题集设计方案

> 2026-06-15 · 基于 RAG 检索评测框架 Phase 1 细化
>
> 核心目标：构建一套**可重复、可版本管理、冻结不可修改**的检索评测数据集。

---

## 一、设计目标

| 目标 | 说明 |
|------|------|
| **数据驱动** | 试题源于真实用户 query，覆盖实际使用场景 |
| **可重复** | 锁死试题集后，任何检索策略改动都能回放对比 |
| **自包含** | 一个 SQLite 文件 = 一个完整数据集项目，可搬运、可 git 管理 |
| **不可篡改** | 标注完成后冻结，项目状态 `draft → annotating → locked` |

---

## 二、数据集架构

### 2.1 项目概念

每次构建数据集都是一个**不可修改的项目**，做完冻结，下次新开一个：

```
dataset/projects/
├── 2026-06-15-retrieval-baseline/
│   └── eval.db                  # 自包含 SQLite
├── 2027-01-10-expanded-dataset/
│   └── eval.db
└── ...
```

每个项目一个 SQLite 文件，一个 `eval.db` 内包含该项目的全部数据。

### 2.2 表结构

6 张表：

#### `eval_projects` — 项目注册

```sql
CREATE TABLE eval_projects (
    id          TEXT PRIMARY KEY,        -- 项目名，如 "2026-06-15-retrieval-baseline"
    name        TEXT NOT NULL,           -- 项目名称
    description TEXT,                    -- 描述说明
    status      TEXT NOT NULL DEFAULT 'draft',  -- draft | annotating | locked | archived
    created_at  TEXT NOT NULL DEFAULT (datetime('now')),
    locked_at   TEXT                          -- 冻结时间
);
```

> 状态流转：`draft` → `annotating` → `locked` → `archived`

#### `eval_queries` — 精选用户 query

```sql
CREATE TABLE eval_queries (
    id               TEXT PRIMARY KEY,        -- UUID，与 messages.id 对应
    content          TEXT NOT NULL,           -- 原始用户消息内容
    source_msg_id    TEXT NOT NULL,           -- 来源 messages 表的 id
    source_conv_id   TEXT,                    -- 来源 conversation id
    created_at       TEXT,                    -- 原始消息时间
    selected_at      TEXT NOT NULL DEFAULT (datetime('now')),  -- 入选时间
    has_answer       INTEGER NOT NULL DEFAULT 0,               -- 0=负样本, 1=正样本（标注阶段确定）
    label_status     TEXT NOT NULL DEFAULT 'raw',              -- raw | llm_prelabeled | human_reviewed | finalized
    difficulty       TEXT DEFAULT 'medium',                    -- easy | medium | hard
    notes            TEXT                                     -- 标注备注
);
```

#### `eval_corpus` — 被检索的语料库

```sql
CREATE TABLE eval_corpus (
    id          TEXT PRIMARY KEY,        -- original_id 的 hash 或 UUID
    content     TEXT NOT NULL,           -- 文本内容
    source_type TEXT NOT NULL,           -- 'note' | 'memory'
    source_id   TEXT NOT NULL,           -- 来源表原始 ID（notes.id 或 user_memories.id）
    topic       TEXT,                    -- 主题
    tags        TEXT,                    -- 标签
    created_at  TEXT                     -- 原始创建时间
);
```

- 数据来源：`notes` 表（status=0） + `user_memories` 表（全量）
- 不包含：documents（文档）、历史消息

#### `eval_ground_truth` — 五档相关性标注

```sql
CREATE TABLE eval_ground_truth (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    query_id      TEXT NOT NULL,         -- 对应 eval_queries.id
    corpus_id     TEXT NOT NULL,         -- 对应 eval_corpus.id
    relevance     INTEGER NOT NULL,      -- 0 ~ 4，五档相关性
    label_source  TEXT DEFAULT 'llm',    -- 'llm' | 'human' | 'corrected'
    labeled_at    TEXT NOT NULL DEFAULT (datetime('now')),
    notes         TEXT,                  -- 标注备注

    UNIQUE(query_id, corpus_id)
);
```

#### `eval_embedding_cache` — 向量缓存

```sql
CREATE TABLE eval_embedding_cache (
    source_type TEXT NOT NULL,           -- 'query' | 'corpus'
    source_id   TEXT NOT NULL,           -- eval_queries.id 或 eval_corpus.id
    model_name  TEXT NOT NULL,           -- 嵌入模型名，如 'doubao-embedding-vision-251215'
    embedding   TEXT NOT NULL,           -- JSON 文本 blob，如 "[0.12, -0.34, ...]"
    dimension   INTEGER NOT NULL,        -- 向量维度
    created_at  TEXT NOT NULL DEFAULT (datetime('now')),

    UNIQUE(source_type, source_id, model_name)
);
```

- 评测引擎运行时：先查缓存，命中直接用；未命中则调 API 计算后写入
- 支持多模型共存，换模型做对比时开新行

#### `eval_metadata` — 元信息

```sql
CREATE TABLE eval_metadata (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
```

- 建议记录：`version`（如 `v1.0`）、`annotator`（标注人）、`self_consistency_rate`（自洽率）、`annotation_date`（标注日期）、`corpus_source_count` 等

## 三、五档相关性标注标准

评测用 NDCG（归一化折损累计增益）做排名质量评估，需要分档权重。

| 档位 | 分数 | 标签 | 含义 | 示例（query: 我上个月吃饭花了多少） |
|------|------|------|------|------|
| **0** | 0 | `irrelevant` | 完全无关 | 「减肥计划」「股票涨了」 |
| **1** | 1 | `tangential` | 同话题但无帮助 | 「餐饮行业趋势」「做菜教程」 |
| **2** | 2 | `partial` | 弱相关，有线索但答题不够 | 「外卖比堂食贵」「最近胃口不好」 |
| **3** | 3 | `relevant` | 直接相关，回答可用 | 「5月食品支出概览」 |
| **4** | 4 | `perfect` | 完美命中，最优答案 | 「5月餐饮月度明细：¥2,847」 |

### 标注规范（标注时顺手记录）

- **算「相关」**：结果直接回答了问题或提供了关键上下文
- **算「不相关」**：结果与问题无关或仅有微弱关联
- **边界案例**：标注备注里记录模糊题的判断依据

## 四、标注流程

### 4.1 整体流水线

```
MySQL 原始数据
    │
    ▼  [B1] 导出脚本：筛选 + 灌入 SQLite
    │
eval_queries (1642 → 去短消息) + eval_corpus (~454)
    │
    ▼  [B2] LLM 精选 500 条有价值的 query
    │
eval_queries 精选后 ~500 条
    │
    ▼  [B2] LLM 逐条五档预标注
    │
eval_ground_truth 有 LLM 预标注结果
    │
    ▼  [B3] 人工在标注页面复核修正
    │
eval_ground_truth 人工确认版
    │
    ▼  [B4] 两周后抽 20% 复标 → 自洽率校验
    │
自洽率 ≥ 90% → locked ✅
自洽率 < 90% → 检查分歧原因，补充标注规范，重标
```

### 4.2 自洽率

自己隔一段时间重标同一批题，看两次结果一致的比例。目标 ≥ 90%。

### 4.3 单人标注说明

目前只有一个人标注（hx），用**自洽标注**替代多人 Kappa 校验：
- 第一轮：LLM 预标注后人工复核
- 第二轮：过两周随机抽 20% 复标，计算自洽率

## 五、MySQL 导出策略

### 5.1 queries 导出

数据源：`messages` 表。

过滤条件：**只保留会触发检索的 query**（取当前管线跳过检索条件的反逻辑）。

当前管线跳过检索的条件：
- 消息很短（`charLen ≤ 5` 或 `charLen ≤ 10 且 byteLen ≤ 15`）
- **且** 不含问号（`?`、`？`）
- **且** 不含意图关键词（`帮我`、`查一下`、`记一下`、`算`、`搜`、`找`）

导出 SQL（保留触发检索的 query）：

```sql
SELECT id, content, conversation_id, created_at
FROM messages
WHERE role = 'user'
  AND status = 1
  AND (
      CHAR_LENGTH(content) > 10
      OR (CHAR_LENGTH(content) > 5 AND LENGTH(content) > 15)
      OR content REGEXP '[?？]'
      OR content REGEXP '帮我|查一下|记一下|算|搜|找'
  )
ORDER BY created_at ASC;
```

- 不限制时间范围，导出所有历史数据
- 不过滤 user_id（目前仅一个用户）
- 也不复用管线代码——输出脚本中独立实现相同逻辑

### 5.2 corpus 导出

数据源：`notes` + `user_memories` 表，全量导出，无需过滤。

```sql
-- notes
SELECT id, content, topic, tags, created_at
FROM notes
WHERE status = 0;

-- user_memories
SELECT id, memory_value AS content, topic, tags, created_at
FROM user_memories;
```

## 六、Embedding 缓存策略

- corpus.json / queries.json 只存文本，不绑死向量
- 评测引擎运行时查 `eval_embedding_cache` 表
  - 有缓存（匹配 `source_type + source_id + model_name`）→ 直接用
  - 无缓存 → 调 embedding API 计算，结果写回缓存
- 换 embedding 模型时，新模型的向量第一次花钱算，后续缓存命中
- 向量以 JSON 文本 blob 存 SQLite

## 七、开发批次

分 4 批交付，每批独立 review。

### B1 — 基础设施

| 项 | 内容 |
|----|------|
| 目标 | SQLite schema 建表 + Go eval 模块骨架 + 导数据脚本 |
| 后端 | `server/internal/eval/` 模块：DB 初始化、表迁移、repo 层 |
| 脚本 | MySQL → SQLite 导出脚本（queries + corpus） |
| 产出 | `dataset/projects/<name>/eval.db` 含 queries、corpus 两张表 |
| Review | schema 设计、代码结构 |

### B2 — LLM 数据加工

| 项 | 内容 |
|----|------|
| 目标 | LLM 挑选 500 条精华 query + 五档预标注 |
| 内容 1 | 调 LLM 从全量 query 中评估价值，选出 ≤500 条（结合 query 内容、会话上下文判断是否适合做检索评测） |
| 内容 2 | 调 LLM 对每条精选 query 逐条预判与 corpus 的相关性（5 档分数） |
| 产出 | `eval_queries` 填充完成（selected），`eval_ground_truth` 有 LLM 预标注结果 |
| Review | prompt 设计、预标注质量抽样 |

### B3 — 标注前端

| 项 | 内容 |
|----|------|
| 目标 | 前端 Admin 标注页面，个人工复核修正标注 |
| 后端 | 标注 API：query 列表、检索结果展示、标注保存 |
| 前端 | Admin 标注页：显示 query → 展示相关 corpus → 五档切换 + 备注 + 保存 |
| 产出 | 你在浏览器逐条复核，产出人工确认版 ground_truth |
| Review | UI 交互、接口逻辑 |

### B4 — 质检锁定

| 项 | 内容 |
|----|------|
| 目标 | 自洽率校验 → 冻结项目 |
| 内容 | 抽 20% query 复标 → 计算自洽率 → 写入 metadata → 状态切 locked |
| 产出 | `self_consistency_rate ≥ 90%` 且 `status = locked` |
| Review | 自洽率是否达标 |

## 八、版本管理约定

- `dataset/projects/` 目录纳入 git 管理
- `.db` 文件通过 `.gitignore` 例外规则放行（当前根目录 `*.db` 会阻拦，需追加 `!dataset/projects/**/*.db`）
- 每个项目冻结后不可修改，需要新数据集就新开一个项目目录
- `eval_metadata` 记录版本号、标注人、自洽率、标注日期，保证可追溯

## 九、与评测引擎的关系

```
┌─────────────────────┐        ┌─────────────────────┐
│  dataset/projects/   │        │  server/internal/eval/│
│  (数据，冻结)          │  ←读取  │  (评测引擎，可运行)      │
│                     │        │                     │
│  eval.db            │        │  evaluator.go       │
│  ├── queries        │        │  ├── 加载 query      │
│  ├── corpus         │        │  ├── 调用 retriever  │
│  ├── ground_truth   │        │  ├── 对比 ground_truth│
│  └── cache          │        │  └── 输出指标        │
└─────────────────────┘        └─────────────────────┘
```

数据集项目只存**数据**（queries、corpus、标注、缓存），不包含检索逻辑。评测引擎是独立模块，读取冻死的数据集跑检索，计算 Recall@K、Precision@K、NDCG@K、MRR 等指标。

---

## 十、总结

离线试题集构建四步走：

1. **导数据**：MySQL → SQLite（过滤掉不触发检索的短消息）
2. **LLM 预加工**：精选 query + 五档预标注
3. **人工复核**：前端页面逐条确认
4. **质检冻结**：自洽率 ≥ 90%，项目上锁

做完后的数据集可重复用于对比任意检索策略（换 embedding 模型、换分段策略、换排序逻辑），每次改动都能回答：「这是优化还是回退？」
