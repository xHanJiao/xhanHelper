## 结论

**REQUEST_CHANGES**。分工是对的：`MemorySource` 只放 `event_id IS NULL`、`EventSource` 按 `event_id` 聚合，`PrevEventXML` 与 `PrevUserXML` 拆开、新 session 也带，事件按 ID 去重（同名事件不互相吞），预算把事件放到总预算最后砍 —— 这些都和设计 §6.2 / §6.10 一致，测试也覆盖了 sticky / carried / pinned / quota / 字面命中 / 已删事件。

但有一处**在常见路径上把事件块整体打掉**的问题（P1），以及三处 P2（预算裁剪语义、一处可 panic 的空指针、测试盲区）。P3 多为设计文档与实现的口径漂移，冷启动调参前最好一次修掉。

## 发现

### P1 - High

1. **短输入（`SkipRetrieval`）或检索失败时，事件块整块消失，并且粘滞链从此断掉**
   - 位置：`server/internal/agent/ctxflow/resource_zone.go:390-395`（`MergeResourceZone` 无条件丢弃 prev 事件）+ `server/internal/agent/orchestrator.go:779-802`（检索没跑时 `zoneFresh` 为空）+ `server/internal/agent/pipeline/step_short_input.go:44` + `server/internal/controller/chat.go:329`。
   - 链路：`继续` / `好的` / `嗯` 这类 ≤5 字且无意图关键词的消息会让 `pc.SkipRetrieval = true` → `orch.Run` 不调用 `Retrieve` → `retrieveResult == nil` → `zoneFresh` 里没有任何 event → `MergeResourceZone` 又把 prev 里的 event 全部 `continue` 掉 → 本轮 XMLContext 里 `<events>` 整块没了。
   - 更糟的是**状态是从上一条 XML 解析的**（设计 §6.10）：这一轮写进 DB 的 XMLContext 没有 `<events>`，下一轮的 `ParseEventRefs` 就解析出空 → 同窗口 sticky 和跨窗口 carried **永久丢失**，直到下一次向量命中/字面命中重新捡起来。
   - 同时事件记忆不会退化成普通记忆（`MemorySource` 只查 `event_id IS NULL`），所以这些内容在这一轮是**完全不在上下文里**，不是"格式降级"。
   - 设计自带的验收项现场就过不了：§10.4「新 session 说「继续」→ carried 事件 summary-only 出现」——「继续」是 2 个字，正好命中 `skip_retrieval=true`。
   - 建议（很小）：`retrieveResult == nil` 时（跳过检索 / 全部 source 失败）把 prev 里的 `TypeEvent` packets 原样并入 `zoneFresh`；只在 `retrieveResult != nil` 时保持现在"以本轮 EventSource 结果为准"的行为。prev 事件的 `Memories` 本来就已经被 `ParseResourceZone` 从 XML 还原了，所以不需要额外 DB 读。另外建议把这条规则写进设计 §6.10，并补一条 `SkipRetrieval` 场景的单测。

### P2 - Medium

2. **事件区预算裁剪是"整条丢弃"，不是降级到 index；且裁剪键是 score，sticky/carried 恒为 0 分会先被砍**
   - 位置：`server/internal/agent/ctxflow/resource_zone.go:548-551`、`server/internal/agent/ctxflow/retriever.go:126-128`、`server/internal/agent/retrieval/event_source.go:197`。
   - `budgetPerType` 对 event 直接 `list = list[:len(list)-1]`，砍掉的是**整个事件**；而设计 §6.4 说"预算不足时 summary → index"，§6.7 也按"index 25 个标题一直保留"来规划。
   - 顺序也有问题：`ContextRetriever.Retrieve` 末尾把每个 type 的 packets **按 Score 降序重排**，而 sticky / carried 事件的 `score` 一律是 0（`event_source.go:197`）。所以事件区一超预算，最先被砍的是"上一轮还是 full 的那个事件"，反而 fresh 命中的 index 事件（score ≥ 0.5）留着 —— 与 §6.5 的 `sticky > index` 优先级相反。
   - 触发条件不是理论上的：4 full×~2300 + 6 compact×~350 + 12 summary×~150 + 25 index×~8 ≈ 13300 > `budget_event: 12000`，事件多起来冷启动后就会撞上。
   - 建议：预算裁剪前先按"该降级的先降级（full→compact→summary→index）"再谈丢弃；至少要按 `mode` 排序而不是裸 score（`EventSource` 已经算好了优先级，别在 Retriever 里丢掉）。这条和 §6.5 的语义要一起定稿。

3. **`fresh` 里出现"加载不到的事件"时会 nil 解引用，panic 被 retriever recover 成"本轮没有事件"**
   - 位置：`server/internal/agent/retrieval/event_source.go:185`（`ev: active[id]` 未判空）→ `:266`（`memoriesByEvent[st.ev.ID]`）。
   - `fresh` 是从"记忆的 `event_id`"来的，没有校验对应事件是否在 `active`（只查未删除）里。当前阶段没有写方制造悬空 `event_id`（§5.3 的 merge/delete 都在同一事务里先把记忆搬走/置 NULL），所以现在是**防御性缺口**；但阶段 4 的 `event.delete` / `event.merge` 一上线，任何一次部分失败或并发都够得着。
   - 症状不显眼：`ContextRetriever` 会 `recover` 并打一行 `[retriever] event panic`，本轮事件块直接空 —— 和 P1-1 是同一个"整块消失"的结果。
   - 建议：`active[id] == nil` 时跳过并打一条 `[event] skip stale event_id` 日志（`nearMiss` 那段已经这么写了，step 3 漏了）。

4. **阶段 3 的关键路径没有测试**
   - `server/internal/agent/retrieval/event_source_test.go` 覆盖了分组 / quota / sticky / carried / pinned / 字面 / below_threshold，但没有：
     - `SkipRetrieval` / `retrieveResult == nil` 时资源区的事件行为（P1-1 的根因，改完必须有回归）；
     - chunk 向量召回路径（测试只用 `fullMemResult`，`searchMemoryScores` 的 chunk 分支没跑过）；
     - `loadActiveEvents` 分页（>200 个事件）；
     - 跨用户隔离（他人记忆命中本用户事件）；
     - 记忆的 `event_id` 指向已软删 / 不存在的事件（P2-3）。
   - `resource_zone_test.go` 里的 `TestBudgetResourceZone_TrimsEventFromTail` 用"手工顺序"验证砍尾部，恰好绕过了 P2-2 的真实顺序问题（真实顺序是 Retriever 按 score 重排后的）。建议改成从 `EventSource` 输出 → `MergeResourceZone` → `BudgetResourceZone` 的端到端断言。

### P3 - Low

5. **`EventRef.Pinned` 只写不读，pinned 跨轮/跨窗口的链路只完成一半**（`event_source.go:189-219`、`resource_zone.go:236-240`）
   - `ParseEventRefs` 解析了 `pinned`、XML 也渲染了 `pinned="1"`，但 step 4 从不看 `ref.Pinned`；`SearchOptions.PinnedEventIDs` 由阶段 4 的 `Conversation.Extra` 填，当前恒空。
   - 现在"pinned 上一轮是 full，这一轮没命中"会走 sticky 降级逻辑（miss+1），而设计 §6.6 要求 pinned 无条件 full。
   - 要么在 step 4 里 `ref.Pinned` 直接给 full 兜底（阶段 4 写入后自动冗余安全），要么在代码里注明"pinned 只认 `PinnedEventIDs`，XML 里的 pinned 仅作展示"。

6. **`EventRepo.List` 的排序没有唯一 tiebreaker，而 `EventSource` 依赖它分页拉全量**（`server/internal/service/event_repo.go:135`）
   - `Order("last_memory_at DESC")`：`last_memory_at` 全 NULL 或大量相同值（冷启动/老事件）时，MySQL 不保证跨分页稳定，可能重复或漏行；`ListUpdatedSince` 同款。
   - 事件量小，实际风险低；但这里是"静默丢事件"的形态，建议 `Order("last_memory_at DESC, id")`。

7. **注入提示词承诺了还不存在的工具**（`server/internal/agent/retrieval/types.go:20`）
   - `DescEvents` 写着 `mode=index 只有标题（…需要时可用工具拉取全文）`，但 `event.get`（甚至 event 域检索）要到阶段 4 才有。模型只能退回复用 `unified_search`，等于教它按一个不存在的路径行事。
   - 与阶段 2 的 P2-5 同源：要么阶段 3/4 一起发，要么先把这句改成"需要时用 `unified_search` 查记忆"，阶段 4 再改回来。

8. **`Miss` 只累加一次，`degrade` 也不看 `miss`**（`event_source.go:202-217`、`eventWorse`）
   - full→compact 之后 `st.miss` 回到 0 且不再累加；compact 只会被 quota/预算推动，永远不会因为"最久没命中"而降级。设计 §6.5 写的是"从优先级最低、最久没命中的开始降"。
   - §6.4 又说"只有 summary 超过 12 或预算不足才降到 index"，两条本身也有点打架；实现跟了 §6.4。建议**把 §6.5 那句话改成实现的行为**，而不是补一套 miss 状态机（多存一位、还要处理跨窗口重置）。

9. **设计文档 §9 的配置示例、§10.1 的日志示例都和实现不一致**
   - §9：`event_pinned_max: 3`（实现是 `quota_event_pinned`）、`retrieval.event.limit: 10`（`conf/config.yaml` 是 20）、缺 `freshness_decay` / `event_memories`。
   - §10.1 写的是 `[event_zone] modes={pinned:1,full:2,...} chars=... event_total=... zone_total=... demoted=...`，代码里不存在这行；实际是 `[event] inject: user=… active=… fresh=… selected=… (full/compact/summary/index=…)`（`event_source.go:302`）+ 资源区的 `[resource_zone] budget trim: … per-zone …`。
   - 冷启动时按文档去 grep 日志会一条都找不到。建议照实现更新 §9 / §10.1（或在代码里补齐 modes/chars/demoted 统计，§10.1 的那几个字段其实很有用）。

10. **`retrieval.event.limit` 的语义漂移**（`conf/config.yaml:164`、`event_source.go:102/385`）
    - 文档叫"候选事件数"，实现里只被当作记忆检索的 topK 乘数（`limit*8` chunk、`limit*2` full memory）；事件条数完全由 `quota_event_*` 决定。有人为了"少注入几个事件"把它调到 5，实际会砍掉记忆召回、事件数不变。
    - 建议改名（`memory_hit_limit` / `recall_k`）或在注释里写清它是召回乘数。

11. **`DefaultZoneBudgets()` 与 config / `validate()` 的默认值已经分叉**（`ctxflow/resource_zone.go:50-53`）
    - 函数默认 `Note: 3000` / `Memory: 600` / `Summary: 800`，config 默认 `Note: 0` / `Memory: 1000` / `Summary: 500`，注释还写着旧值。走这个函数的路径（测试、以及任何没接 appinit 的调用方）与生产不是一套数字。

12. **`ParseEventRefs` 与 `ParseResourceZone` 把同一条 XML 全量解析两遍**（`orchestrator.go:396` 与 `:794`）
    - 单次成本可忽略，但同一条坏 XML 会打两条 `[resource_zone] parse ... error` 日志，且两次解析结果理论上可能不一致（中间无写入，概率为零）。
    - 顺带：`retrieval.note` 已是死配置（`NoteSource` 不在 retriever 里，`opts.Note` 没有读者），留给阶段 5 清理时一起删；`EventSource.Warmup` 每次启动固定打一行 `event warmup: skipped`，可以降级或去掉。

## 未覆盖 / 残余风险

- **阶段 3 把三件事捆在一个提交里**：事件注入 + 笔记退出资源区（`budget_note/quota_note = 0`）+ 资源区总预算 7000 → 15000。功能上都是设计里的（§6.7 / §6.8），但出问题时无法只回滚其一。建议发版说明写清楚，并观察 `[resource_zone] budget trim` 的 `total` 分布，确认 15000 的实际占用（设计 §6.7 的典型值 ≈ 10770）。
- **事件记忆不再进 `confirm_count`**：`recordInjectedMemories` 只统计 `TypeMemory`，事件块里的记忆不会 +1。现在没影响，但将来若用 confirm 做衰减/清理，事件记忆会被当成"从来没被看过"。
- **事件层状态全在 XML 里**：除了 P1-1 的跳过检索，任何一次 `ParseResourceZone` 解析失败（例如某条历史 user 消息的 XMLContext 里有非法字符）也会把整个资源区重置，事件跟着丢。设计 §6.10 接受"不落库"，但这条自愈路径要心里有数。
- **replay / preview 不注入事件**：`agent/replay/runner.go` 手动构造 `SearchOptions`，既没有 `PrevEventRefs` 也没有资源区，阶段 8 的"dump 回放"看到的不是线上注入形态。做事件调参时别拿它当基准。
- 未跑真实 LLM / embedding；未在 MySQL 上验证 `ORDER BY last_memory_at` 的分页稳定性；未做并发验证（同一会话两条消息同时检索 + 同时 session_end 拼装）。
