## 一、缘起：一次真实数据回收

记忆系统（`user_memories` 上那套「抽取 + 逐候选决策循环」）2026-09-24 上线后跑了一个月，
本轮拿线上数据做了一次只读回收。数据源：本地 MySQL `xhan_helper_test`
（云端 dump `server/data/mysqldumps/xhan_helper_cloud-20261013-203146.sql`），时间窗 09-24 ~ 10-13。

### 1.1 基座

| 项 | 值 |
|---|---|
| `user_memories` | 1069 = 存量 777（`conversation`）+ 新链路 **292**（`inline` 137 / `post_chat` 155） |
| 评分（`rating`） | 👍 39 / 👎 34 / 未评 996 —— 新链路覆盖 **73/292 = 25%** |
| `notes` | 795 条仍在用（闸门顺带只软删 7 条） |
| 向量 | 新记忆 292/292 都有向量，无脱同步 |

### 1.2 结论一：噪声不是「重复」，是「本不该记」

- 292 条新记忆**内部**相似度 ≥0.80 的只有 **2 对**，≥0.85 = **0**；
- 与 795 条旧笔记**跨域** ≥0.85 = **0**。

去重机制是干净的。问题在**判据/门槛**——很多内容压根不该进库。

### 1.3 结论二：两个入口质量差得很明显

| 入口 | 👍 | 👎 | 好评率 |
|---|---|---|---|
| `inline` | 18 | 7 | **72%** |
| `post_chat` | 21 | 27 | **44%** |

post_chat 更碎（👎 平均 68 字 < 👍 78 字），产量还比 inline 多（10 月 inline 60 / post_chat 110），
**与「查漏补缺」的定位正好相反**。

### 1.4 结论三：产量与满意度是反着的

按 topic 粗分四族（手工归类）：

| 族 | 条数 | 👍 | 👎 | 好评率 |
|---|---|---|---|---|
| 生活 / 背景 | 89 | 18 | 7 | **72%** |
| 项目决策与调研 | 103 | 10 | 8 | 56% |
| 工作过程与交付 | 57 | 8 | 12 | **40%** |
| 记账流水 | 28 | 3 | 7 | **30%** |

**55% 的产量压在项目工作流上，而那正是满意度最低的两族。**

再按入口拆开（`条数 / 好评率`），指向三个不同的病因：

| 族 | inline | post_chat |
|---|---|---|
| 生活/其它 | 48 / 86% | 56 / 55% |
| 工作过程 | 23 / **80%** | 34 / **27%** |
| 记账流水 | 7 / 50% | **21 / 25%** |
| 项目决策 | **59 / 25%** | 44 / 64% |

1. **post_chat 在每一族都更松**（同一个「工作过程」族：inline 80% / post_chat 27%）——差的是**门**，不是内容；
2. **记账流水是 post_chat 的主责**（21 : 7），且规则**已经写了**（`MemoryDefinition` 末句、准则 4 都写了"逐日流水/台账不记，走 document"）——是**说了没做到**；
3. **inline 自己的坑是"项目决策"族**（59 条 / 25%）：主 LLM 在开发类对话里高频触发，把每次技术讨论都当成"决定/结论"（`技术调研` 27、`技术决策` 21、`AI开发` 17、`系统设计` 10）。

### 1.5 结论四：召回 ≠ 有用

| 评分 | 被召回（`confirm_count` ≥1） | 从未召回 |
|---|---|---|
| 👍 | 12 | 27 |
| 👎 | 10 | **24** |

召回率两条一样（31% / 29%），且 👎 里 71% 从未被召回——**记了也没人看**，白花抽取与决策的算力。

### 1.6 结论五：碎片化来自视野盲区 + 判据边界没划

`旅行计划` 一个 topic **32 条**，全是同一趟日本行程的逐次微调；`活动埋点系统` 每个 6.x 节一条。
这些记录向量各不相同（所以去重抓不到），但**本质是一件事的连续版本**。

两个成因（注意：行程微调**不是「观点」**，所以不能归因到「观点/看法变了 → 新增」那条判据——那一句
是同一个循环里另一条规则，本轮的 §3.1 顺手给两者补了分界）：

1. **视野盲区**：循环只看语义 top_k 近邻，看不到「这个 topic 已经挂了多少条」；
2. **判据边界没划**：指令里「多了一件无关的新事 → `save_memory`」与「同一件事变了 → `update_memory`」
   之间的界，全交给模型自己划——它把每次行程微调都当成「新事」。

## 二、关键发现：决策循环的指令从未进代码

`record-loop-prompt.md` §2 有一大段完整指令（**动作定义 / 「同一件事」的判据 / delete 是最后手段 / 旧笔记清理 / 输出契约**）。
逐层核对后确认：**它只存在于那份 md 里，代码里没有。**

| 检查 | 结果 |
|---|---|
| `rg recordLoopInstruction`（全仓库） | 无 |
| `git log -S recordLoopInstruction` | 只有 `bb28ffd6`，该提交只改了 docs + `extractor.go` + `memory_definition.go` + `static.go`，**没碰 `record_loop*`** |
| `MiniReAct.Run(ctx, userMessage)` | `msgs = initialMessages + {user: userMessage}`，而决策循环 `InitialMessages` 为空 |
| `RecordDecisionLoop.Decide` 实际发出的 prompt | **system 只有 3 句**（"你是记忆库的写入决策助手" + `MemoryDefinition` + "你的输入是一条候选记忆…"），**user 只有 `<candidate>` + `<neighbors>`**；指令实际靠工具描述那几行（"新开一条记忆"/"覆盖近邻中某条讲同一件事的记忆"） |

**后果**：循环从来不知道"什么算同一件事"、不知道"什么都不调是合法终局"、不知道"delete 是最后手段"——
它的动作集 `save / update / delete / NONE` 里，**结构上只有"写"这一条路**。
这与 §1.2「噪声不是重复、是本不该记」完全对上：**该拦的地方（要不要记）它没有判据，它能判的地方（是否重复）判得很准。**

> 这条是**实现漏掉定稿**，不是设计缺陷——所以本票第一刀不是调策略，是**把漏做的补上**。
> （同一批发现的文档漂移：`design.md` §6 与 `record-loop-prompt.md` §3.2 仍写 topic「≤20 字」，代码早已是 5 字，
> 见 `topic-5char.md`。本票顺带对齐。）

## 三、本票要做的（五处改动，全部是 prompt 与视野，不动循环骨架）

### 3.1 A · 补齐决策循环指令（本票最重要）

- 新增 `recordLoopInstruction`（`agent/record_loop_types.go`），正文来自 `record-loop-prompt.md` §2，
  按当前实现校正两处：**topic 上限 20 → 5 字**（`memoryTopicMaxLen = 5`）；去掉未实现的措辞。
- **并入 system prompt**（`recordLoopSystemPrompt`）而不是拼进 user 消息：它是稳定常量，构成可命中的缓存前缀；
  变化部分（`<candidate>` / `<neighbors>` / `<topic_records>`）才进 user 消息。
- 必须进去的四节：**动作定义**（含"什么都不调"= 合法且常见的终局）、**判据**（同一件事 = 同一主体 ＋ 同一件事本身）、
  **update 优先于新增**、**delete 是最后手段**。

### 3.2 B · `MemoryDefinition` 加负清单

`agent/promptbuilder/memory_definition.go` 是「记忆是什么」的全链路唯一定义（抽取段 + 决策段共用，主循环不用）。
末句原先只有"逐日流水"一条，扩成负清单：

```
以下不属于记忆：
- 逐日流水（睡眠打卡、体重、饮酒、运动、时间日志等按天读数）——属于文档台账。
- 单笔账目的录入与归类细节（某个小票怎么拆、某件商品归哪个二级分类）——属于账单数据本身。
- 只对本次任务成立的过程性内容：本轮产出形式、推进顺序、本轮临时口径、讨论中的中间结论。
- 已经写进文档/方案/代码的内容——文档才是它的家，记忆不重复承载。

判据一句话：这件事过一个月再看，还对了解用户本人有用吗？说不出用途的，不记。
```

命中 §1.4 的三类噪声（记账 28、工作过程 57、项目决策里的过程细节）。

### 3.3 C · 两个触发门同步收窄

- `agent/promptbuilder/static.go` 准则 4：加"长期"限定 + 排除"本轮任务怎么推进 / 已进文档的"。
  受 `builder_test.go` 的结构断言约束：**列表项内不能出现空行**，且必须保留 `record_memory` / `不留旧数据` / `内部动作`。
- `tool/record_memory.go` 的 `Description` / `Catalog.ShortDesc` / `Functions[0].Description`：同一套措辞
  （主 LLM 看到的口径与决策段必须一致）。

### 3.4 D · 抽取段改「查漏」

`agent/extractor.go` 的 `buildMemoryInstructionXML`：

- task 措辞从"提取值得长期留存的记忆，最多 N 条" → **"找出尚未被记录、且将来还会用到的长期信息；这是查漏不是整理纪要；宁可少提不要凑数"**；
- 每条候选加 `reason`（为什么它一个月后还有用）；
- **硬门禁：`reason` 空的候选直接丢弃**（说不出用途的候选正是要消掉的那一批），丢弃数记日志。

`memory_max_per_session`（默认 5）与「最多 N 条」措辞保留，既有单测 `TestExtractCandidates_MultiAndTruncate` 依赖它。

> **不做**（本轮明确不喂）：把"本会话 `inline` 已写过的记忆"主动喂给抽取段。理由：决策循环的预检索
> 本就能把 inline 写过的捞成近邻，重复不至于漏；先只改门槛，跑两天看数据再决定要不要加。

### 3.5 E · 视野：把「同 topic 已有记录」并入输入

- `agent/record_loop.go`：在 `cand.Topic = d.nameTopic(...)` **之后**（topic 定稿在预检索之后，顺序不能挪）
  取 `MemRepo.ListByUser(ctx, userID, "", "", cand.Topic, N, 0)`——**该方法已存在，不新增 repo 方法**；
  过滤掉已在语义近邻里的 id，并入 `state.idSet` / `state.idType`（否则模型的 update/delete 打不到它们。
  注意：同 topic 记录**不混进 `<neighbors>`**，只进独立的 `<topic_records>` 块，模型能分清两批来源）。
- `agent/record_loop_render.go`：新增并列块 `<topic_records count="N">`，前 N 条（`RecordLoopConfig.TopicNeighborLimit`，默认 8、不进 yaml）。
- **`count` 是关键**：让模型看见"这个主题我已经有 32 条了"——治碎片化最便宜的一刀。
- 取数失败**不阻断决策**：退化成只有语义近邻，记日志（可降级，不静默；单测 `TestSameTopicRecords_DegradesOnRepoError`）。

## 四、影响面

- **主链路**：`record_memory`（inline）同步多一次按 topic 的 DB 查询（2 条 SQL，走已有联合索引 `(user_id, topic)`）；
  每次记记忆的 prompt 变长（指令并入 system，稳定前缀，缓存友好）。
- **后台**：post_chat 抽取与决策各变长；`reason` 门禁会**降低** post_chat 产量（这是目的）。
- **不动的**：所有工具 schema 形状、落库字段、向量逻辑、API、客户端、`confirm_count` 口径、资源区配额。
- **无 DB 变更、无迁移、无新配置项**（`TopicNeighborLimit` 只给代码默认值 8，不进 yaml）。

## 六、明确不做（本轮）

- **给循环加"不值得记"出口**（显式 `skip(reason)` 工具）：现在只有"写"这一条路。先看补完指令 + 收窄门槛后还剩多少噪声，再决定要不要动循环骨架。
- **候选 × 源对话的幻觉核对**：抽取段说什么就记什么，目前全链路没有核对（`户外活动` 那条"又叉→又又"的更正即此类）。另起一票。
- **post_chat 决策异步化**：inline 每次记记忆同步多花 2~4 秒循环时间；若体感变差再转 `DelayedTask`。
- **下掉 post_chat**：数据不支持（10 月 110 vs inline 60，砍掉即腰斩捕获量）；本票走"换门"（§3.4）。
- **把评分喂回检索排序/淘汰**：`rating` 仍只存不用。
- **修 `post_chat/memory_extract` 的成本打标串口径**（**真 bug，建议单开票**）：这个 sub_category 实际混了
  抽取 / topic 命名 / 决策循环三段（原因见附录），导致成本看板上"记忆管线花了多少"永远算不准、
  且与 inline 侧不可比（inline 的决策循环标在 `tool/record_memory`）。本票只记录，不动口径——
  改它会牵动历史数据的可比性，要单独决定。

## 七、风险与回滚

- **全部改动都是文本与注入内容**：回滚 = `git revert`，无 DB 影响。
- **风险 1（缝，只能真跑）**：改完 prompt 的真实效果无法离线预判——只能靠两天后的评分验证。
- **风险 2**：`<topic_records>` 让模型看见同主题历史后，可能**变得爱删/爱 update**（update 会覆盖 summary）。
  缓解：指令里 `delete` 仍是最后手段；观察统一到两天后的回收里看。
- **风险 3**：`reason` 硬门禁可能误杀（模型偶尔漏填字段）→ post_chat 这条链路**悄悄停产**。
  实测评估：7 天 IO 审计里抽取段的 schema **形状漂移 0 次**（146 个候选键只有 `summary`+`facts`、
  可选字段都 146/146 填满），所以概率低；但门禁是全链路唯一"失败即降级、不报错"的地方，故加了
  **全丢告警**（`len(result.Memories) > 0 && len(cands) == 0` → 打 WARN，正是漂移的指纹）。
  另：抽取段历史上出现过一次"整轮落空"（HTML 实体转义，见附录），说明这条链路确实有先例。
- **已知敞口（本票不解决）**：改完仍是"没人读过代码"的状态，靠上面的单测 + 两天数据兜底。

## 附：读数口径与坑（存档）

- **评分是自选样本**：覆盖 25%，若只看已评会有偏；但四族覆盖率接近（34%~36%），族间对比可用。
- **`confirm_count` 有历史脏值**：口径 B 上线时只清了本地 prod、**未清云端**，云端该列可能混着旧语义
  （检索侧 +1；有一条 inline 记到 25）。「召回率」只能当量级看，不能当准数。
- **`created_at` 时区混存**：旧 MySQL 行 `+00:00`、本地 SQLite 行 `+08:00`，按天聚合边界最多差 8 小时。
- **`llm_cost_details` / `llm_call_ios` 推量级（口径已修正）**：
  - **`post_chat/memory_extract` 这个 sub_category 混了三段调用**——抽取段 + topic 命名 + 决策循环。
    因为 `agent/memory_worker.go` 设了这个场景，而 `topic_namer.go` / `mini_react.go` **不设场景、直接继承**；
    inline 侧相反，是分开的（`record_loop.go` 的 `RecordInline` 显式标 `tool/record_memory`）。
    **所以「memory_extract 2210 次」不是抽取次数，分母用错了**（见 §6 挂账）。
  - 实测（7 天 IO 审计样本，`llm_call_ios` 按输入分型）：抽取 58 / topic 命名 151 / 决策循环 522。
    抽取里 `extracted:true` 47、`false` 10；共 146 个候选；**决策循环 ≈ 3.6 轮/候选**、**topic 命名 ≈ 1.0/候选**。
  - **抽取段 schema 遵从度**（146 个候选）：出现过的键只有 `summary` + `facts`，146/146 两键齐全，
    **形状漂移 0 次**；57/58 条响应可解析。唯一的失败是 1 条响应**整体被 HTML 实体转义**（`"` → `&#34;`，
    2026-10-07）——那是既有的、挂在解析阶段的故障，与 §3.4 的 `reason` 门禁无关。
- 本轮的族划分是**按 topic 关键词手工归类**，粒度粗；「该不该记」的判定来自用户的 73 条评分，不是标注集。
