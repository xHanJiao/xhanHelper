# 多源参数面板的状态一致性问题

## 问题表现

LLM 参数面板（温度、思考模式、最大 Token 数、Pro 模型开关）在跨会话切换时出现多种不一致：

1. 从 Agent 列表点击"开始对话"，参数面板显示的不是 Agent 配置的值，而是 localStorage 残留的旧值
2. 切换到已有 Agent 绑定的会话，参数面板不刷新，仍显示旧会话的配置
3. 没有 Agent 的会话，TopBar 却显示有 Agent 图标
4. 参数面板标记为"不可修改"但显示的值既不是 Agent 配置也不是默认值

## 根因分析

### 数据源多头，生命周期不一致

参数有三个来源，但各自的生命周期完全不同：

| 数据源 | 生命周期 | 问题 |
|--------|---------|------|
| `localStorage` | 浏览器持久化 | 脱离后端真实状态，跨会话残留 |
| `chat.agentId` (Pinia store) | 内存，跨路由保留 | 被 `agent_matched` SSE 静默设置后永不清理 |
| `conv.agent_id` (会话列表数据) | 服务端返回 | 新会话未写入时为空，切换会话后才刷新 |

三者的存活时间和更新时机完全不同，任何依赖单一来源的判断都会在某个场景下失效。

### 路由切换的静默失败

从 `/agents` 点击"开始对话"跳到 `/chat`，`route.params.id` 两次都是 `undefined`，Vue 的 `watch` 不触发回调。这意味着依赖 route watcher 来刷新参数的逻辑完全不执行。`onMounted` 虽然可靠，但只在组件首次挂载时运行——切回已有会话时组件不重新挂载。

### 优先级链条断裂

正确优先级应是 **Agent 配置 > 前端设置 > 服务端默认 > LLM 自身默认**。但最初实现中，前端 fallback 逻辑写在 `else if a != nil` 块内部，无 Agent 时整段跳过，参数保持 nil，编排器直接用了配置默认值。

## 解决方案

### 1. 收敛数据源——后端作为唯一真相源

新增 `GET /api/llm-config?agent_id=xxx` 接口，在服务端完成优先级合并：

```
不传 agent_id → 返回服务端配置默认值
传 agent_id   → 返回 Agent 的 params_json 覆盖默认值后的结果
```

前端不再维护参数状态，每次需要时直接从后端拉取。

### 2. 覆盖所有导航入口

```
onMounted           → 进入 ChatView 时拉取
route.params.id 变化 → 切换会话时拉取 + 同步 chat.agentId
route.path 变化      → 从 /agents 跳转时拉取
needsRefetch         → 数据刷新时拉取
agent_matched SSE    → 中途绑定 Agent 时更新面板
```

### 3. 同步 agentId 与会话数据

路由切换到已有会话时，从 `convs.list` 中读取该会话的 `agent_id` 并同步到 `chat.agentId`。切到无 Agent 会话时清空 `chat.agentId`，消除残留。

### 4. 移除 localStorage

不再在浏览器端持久化参数——每次新建会话都从服务端拉取最新默认值。用户在面板上的修改仅在当前会话内存中生效，刷新页面即恢复。

## 教训总结

1. **多源参数应单向流动**——后端是唯一真相源（source of truth），前端只是镜像。不要在多个地方独立维护同一份数据的副本。

2. **不要在组件内部维护跨路由的状态**——Pinia store 中与"当前会话"绑定的字段（如 `agentId`），必须在路由切换时主动同步或清理，不能假设上一个值仍然有效。

3. **`watch` 的静默是陷阱**——当新旧值相同时 watch 不触发。依赖 URL 参数变化来驱动逻辑时，必须考虑参数值不变但含义已变的情况（如从另一个页面跳转到同一路由）。

4. **优先级逻辑应收敛到一处**——分散在 controller、orchestrator、前端三处的 fallback 逻辑极易出现某条分支被跳过的情况。将合并逻辑收敛到单一接口是最可靠的解法。

5. **修改代码前确认缩进方式**——本项目 Go 文件使用 Tab，Vue 文件混用空格。用 Edit 工具匹配字符串时必须先确认目标文件的实际空白字符。
