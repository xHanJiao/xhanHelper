## 发现

### P3 - Low

1. **丢条目循环是 O(n²)：每丢一个条目就重序列化整棵树**
   - 位置：`server/internal/agent/mini_react.go:453-471`（`truncateJSONArrays` 的 `for` 循环）、`:465-470`（一次只 `drop()` 一个元素）。
   - 影响：`event.get` 最长 87 条（dev 实测 p90=20 / max=87），丢几十次可忽略；但这是通用截断函数，若将来某个工具返回几千条短条目且字符串截断救不回来，会变成几千次全量 `json.Marshal`（百万级字节 × 数千次），单次工具调用可能卡住数秒。当前没有这种工具，属「先记着」级别。
   - 建议：真要收紧，改成先按「最长数组长度的一半」批量丢、再二分收敛；或按剩余预算估算应丢条数，一轮丢到位再向后微调。不必现在做。

2. **兜底标记会连 `success` 一起丢掉，且只处理「挂在对象字段上的数组」**
   - 位置：`server/internal/agent/mini_react.go:472-474`（骨架仍超预算时返回 `{"truncated":"…"}`）、`:482-509`（`longestArrayDrop` 只把「对象字段 → 数组」当候选）。
   - 影响：极端结构（根是数组、或数组里套数组且没有可丢的对象字段数组）会从「能读到一部分」退化成「只剩一句标记」，且 LLM 看不到 `success=false`/`error`。当前工具结果都是 `tool.Result{success,data}` 且 `data` 为对象，实际触发不到；注释也写明了交给最小标记兜底，属可接受的取舍。
   - 建议（可选）：标记里带上原 `success`（和 `error`），如 `{"success":false,"error":"…[结果过大]…"}`/保留原 `success` 值，成本一行，能避免下游把「截断」误读成「失败」或反之。

3. **设计文档还停在「监控/调试读取」，监控快照已在本轮摘掉**
   - 位置：`docs/design/event-threads/design.md:611`、`:804`（「状态页只剩监控/调试读取」「`ThemeState` 仅剩监控/调试读取」）。
   - 现状：`appinit/router.go:31-40` 已不再注册 `themes` 快照，`ThemeState` 的读取方只剩 Admin 的 message-debug（`controller/message_debug_handler.go`）。文字不改会让后来者以为监控还在读。
   - 建议：两处改成「仅调试读取（Admin message-debug）」。另 §8.4（`:616`）与后续变更（`:799`）里的「全文向量」实际包含旧 theme concept 向量（`ThemeEmbedder` 用 `entity_type=theme` 写入），可顺手注明，避免下次清理时以为 concept 向量漏了。

4. **`entity-gc --purge-legacy-themes` 没写「先停服务」，且统计在写事务之外**
   - 位置：`server/cmd/entity-gc/main.go:26-48`（帮助/示例）、`server/internal/entitygc/gc.go:171-196`（先 Count）、`:198-219`（再开事务删）。
   - 影响：服务运行时跑，Count 与实际删除之间可能有增量（旧主题已停写，实际几乎不会变），且进程内向量库仍持有旧的 theme 向量直到重启（无读取方，所以无害）。属提示缺失，不是数据问题。
   - 建议：帮助与设计 §8.4 补一句「建议先停服务再跑」；与 §8.5 冷启动的同类提示保持一致。

### 既有问题（不属本阶段，顺带记录）

- **`max_tool_result_chars` 不作用于主对话的实时工具结果**：主循环把 `json.Marshal(result)` 原样塞进 LLM 消息（`server/internal/agent/orchestrator.go:1771-1780`），截断只发生在 mini_react（`mini_react.go:382-385`）和历史回放（`orchestrator.go:2126`，仍是裸 rune 切片）。也就是说主对话里一次大的 `event.get` 仍会完整进入当轮上下文。这是既有行为（其它工具同理），但本阶段的说明文字容易被理解成「event.get 已经被 2000 字截断」，需要知道真实边界。
- 阶段 8 单测注释里「拼装循环靠这个 JSON 判断归属」不准确：`event_assembler.go` 并不解析工具结果的 JSON（归属来自 LLM 输出；`ToolCallLog` 只用于子任务摘要）。截断修成合法 JSON 仍然是对的，只是别让注释误导后续排查。

## 做得好的地方

- **截断方向正确**：字符串先按 rune 截（不劈多字节）、骨架超预算才丢数组条目，保留靠前条目（事件按 `updated_at DESC`、搜索按相关度，正好都是「尾部最不重要」），并在根对象显式标注省略数，LLM 能知道结果不完整。
- **测试打在真实故障面**：`subagent_test.go:1045-1096` 直接用 40 条记忆的 `event.get` 形态，断言「合法 JSON / `success` 保留 / 元信息保留 / 条目结构完整」，而不是造一个小样例走过场。
- **清理工具边界干净**：先统计后事务、失败整批回滚、`--write` 走 `GuardProdWrite`，测试同时覆盖 dry-run 不删、write 只删 theme、note/topic 数据不受影响、重跑幂等（`gc_test.go:121-196`）。
- **主题概念向量归属核对无误**：`theme_embedder.go:52-77` 用 `entity_type=theme` 写 concept 向量，`ConceptEmbedService` 只给 `topic` 建 `entity_type=concept`，所以按 `entity_type=theme` 删不会留孤儿 —— 这块没有隐藏缺口。
- **监控收尾配套**：`router.go` 摘注册、`AdminView.vue:848` 改文案一起做；`cron_runner.go:45` 的注释本来就把 `discoverTimes` 写成「每日回顾」，新文案与实现一致。
- **端到端注入测试到位**：`TestBuildUserMessage_InjectsEventZone` 钉住「事件只在资源区出现一次、且在 `user_query` 之前」，`TestBuildUserMessage_CarriesEventAcrossWindow` 钉住「新窗口 carried 是 summary 且不带记忆正文」。
