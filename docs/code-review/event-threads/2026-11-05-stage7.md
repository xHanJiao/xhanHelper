## 结论

**REQUEST_CHANGES**：1 个 P1（Swift 事件页的错误态会「粘住」，一次失败后整页不可恢复，只能重启 app；改动只有几行），6 个 P3 可在阶段 8 验收前顺手收。

服务端这轮是干净的：只读接口的用户隔离、软删过滤、分页口径、避免 N+1 都做对了，`/api/themes` 与 `ThemeHandler` 删得很彻底（全仓无悬空引用）。Vue 页面沿用了 `MemoryView` 的成熟骨架（路由 meta / `PageHeader` / `ListItemCard` / `NPagination`），没有引入新范式。

## 发现

### P1 - High

1. **Swift 事件页一旦失败就永久停在错误页：`errorMessage` 只写不清，且三个不同作用域的失败共用一个字段**
   - 位置：
     - `client/xHelper/xHelper/Shared/ViewModels/EventViewModel.swift:23-36`（`load()` 成功分支不清 `errorMessage`）；
     - `:38-51`（`loadMore()` 失败也写 `errorMessage`）；
     - `:53-63`（`loadDetail()` 失败也写同一个 `errorMessage`）；
     - `client/xHelper/xHelper/Shared/Views/PageContainer.swift:39-45`（`errorMessage != nil` 优先于内容渲染，整页换成「错误 + 重试」）；
     - `client/xHelper/xHelper/Shared/Views/EventListView.swift:12,15`（把该字段直接喂给 `PageContainer`，`重试` 仍调 `load()`）；
     - `client/xHelper/xHelper/Shared/Views/EventDetailOverlay.swift:57`（`.task` 加载详情）。
   - 现象：任一请求失败 → `errorMessage` 被赋值；之后哪怕 `load()` 成功拿到数据，`PageContainer` 依然渲染错误视图（重试按钮永远救不回来）。VM 由 `ContentView` 的 `@StateObject` 持有（`ContentView.swift:310`），切面板/重开面板都不会重建，**只有重启 app 才会清掉**。
   - 三个触发面：
     1. 列表请求失败（网络抖动 / 服务重启）；
     2. 向下滚动触发 `loadMore()` 失败——会把已经显示出来的列表整页打掉；
     3. **关闭正在加载的详情弹窗**：`EventDetailOverlay` 的 `.task` 随视图消失被取消，`URLSession` 抛 cancellation，`loadDetail` 的 `catch` 照样写 `errorMessage` → 背后的列表变错误页（不需要真的断网）。
   - 影响：新加的事件页在真实使用中很容易「看着看着就变成错误页且回不来」，属于功能不可用，不只是文案问题。
   - 建议（保持最小改动）：
     - `load()` 开头 `errorMessage = nil`，与仓库既有写法一致（`MemoryViewModel.swift:35-36`）；
     - 详情失败/取消不要写列表字段：单独的 `detailErrorMessage`（或 `catch is CancellationError { return }` + 弹窗内提示）；
     - `loadMore()` 失败不要占用整页错误态（用 `isLoadingMore` + 卡片尾部提示，或成功后统一清空）；
     - 顺手让弹窗在失败时显示一行原因 + 重试（现在详情失败后弹窗只剩标题和「N 条记忆」，见 P3-4）。

### P3 - Low

2. **Swift 每次进入事件面板都打两次列表请求**
   - 位置：`client/xHelper/xHelper/Shared/Views/PageHolders.swift:76-79`（`EventPage` 挂 `.task`）+ `client/xHelper/xHelper/Shared/Views/EventListView.swift:33`（列表自己也挂 `.task`）。
   - 影响：打开面板 / 每次切回面板都会并发发两个 `GET /api/event-threads`；两个 `load()` 都 `offset=0`，结果一致所以看不出来，只是白费一次请求。
   - 建议：删掉 `EventPage` 的 `.task`（`MemoryPage` 里已经注明了「加载由列表自己的 `.task` 负责」）；`AgentPage` / `BillPage` 也有同样问题，但那是既有代码，可一起清也可不动。

3. **Swift 分页失败会静默跳过一整页**
   - 位置：`client/xHelper/xHelper/Shared/ViewModels/EventViewModel.swift:41`（先 `offset += 50` 再请求），`:46-49`（失败不回滚）。
   - 影响：某页加载失败后，用户再滚动会请求 `offset + 100`，中间 50 条永远看不到（`hasMore` 仍为 true，不会提示缺口）。事件超过 50 条才会遇到。
   - 建议：成功后推进 offset，或直接 `offset = events.count`。

4. **Swift 详情加载失败/取消后弹窗是空壳**
   - 位置：`client/xHelper/xHelper/Shared/Views/EventDetailOverlay.swift:46-48`（只处理 `detail == nil && isLoadingDetail`），失败时两条件都不成立，只剩标题与「N 条记忆」。
   - 建议：弹窗内显示 `detailErrorMessage` + 重试按钮；与 P1-1 的拆分一起做。

5. **Vue 详情弹窗存在请求竞态（快速关 A 开 B 时正文会短暂串台）**
   - 位置：`front-end/src/views/EventView.vue:45-57`（`openDetail` 无请求序号/取消）。
   - 现象：打开 A → 关闭 → 打开 B，A 的响应后到会写入 `detail`，弹窗标题（`:title="detail?.name"`）与正文都短暂变成 A 的内容，等 B 返回再纠正。
   - 建议：`const seq = ++detailSeq` 回来后比对，或 `AbortController` 取消上一个请求（仓库其它列表也没做取消，属小概率，不阻塞）。

6. **已软删事件仍可通过详情 URL 正常查看，客户端又不认 `is_deleted`**
   - 位置：`server/internal/controller/event.go:99-134`（只判 `e == nil`）、`server/internal/service/event_repo.go:97-108`（`GetByID` 含软删）、`client/.../EventViewModel.swift`（模型没解 `is_deleted`）、`front-end/src/views/EventView.vue`（不读该字段）。
   - 影响：列表默认隐藏已删事件，但书签/旧链接打开一个已删/已合并的事件时，两个客户端都会当成正常事件展示（记忆已回池，所以显示 0 条）。设计里「已删也返回 `is_deleted`」是给 `event.get` 工具（拼装/LLM 视角）定的，HTTP 层受众不同。
   - 建议：HTTP 层 `is_deleted` 直接 404（与列表口径一致，改动一行）；若想保留，两个客户端至少把 `is_deleted` 渲染成显式标记。

7. **单测只覆盖 happy path，注释承诺的排序没有断言**
   - 位置：`server/internal/controller/event_test.go:18`（注释承诺「updated_at 倒序」）、`:81-109`（实际只断言了名字 / 条数 / facts）；未覆盖分页参数与「列表过滤已删事件」（repo 层有，controller 层没有）。
   - 建议：给两条记忆显式不同的 `UpdatedAt`，断言返回顺序；顺手补一条 `limit/offset` 断言。

8. **文档小尾巴**
   - `server/internal/model/event.go:13` 仍写「阶段 7 再定名」，路由已定为 `/api/event-threads`，建议改成陈述句。
   - 设计 §8.3 把 `controller/theme.go` + `/api/themes` 列在「阶段 5 已删除」，实际是本轮（阶段 7）删的；「后续变更」有记录，但读 §8.3 会以为阶段 5 就没了。建议在 §8.3 那两行后补「（实际在阶段 7 收尾删除，见后续变更）」。

## 做得好

- **只读边界干净**：HTTP 层只有两个 GET，写操作全部留在聊天里的 `event` 工具；路由挂在 auth 分组下，`GetByID` 带 `user_id`，别人的事件返回 404（有单测钉住「不泄露存在性」）。
- **列表没有 N+1**：先按页取事件，再用 `CountByEventIDs` 一次 `GROUP BY` 拿记忆数（空列表直接短路），`Count` 与 `List` 的 `is_deleted` 口径一致，分页总数不会和列表打架。
- **详情排序放在 Go 里**：`updated_at DESC` + `id` tie-break（`event.go:116-121`），不依赖 MySQL/SQLite 对时间/NULL 的排序差异，也没有把大字段排序下推到 DB 的口径依赖。
- **脏 facts 降级**：解析失败只记日志、`facts` 返回空，不会把详情打成 500。
- **命名避坑**：`/api/event-threads` 与活动埋点 `POST /api/events/batch`、`events.db` 的 `events` 表彻底错开，设计里「不要用 `/api/events`」的约定落地了。
- **旧页面拆除彻底**：全仓已无 `AppTheme` / `ThemeViewModel` / `ThemeListView` / `ThemeDetailOverlay` / `listThemes` / `BrowsePanel.themes` 残留；`ThemeHandler` 与 `/api/themes` 无任何引用（`go build` + `rg` 双向确认）。
- **前端骨架一致**：Vue 的根节点、`page-scroll`、路由 meta（`backToChat`/`hideTabs`/`contentHeader`）、12 条/页的分页方式都与 `MemoryView` 一致；Swift 复用 `PageContainer`/`CardGridView`/`CardStyle`/`DetailSheet`，`CardStyle.theme` 换成 `.event` 并改用 `appAccent` token（两个 target 的 asset 目录都有该 colorset，含深色变体）。
