# 行为准则准则 4 被劈出编号列表 —— 一次没修对的修复

## 问题表现

系统提示词「行为准则」的 markdown 预览里：

- 准则 4「记录与维护」只渲染到「…用户分享的外部信息。」；
- 中间飘着一整段**无编号**文字：`一条记忆 = 一件事…属于文档台账。` 与**本属准则 4 的**「用户纠正或更新已有事实…才用一行说明改了什么」被粘成一段，掉在列表外；
- 再往下 5–9 才重新成表。

## 根因

`promptbuilder/memory_definition.go` 的 `MemoryDefinition` 常量里有一个**空行**。准则 4 当时用
`fmt.Sprintf` 把整段拼进列表项：

```
4. 记录与维护：…——记忆是从…外部信息。
                                       ← MemoryDefinition 里的空行
一条记忆 = 一件事…文档台账。            ← 行首在 col 0，没缩进到列表内容列（`4. ` 的内容列是第 3 列）
   用户纠正…说明改了什么
```

CommonMark 的判定：列表项内出现空行后，下一行若未缩进到该项的内容列，**该项即结束**，后续行变成列表外的顶层段落。所以准则 4 的续段整块掉出列表。而后续若没有空行，`5.` 会被并进这个顶层段落（这就是最初报的「5–9 被准则 4 吞掉」）；补了空行，`5.` 就另起一个新列表——数字看着对了，但准则 4 的形状已经坏了。

两个并存的毛病：

1. **内容重复**：`MemoryDefinition` 的定义部分（一条记忆=一件事、topic ≤5 字、逐日流水走文档）与 `record_memory` 工具说明 + 参数 schema 重复。
2. **格式脆弱**：一个「纯文本常量」被拼进「markdown 有序列表项」，常量里的空行/缩进会破坏列表结构。

## 走错的修复（528b793b）

给「5. 诤友」前补了一个空行。方向反了：它只让 5–9 不再被吞（数字恢复），代价是准则 4 彻底被劈开。同批加的 `TestCorePrinciplesListNotSwallowed` 只断言字符串里有 `"\n\n5. "`，**钉不住真实渲染**，所以测试绿着、现象还在。

## 最终修复

准则 4 不再内嵌 `MemoryDefinition`，改成单行，只留工具描述**装不下**的行为规则（纠正/更新不留旧数据、冲突主动指出、内部动作不写回复、只对用户关心的数据用一行说明）+ 触发词。于是：

- 整个行为准则 1–9 是**连续单段项的有序列表**（没空行，不会被劈）；
- 定义只在 `record_memory` 的 description/schema 与抽取段（`extractor.go`）、决策段（`record_loop_types.go`）出现，去掉重复；
- `corePrinciples` 从 `var … fmt.Sprintf(…)` 退回普通 `const`，去掉 `fmt` 依赖。

## 钉子

`builder_test.go` 重写为 `TestCorePrinciplesListStructure`：断言 `corePrinciples` 里**没有 `"\n\n"`**（夹空行就是把项劈出列表的直接原因）、1–8 各在行首、准则 4 的行为规则关键词仍在。渲染器在服务端之外，Go 侧只钉这条原始结构不变量；真实渲染另用 markdown 预览核对。

## 教训

- 把「多段纯文本」拼进 markdown 列表项前，先想清楚列表内容列与缩进——不然格式会静默坏。
- 「字符串里有 `\n\n5.`」这种断言验证的是源码文本，不是渲染结果；能用渲染器验就别只用字符串。
