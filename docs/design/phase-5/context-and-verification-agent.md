# Phase 5 — 上下文工程升级 + 验真 Agent

> 日期: 2026-05-08 | 状态: 方案讨论中

---

## 一、上下文工程升级

### 1.1 现状问题

- 历史对话无差别塞入上下文，没有对「相关性」做筛选
- 没有 token 预算控制，长对话可能超出模型上下文窗口
- 整体输入内容（system prompt + 工具定义 + 记忆 + 历史消息）缺乏统一编排

### 1.2 目标

1. **相关性控制**：历史消息按与当前问题的相关度排序/筛选，而非简单的最近 N 条
2. **Token 预算**：设定总 token 上限，各模块（system prompt、工具、记忆、历史）按比例分配，超出部分截断
3. **输入编排**：明确每一轮发给 LLM 的消息结构，各模块按优先级组合

### 1.3 待讨论要点

- 历史消息相关度用什么策略？向量检索 vs 时间衰减 vs 混合？
- Token 预算的分配比例：system 占多少，工具定义占多少，历史消息占多少，记忆占多少？
- 编排顺序：system → 工具 → 记忆 → 历史？还是有更好的排列？
- 是否需要「摘要」机制——对超长历史做中间摘要压缩？
- 是否区分 Flash 和 Pro 两套预算策略？

## 二、验真 Agent

### 2.1 目标

给定一段文字，通过搜索引擎（Bing）、论文搜索引擎等外部信息源，核验内容真实性。

### 2.2 输入/输出

- **输入**：一段文字（用户粘贴或对话中引用）
- **输出**：逐论断的验真结果（真/假/存疑），附引用来源

### 2.3 工具/MCP

- Bing 网页搜索
- 论文搜索引擎（Google Scholar / Semantic Scholar / arXiv）
- 可能的其他信息源（维基百科、新闻 API 等）

### 2.4 待讨论要点

- Agent 的触发方式：用户显式调用 vs 聊天中自动触发？
- 验真流程：拆解论断 → 并行搜索 → 比对 → 输出结论？
- 是否需要独立的 Agent 定义（system prompt），还是复用现有智能体框架？
- MCP Server 的选择：Bing Search MCP 是否有现成的？还是自己写？
- 搜索结果如何与原文论断做比对？用 LLM 判断还是规则匹配？
- 验真结果以什么形式展示？（当前回复内嵌 vs 特殊卡片）
