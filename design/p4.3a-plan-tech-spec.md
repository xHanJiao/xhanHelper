## 一、目标

用户发复杂请求 → LLM 生成执行计划 → 并行执行独立节点 → 客户端看到节点状态列表。

```
用户: "对比1月和5月餐饮消费"

后端:
  1. LLM 生成 Plan: [query_bills(1月), query_bills(5月)] → LLM总结
  2. query_bills(1月) ─┐
     query_bills(5月) ─┘ 并发执行
  3. 汇总结果 → LLM 生成对比分析

客户端:
  ✅ 查询1月账单 (2.3s)
  ✅ 查询5月账单 (1.8s)
  🔄 分析对比...
  ⏳ 生成回复
```

    prompt := `你是一个任务规划器。根据用户请求，生成一个执行计划。

  "nodes": [

    resp, _ := o.llmClient.ChatSync(ctx, &llm.ChatRequest{...})

### 3.3 plan_executor.go — 并发执行

```go
type PlanExecutor struct {
    registry *tool.Registry
    llm      llm.LLMClient
}

func (e *PlanExecutor) Execute(ctx context.Context, plan *Plan, deviceID string) <-chan PlanEvent {
    events := make(chan PlanEvent, 32)

    go func() {
        defer close(events)

        // 1. 发整个 plan（客户端初始化显示）
        events <- PlanEvent{Type: "plan", Plan: plan}

        done := make(map[string]bool)
        for plan.Status == "running" {
            ready := findReadyNodes(plan, done)
            if len(ready) == 0 {
                break
            }

            // 2. 并发执行所有就绪节点
            var wg sync.WaitGroup
            for _, node := range ready {
                wg.Add(1)
                go func(n PlanNode) {
                    defer wg.Done()
                    events <- PlanEvent{Type: "plan_node_start", NodeID: n.ID, Label: n.Label}

                    switch n.Type {
                    case "tool_call":
                        result := e.registry.ExecuteByName(ctx, n.Tool, n.Function, n.Args)
                        if result.Success {
                            events <- PlanEvent{Type: "plan_node_done", NodeID: n.ID, Result: result.Data}
                        } else {
                            events <- PlanEvent{Type: "plan_node_fail", NodeID: n.ID, Error: result.Error}
                        }
                    case "llm_summary":
                        // 收集所有依赖节点的结果，让 LLM 总结
                        summary := e.llmSummary(ctx, plan, n)
                        events <- PlanEvent{Type: "plan_node_done", NodeID: n.ID, Result: summary}
                    case "reply":
                        // 最终回复，等同于现在的 text_delta
                        for _, r := range summary {
                            events <- PlanEvent{Type: "text_delta", Content: string(r)}
                        }
                        events <- PlanEvent{Type: "plan_node_done", NodeID: n.ID}
                    }
                }(node)
            }
            wg.Wait()

            // 标记完成
            for _, n := range ready {
                done[n.ID] = true
            }
        }

        events <- PlanEvent{Type: "plan_done"}
    }()

    return events
}
```

## 五、设计决策：Orchestrator 自动并发（非 Plan Tool）

**Plan 不作为独立 Tool。** 实测 LLM 不爱用 `plan.execute`——它觉得直接调工具更可控。反过来看，LLM 已经会在一个回复里同时调用多个工具，这就是"规划"。Orchestrator 只需识别这种场景，自动做并发和可视化。

### 5.1 职责划分

| 层 | 职责 |
|------|------|
| **LLM** | 决定调什么工具、调几个（已经会了） |
| **Orchestrator** | 检测到 2+ 个无依赖 tool_call → 自动并发 + 可视化 |

### 5.2 流程

```
LLM 返回: tool_calls=[query_bills, get_current_time]
  ↓
Orchestrator 检测: len > 1 → 包装成 Plan
  ↓
发 plan 事件（客户端初始化节点列表）
  ↓
并发执行（goroutine + WaitGroup）
  ↓
客户端实时看到节点状态:
  ✅ 查询账单 (2.3s)
  ✅ 获取时间 (1.8s)
```

### 5.3 优势

- **LLM 零感知**：不需要知道"并发"、"plan"概念
- **零 prompt 工程**：不需要引导 LLM
- **自动生效**：任何一次回复中 2+ tool_call 自动并发
- **向后兼容**：单 tool_call 走原有路径
