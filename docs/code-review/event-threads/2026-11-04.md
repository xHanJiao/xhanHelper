## 发现

### P1 - High

1. **`server/internal/agent/event_assembler.go:625` — 候选 summary 按字节截断（300 bytes）**
   - `truncateStr(c.Event.Summary, 300)` 的实现是 `s[:n]`（按 byte，见 `internal/agent/profile_worker.go:658`）。
   - summary 的硬上限是 200 **字**（rune），中文约 600 字节；超过 100 字就会被砍，且 300 字节边界大概率落在汉字中间，JSON 序列化时变成 U+FFFD。
   - summary 是 LLM 判断「记忆归哪个事件」的主要依据；阶段 4 之前没有 `event.get` 可补看全文，等于候选信息系统性残缺。
   - 建议：改为 `truncateRunes(c.Event.Summary, 300)`（或直接不截，200 字本身不长），并补一条中文 summary 的回归测试。

### P2 - Medium

2. **`server/internal/agent/event_assembler.go:405`（`applyNewEvents`）/ `:455`（`applyAssignments`）— 「一条记忆只归一个事件」未跨区块生效**
   - `applyNewEvents` 只用 `batch` 过滤 `memory_ids`，不记录“已被哪个 new_event 认领”；`applyAssignments` 的 `seen` 只覆盖 assignments 自己。
   - 同一份 plan 里若两个 `new_events` 列了同一记忆：第一个建的事件变成**空壳**（`CreateWithMemories` 专门要避免的情况），summary 描述的记忆已不在它名下；`new_events` 认领后被 `assignments` 挪走同理。
   - 违反设计 §2.1 的硬不变量。建议在 `applyPlan` 维护 `claimed map[string]string`：new_events 先认领、assignments 跳过已认领（或明确相反优先级），并在日志里说明丢弃原因。

3. **`server/internal/agent/event_assembler.go:432` — embedding 失败 fail-open，语义查重被静默跳过**
   - `duplicateBySummary` 失败时只打日志并继续创建新事件（`dedupe embed error (skip embed check)`）。
   - 设计 §4.3.1 的取向是「宁可不建，也不建错的」；embedding 故障时唯一兜底只剩归一化同名查重，同义不同名（`科三考试` / `驾照考取`）会直接长出两个事件——正是设计说的「长期两个事件并存」。
   - 建议：embedding 失败即拒绝创建（记忆留普通池），或连续失败才降级；并把该决策写进设计文档。

4. **`server/internal/agent/event_assembler.go:179` — `loadActiveEvents` 硬编码 200 条静默截断**
   - `List(ctx, userID, false, 200, 0)`：事件超过 200 后，更旧的事件既不在候选里也不参与创建查重 → 重复建 / 分配错。
   - 设计预期 20–30 个事件，但表是长期只增的。建议显式打日志，或按游标取全量；不要静默截断。

5. **`server/internal/agent/event_assembler.go:145` — 拼装可用工具缺 event 域与 `event.get`，设计 §4.3 的「自己搜」未闭合**
   - 目前只挂 `unified_search`（memory/note/summary/theme/history，没有 event 域），也没有 `event.get`（阶段 4 才加）。
   - 结果：候选 summary 看不全时无法补看完整记忆；「怀疑两个事件重复才允许搜」实际只能搜记忆，搜不到事件。
   - 建议：若确认阶段 4 一起补，在 prompt / 设计文档里写明「当前不可用」，避免后续误以为已支持；同时优先修 P1-1（两者叠加影响最大）。

6. **`server/internal/agent/event_assembler_test.go` — 成功路径与批处理无测试**
   - 现有测试覆盖工具函数与 `applyPlan` 直调；缺：
     - `Assemble` 批处理循环（>batchSize 时切批、统计累加）；
     - `EventWorker.Process` 成功路径（MemoryPhaseDone=true → ListUpdatedSince → Mock LLM → 落库），以及 MemoryWorker 报错时 done 不被置位；
     - 跨区块重复认领（P2-2）、merge 别名再次命中新建事件等组合；
     - `UserMemoryRepo.ListUpdatedSince`（`updated_at >= since` 边界）。
   - 建议至少补 1 条 `EventWorker` 端到端（可复用 `syncMockLLM`）+ 1 条双 new_event 认领同一记忆的回归测试。

### P3 - Low

7. **`server/internal/llmcost/io_audit.go:35` — 审计白名单没有 `SubEventAssemble`**
   - 新增了 `SubEventAssemble` 常量与 scenario，但 `auditWhitelist` 未登记 → 拼装的 request/response 不进 `llm_call_io`，出问题无法像记忆提取那样回放。
   - 若有意控制审计量，请在 `docs/design/llm-call-audit.md` 补一句；否则加一行。

8. **`server/internal/agent/event_assembler.go:386` — 链式合并是「半应用」**
   - `A→B`、`B→C` 同批时，代码拒绝 `B→C` 但先应用了 `A→B`，结果与 LLM 意图（全部并到 C）不一致。
   - 建议整组有链就全拒（更符合「禁止链」），或合并后重新校验 target。

9. **`server/internal/agent/event_assembler.go:352` — 写库错误只记日志、不聚合返回**
   - `applyPlan` 不返回 error：DB 整体不可用时日志刷屏，但 `EventWorker` 打的是 `assemble done ... created=0`，任务标 done。
   - 属于有意降级，但建议把失败次数汇总进 stats 一并打日志，至少能区分「LLM 输出空」和「DB 写失败」。

10. **`server/internal/agent/event_assembler.go:590` — prompt 硬编码「最多 6 轮」**
    - `max_iterations` 可配置，prompt 写死 6；配置不同值时 prompt 会撒谎。建议 `fmt.Sprintf` 注入，或删掉具体数字。

11. **`server/internal/agent/event_assembler.go:610` — 拼装输入没带 facts / tags**
    - 设计 §8.5 明确冷启动输入是 `memory_value + topic + tags + facts + 时间`，当前 builder 只放了 value/topic/date。
    - facts 是用户原话，对事件边界判断有价值；阶段 6 复用同一个 builder，建议现在补上或至少留注释。

12. **`server/internal/agent/event_assembler.go:491` — name 超长会让整条更新（含 summary）失败**
    - `UpdateSummary` 先 `validateEventName`，name >100 字直接返回错误 → 本可写入的 summary 也丢了。
    - 建议 name/summary 分开应用，或 name 超长时忽略 name、只写 summary。

## 复核 `8358fed0`（阶段 1 review 的修复）

修复方向正确，并补了针对性测试（`AssignMemoriesGuards`、`AssignDoesNotBumpUpdatedAt`、迁移 027、`is_deleted` 暴露、分页）。留 3 个小的：

1. `server/internal/service/event_repo.go:167` — `UpdateSummary` 是 check-then-act（`existsActive` 后再 `Updates`）。事件在两步之间被并发软删时，更新命中 0 行但返回 nil。事件量小、概率低；介意就补 `RowsAffected` 判断。
2. `server/internal/service/event_repo.go:59` — `CreateWithMemories` 在事务提交前就写了 `e.ID`；事务回滚后调用方手里的 `e` 会带一个不存在的 ID。当前唯一调用方失败即丢弃，建议在方法注释写明「失败时 e.ID 不可用」。
3. `server/migrations/027_create_events.sql` — 与 AutoMigrate 双保险有顺序约束：先跑 SQL 再启新二进制；反过来 `CREATE TABLE` 会因已存在而中断。建议在部署说明或迁移文件头写清楚。

## 未覆盖 / 残余风险

- **每个有记忆召回的 session 都会触发一次拼装 LLM 调用**：`BatchUpdateConfirm` 会刷 `updated_at`（设计 §4.2 已知并接受），已归属事件的旧记忆也会作为本批输入重新进入 LLM；prompt 只能让模型自行判断「内容有没有变」，实际可能产生 summary 反复重写 / 漂移。建议冷启动后观察日志里的 `updated` 计数：若每轮都很大，说明召回噪声在驱动 summary churn，需要收紧输入（例如只让 `event_id IS NULL` 的记忆进批）。
- **阶段 2 上线即开始写 `event_id`**，而注入侧（阶段 3）还没过滤 `event_id IS NULL`。当前不会重复注入（EventSource 尚不存在），是安全的；但阶段 3 上线时必须同步加过滤，否则已归属记忆会在普通记忆块和事件块出现两次。
- 未做并发验证（两个 session_end 同时拼装）；cron 侧按用户去重 + 串行执行，实际风险低。
- 未跑真实 LLM / embedding，未在 MySQL 验证 `FOR UPDATE` 与迁移执行。
