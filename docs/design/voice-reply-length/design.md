# 语音回复长度重新定档（60 字 → 分场景 200 字）设计

> 状态：**已实现（2026-11-13），待真机验收**
> 关联：`docs/design/voice-chat/design.md`（语音链路总设计，§语音回复约束 与文末 2026-11-11 条目是本次要改的旧值）
> 实测数据：线上库 2026-11-10 ~ 11-13 的语音轮（只读查询，查询语句见文末）

## 背景

2026-11-11 因为「语音回答还是偏长」，把 `voiceModeNotice` 收紧成「只回 1–3 句，最多 60 个汉字」，
并加了工具轮补刀「只回 1–3 句结论」（见 `voice-chat/design.md` 文末该日条目）。

两天后反馈反过来：**回答太短，像个傻子**。这次不是凭感觉，线上数据确认了：

| 日期 | 语音轮 | 非空回复 | 平均字数 | ≤60 字 |
|---|---|---|---|---|
| 11-10（收紧前） | 14 | 8 | 285 | 1 |
| 11-11（当天） | 75 | 35 | 191 | 9 |
| 11-12 | 41 | 24 | 65 | 14 |
| 11-13 | 10 | 6 | 51 | 5 |

规则上线后平均长度从 190–285 字掉到 51–65 字，11-13 的 6 条非空回复有 5 条 ≤60 字。
**「太短」是这条 prompt 直接造成的。**

## 问题（三条，前两条已用数据确认）

### 1. 长度一刀切，解释类问题也被压成一句

60 字对寒暄/记账是对的，对「解释原因、给判断、提方案」不够。实例：

```
用户：那其实对这些书最省心的方法就还真的是跟其他东西一起打包一起发回去，对吧？（61 字）
AI：  对，这样一次取件、一次送货，书按重量跟其他行李一起算，既不用自己跑邮局，
      也不用另约一趟；只有特别沉的几箱，才拆出去单独发。（61 字）
```

这条其实还好。真正丢信息的是多问题并存的轮次（见下条）。

### 2. 一口气说几件事时，只挑一件答

用户的长句经常包含 3–5 件事（打包 + 胃不舒服 + 去超市 + 下午出门），
「只回 1–3 句」迫使模型只回其中一件：

```
用户：……今天上午得去一趟京客隆。……下午四点出门……（80+ 字，四件事）
AI：  这早饭挺像样，热的烧饼配上麦片，对胃也舒服。吃完先去京客隆，
      回来再打包衣服和小件，下午四点出门就不慌了。（52 字）
```

另一条 54 字的回答只给了「书按公斤寄最划算」的结论，没有回答同句里的
「和其他行李合并走一趟」值不值。**这不是模型不会，是 prompt 要求它少说。**

### 3. 放宽长度后必须守住「不许 markdown」

11-11 之前那些 300–600 字的长回答里带 markdown 列表（`- 量小（一两袋）…`），
TTS 会把列表符号也念出来。放宽字数时这条约束不能一起松。

## 目标

1. 语音回复按问题类型分档：确认/闲聊/记账/提醒 1–3 句；解释/判断/方案最多 200 个汉字。
2. 用户一句话说几件事时，每件各回一句，不只挑一件。
3. 明确告诉模型「用户的话来自 ASR，可能有错别字/断句错，按上下文推断」。
4. 保住口语化、无 markdown/列表/代码块、工具结果不复述。
5. 非语音轮 system prompt 逐字节不变（前缀缓存不受影响）。

## 非目标

- 不改 `reply_form` 的常驻分档（300/500 字），也不改 `brief_answer`。
- 不改 `max_tokens`（全链路没有 `finish_reason=length` 处理，硬截断不可感知）。
- 不改客户端：TTS 切句/朗读逻辑不动，没有新的字数上限。
- 不改连续模式的分句提交、打断顺序。
- 不切模型档位：实测 51 条语音轮全走 `deepseek-flash`，但 `strong_model: deepseek-v4-pro`
  已被上游路由到同一个 V4.1-Flash，换档没有收益。

## 方案

### 1. `voiceModeNotice`（`server/internal/agent/promptbuilder/static.go`）

```text
本轮是语音对话：你的回答会被直接朗读。
- 用口语化、自然的中文（或与用户相同的语言）回答。
- 篇幅看问题：确认、闲聊、记账、提醒 → 1–3 句；要解释原因、给判断、提方案 → 最多 200 个汉字，
  结论之后把关键依据说清；用户明确要求详细才继续展开。
- 第一句就是结论或判断；不铺垫、不复述用户的话、不解释你将做什么。
- 用户一口气说了几件事时，每件各回一句，别只挑一件答（句数按件数走，不受 1–3 句限制）。
- 用户的话来自语音识别，可能有错别字或断句错：按上下文推断真实意图，别揪字面；
  确实听不准就一句话确认，不要瞎猜。
- 不用 markdown、列表、表格、代码块、链接、表情符号；要分点就用「第一、第二」这类口语词。
- 调用了工具只讲结论和关键依据，不复述工具返回的条目、路径、字段或过程。
- 与「回复形态」的篇幅分档冲突时，以本段为准。
```

关键动作是**删掉「宁可少说」**（压制力最强的一句），并把「1–3 句」的适用范围收窄到寒暄类。

### 2. 工具轮补刀（`server/internal/agent/orchestrator.go:1190`）

```go
const voiceToolRoundReminder = "（语音轮）只回结论和关键依据，不要复述上面的工具返回细节。"
```

只放宽「句数」，保留「不复述工具返回」。仍然只改本次请求的消息副本，`state.msgs` 与落库不动。

| 文件 | 改动 |
|---|---|
| `server/internal/agent/promptbuilder/static.go` | `voiceModeNotice` 文本 |
| `server/internal/agent/orchestrator.go` | `voiceToolRoundReminder` 文本 |

## 为什么是 200 字

| 参考 | 口径 | 结论 |
|---|---|---|
| 本机 `N.E.K.O`（实时语音陪伴） | 主对话**不设字数上限**，只有任务汇报写「简洁自然」 | 陪伴型产品不做硬上限 |
| 本机 `Full-Duplex-Model/cascaded-full-duplex` | 语音通道 `usually one spoken sentence, two if needed`；文字通道 `match length to the request` | 语音/文字两套规则分开写 |
| 本机 `Full-Duplex-Model/qwen-audio-agent`（客服示例） | 每轮 2–3 句，说完就停；超 3 条先报总数再问要不要逐条听 | 任务型对话才压到 2–3 句 |
| 小智 xiaozhi（国内主流语音助手） | 默认「输出控制在 50 个字内」，长内容改为**单次 ≤300 字 + 讲完问要不要继续** | 用「分段 + 征询」代替一刀切 |
| `askjg-demo-gemini-pcc` | 寒暄 1–2 句；问 how/why、讲原理必须 4–6 句 | 「语音模型天生答得短，必须主动抵消」 |
| OpenAI Realtime / Twilio 教程 | keep responses short, a sentence or two | 都是电话客服场景，任务单一 |
| 语音 prompt 工程博客 | 语音回答比文字短 60–70%，听觉注意窗 8–10 秒（中文约 40–75 字） | 解释了这个 60 字是怎么来的，也说明它只适合寒暄 |

200 个汉字 ≈ 40 秒朗读，是**解释类问题的上限**，不是默认档；默认仍走 1–3 句。
如果真机上觉得 40 秒太长，把 200 调成 150 即可，不用改链路。

## 数据依据与复查方法

线上库导入本地后（`xhan_helper_test`，`xhan` 用户只读）用以下语句复查。

**长度分布（按天）**

```sql
SELECT DATE(created_at) AS d, COUNT(*) AS n,
       SUM(CHAR_LENGTH(content)=0) AS n_empty,
       ROUND(AVG(NULLIF(CHAR_LENGTH(content),0))) AS avg_nonempty,
       MAX(CHAR_LENGTH(content)) AS max_len,
       SUM(CHAR_LENGTH(content)<=60 AND CHAR_LENGTH(content)>0) AS le60
FROM messages
WHERE role='assistant' AND request_json LIKE '%本轮是语音对话%'
GROUP BY DATE(created_at) ORDER BY d;
```

`request_json` 里带「本轮是语音对话」即语音轮（prod 开了 `debug_persist_json`，保留 3 天）。

**另外两个怀疑已排除**

- **连续模式碎片化**：18 个语音会话、144 条 user 消息，相邻 user 消息间隔中位数 115 秒，
  小于 6 秒的只有 1 次，最长连续短消息 2 条 → 不存在「模型只听到半句」。
- **模型档位**：语音轮全部 `deepseek-flash`，与强模型同一上游，换档无收益。

**上线后复查**：同一条 SQL 对比平均长度（预期回到 100–150 字）与 ≤60 占比（预期明显下降），
再抽 5 条解释类轮次读一遍，确认没有回到「300–600 字带列表」的旧状态。

## 验收

- `cd server && go build ./... && go test ./internal/agent/...` 全绿。
- `TestVoiceModeToggle`：语音轮注入新章节且位于 system prompt 末尾；非语音轮输出逐字节不变。
- 真机语音各试一次：闲聊（应 1–3 句）、解释类问题（应给依据、不超过 200 字）、
  一句话说多件事（应逐件回应）、调工具（只回结论）。
- 网页端 TTS 无 markdown 符号被念出来。

## 风险与回退

- **回到「说一大堆」**：最坏情况是解释类问题普遍接近 200 字，听感 40 秒。回退只需把 200 改成 150，
  或删掉「每件各回一句」。
- **多件事逐条答导致超长**：与 200 字上限冲突时模型可能自己取舍；观察一周，必要时改成
  「最多回应前两件，其余问用户先处理哪件」。
- **ASR 噪声提示可能让模型过度确认**：如果出现「你是说……吗」过多，删掉那一行即可，其余不受影响。
