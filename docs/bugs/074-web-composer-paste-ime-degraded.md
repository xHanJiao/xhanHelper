# 074 · 粘贴之后拼音不组词、数字变成圈码（①②③④）

> 完整复盘。前半是现象与复现（不用看代码也能读），后半是排查过程与结论（含走过的弯路）。
> 一句话给赶时间的人：**这是 iOS 27 键盘层的问题（原生 App 也中招，与我们的页面代码无关）；我们用「粘贴后重写一次输入框内容」把它顶回去。**

- 日期：2026-11-21
- 平台：iOS Safari 与主屏 PWA 都命中（苹果自带拼音、九宫格）。复现时系统版本没记；外部同类报告集中在 iOS 27（见第九节）
- 相关：`docs/bugs/073`（同一个输入框的另一个坑：组合输入中丢拼音，两者无因果关系）

---

## 一、现象

在聊天输入框里**粘贴过一次**（哪怕只粘两个字），紧接着用中文输入法：

- 拼音**不组词**了：打 `nihao` 不会上「你好」，候选条也不出现，每一下击键直接往输入框里落一个字符；
- 打数字时，落进来的是**圈码** `①②③④`（不是 `1234`）；
- 切键盘的 `123` / 字母层、切一次输入法语言，**都不恢复**；
- 但英文 `abc` 是能正常打进去的 —— 输入框没失焦，键盘也还在；
- **切出页面再回来**（或粘完等两三秒再打字）就恢复正常。

不是 100% 必现，但「粘完立刻打字」时命中率很高；我们自己的复现里，五个输入框粘 5 次能有 4~5 次坏。

## 二、如何复现

1. iPhone 用 Safari（或主屏 PWA）打开网页聊天页；
2. 在别处复制两个字；
3. 点一下输入框让光标出现 → 用弹出的操作栏「粘贴」，或点输入框上方的「粘贴」提示；
4. **立刻**（1~2 秒内）用九宫格打拼音，或打几个数字。

看到拼音不上屏 / 数字变圈码 = 复现。

---

## 三、这问题为什么难查

写下来给以后参考，这类问题的坑基本都在这里：

1. **偶发**。不是每次必现，单次试验的「好 / 坏」不能下结论 —— 这正是我们中途被带偏的原因（见第 5 步）。
2. **「切出去回来就好」有强误导性**。听起来像「某个状态卡住了、重新加载就行」，很容易猜成键盘状态、输入法切换、`blur` 后自愈之类。
3. **症状太怪**。圈码 `①②③④` 不是常见的输入法候选行为，第一反应会往「长按弹层卡住」「特殊字符键盘」上想，而真机验证把这些全否了。
4. **时间上和刚上线的一次改动重叠**。我们前两天刚把输入框从 naive-ui `NInput` 换成原生 `<textarea>`（`docs/bugs/073`），很容易默认「是我改坏的」。
5. **二分必须真机**。iOS 的 WebKit 无法在本地复现（我这边没有真机；Chrome headless 的输入法模型完全不同），每一轮实验都要「改代码 → 你上手机 → 回传结果」，单轮成本高，所以更要一次拿到尽量多的信息。
6. **探针本身会污染实验**。合成的探针页如果自己也在改 DOM、写日志，它就成了新的变量 —— 我们中途确实踩到了这一点。

---

## 四、排查过程（按时间线，含被排除的假设）

### 第 1 步：先怀疑自己刚改的输入框 —— 排除

怀疑点：上一版换掉 `NInput` 后，`autoGrow`（输入后改高度）和 `pinToBottom`（贴底滚消息列表）会在粘贴后立刻动布局/滚动，可能打断输入法。

做法：加三个临时 URL 开关，在真聊天页上分别关掉「贴底滚动」「输入后量高」「粘贴处理器」。

结果：**三个开关全关，照样坏。** 同时确认这个毛病在换输入框之前就有（老版本 `NInput` 一样）。

→ 结论：不是我们这次改动，也不是「动布局/滚动」。

### 第 2 步：做一个探针页，把「页面级」的嫌疑一条条拆 —— 全灭

做了 `/probe.html`：真 textarea + 5 个开关（引入真实的 `style.css` / `user-select:none` 那套手机规则 / `100dvh` 壳 + `--keyboard-inset` / 自动增高 / 贴底滚动）+ 事件时间线 + 圈码码点识别。

结果：**全关也坏，逐个开也坏。** 5 个假设全部排除。

但这次拿到了一条硬证据（事件时间线）：

```
6. paste
7. beforeinput insertFromPaste     ← 粘贴本身正常
8. input len=63
9. beforeinput insertText composing=false
10. input len=64                  ← 之后每按一下，长度只 +1
...
```

也就是说：**全程没有 `compositionstart / compositionupdate`** —— 输入法根本没进入「组词」阶段，走的是「击键 → 直接插一个字符」的降级路径；插进来的字符是 `⑧`（U+2467）这一类圈码。

### 第 3 步：对照实验，看是不是「所有网页都这样」—— 出现矛盾

| 对照 | 结果 |
|---|---|
| 备忘录（原生输入框） | 正常 |
| 别的网站（bing 搜索框） | 正常 |
| 我们的聊天页 | 坏 |
| 一个纯裸页（`<textarea>` + 无 CSS 无 JS） | **坏** |
| 裸页 + 我们那套布局壳（无 JS） | **不坏** |
| 裸页 + 一段「每次按键就重写 DOM」的日志 JS | **坏** |

这里出现了明显矛盾：**比裸页只多了一层布局壳的反而不坏，裸页却坏**。矛盾本身就是信号 —— 它说明这轮二分已经被「偶发」污染了（每页只试了 1 次）。

### 第 4 步：不再猜「页面哪里有问题」，改成「一次性横向对比兜底方案」

做了一个 `/fix.html`：一页 5 个输入框，**每个框自带计数器**（`插入 N 字 · 圈码 M`，只在粘贴之后开始计数），每个框挂一种「粘贴后重置编辑会话」的做法。你只需要在每个框里粘 5 次、随手打几个数字，页面自己给出比例。

| 框 | 粘贴后做什么 | 结果 |
|---|---|---|
| 1 | 什么都不做（对照） | 坏 |
| 2 | `blur()` + `focus()` | 坏 |
| 3 | **重写 value（清空再写回，保留光标）** | **好** |
| 4 | 拦截 `paste`，自己 `execCommand('insertText')` 插入 | 坏 |
| 5 | 只 `setSelectionRange` 一下 | 坏 |

一次实验就得到了可用结论：**只有「把输入框内容重写一遍」能把输入法救回来**。这条也反过来印证了第 2 步的判断 —— 坏在「编辑会话」这一层，而不在字符插入这一步（第 4 个方案插得进去，但会话还是坏的）。

---

## 五、结论：到底是什么问题

**iOS 侧的状态问题，不是我们页面的代码。**（后来在外部找到了直接同款报告，把它定性成 iOS 27 的系统级 bug，见第九节。）

证据链：

1. 纯裸页（无任何样式与脚本）也能复现 → 与我们的组件、CSS、监听器无关；
2. 备忘录（原生输入框）正常、别的网站正常 → 也不是「iOS 网页版通用」；
3. 事件层面看得很清楚：粘贴之后输入法不再发 `composition*`，击键退化成「直接插一个字符」，插入的是圈码；
4. 英文仍能正常输入、键盘不收起 → 输入框与键盘的连接还在，坏的只是「输入法组词」这条通道；
5. 切出页面（编辑会话重建）后恢复正常 → 这是唯一能解除的方式，也正好是最后采用的兜底。

**没查到的那一层**：WebKit 内部到底是哪个状态字段被打坏了，需要 Safari 网页检查器抓 WebKit 侧日志（手机上一手操作取不到），所以这条记录停在「可稳定复现 + 可稳定解除」。如果以后手上有条件抓，可以从这里接着往下推。

另外要区分清楚：这个问题和 `docs/bugs/073` 不是一回事。073 是「组合输入期间输入框变高 / 滚列表，导致未上屏的拼音丢失」，根因在我们自己（naive `NInput` 的 autosize 在组合输入时也同步 mirror），已经换原生 textarea 修掉。074 是粘贴这个动作触发的输入法降级，两者只是碰巧都在同一个输入框上。

## 六、怎么解决的

`front-end/src/views/ChatView.vue`：粘贴落字之后**把 textarea 的 value 清空再写回**（连同光标位置、内部滚动位置一起还原），用这个动作逼 WebKit 重建一次编辑会话。

- 两个入口都挂：`@paste`（光标操作栏粘贴）和 `@beforeinput` 里 `inputType === 'insertFromPaste'`（输入框上方「粘贴」提示），`setTimeout(0)` 去重，保证一次粘贴只重建一次；
- 图片粘贴路径不动（带图片且不带文字时仍然走附件逻辑，不重建会话）；
- **只在 iOS 生效**（`useDevice().isIOS`）：桌面和安卓没有这个降级态，不值得每次粘贴白丢一次撤销栈。

**已知代价**：这次粘贴不能再撤销了（重写 value 会清掉撤销栈）。后续输入仍可正常撤销到「粘贴后」的状态。

## 七、验证

真机（iOS PWA + Safari 标签页、苹果拼音九宫格）全部通过：

1. 光标操作栏粘贴 → 立刻打拼音：能组词上屏，无圈码；
2. 输入框上方「粘贴」→ 立刻打数字：落的是 `1234`；
3. 粘贴长文（4 行以上）：高度与内部滚动正常；
4. 粘贴后光标不跳位、键盘不被收起；
5. 粘贴后继续打字、Enter 发送正常。

本地（headless Chrome + CDP 模拟）：粘贴后 `value` / `selectionStart` / 高度 / `document.activeElement` 均未被破坏，后续输入与 v-model 一致，无报错。

## 八、沉淀：下次遇到「只在网页里、偶发、离开再回来就好」的输入类问题

按这个顺序走，能省掉我们这次绕的弯路：

1. **先分清「是不是我们的代码」**：一个纯裸页（只放 `<textarea>`，无 CSS 无 JS）+ 一个第三方网站 + 一个原生 App 输入框，三格对照。裸页也坏、第三方不坏，基本就能把范围收到「页面上下文」之外。
2. **「等几秒/离开再回来就好」= 时间窗问题**，不是稳定状态。此时不要按「状态卡住」的思路去猜状态机，要按「某个动作之后的一小段时间内别碰它」的思路设计修复。
3. **别用肉眼判字符**：直接把插入内容的 Unicode 码点打出来（`①②③④` 是 `U+2460` 起，`1234` 是 `U+0031` 起），一眼就能分清是「输入法给的怪字符」还是「我们自己渲染成了怪样子」。
4. **偶发问题不要单次取样**：任何 A/B 都要么重复多次、要么让页面自己计数（像 `/fix.html` 里的「插入 N 字 · 圈码 M」），否则结论会被噪声带跑。
5. **兜底方案横向对比，而不是逐个上线试**：同一页放多个变体 + 计数器，一次实验拿到比例；比「改一版 → 上一轮真机 → 再改」快一个数量级。
6. **探针页本身要干净**：它自己写 DOM / 打日志都会变成新变量。能不加 JS 就不加；一定要加时，把「加日志」本身也当成一个开关去验证。
7. **兜底要写清代价**：这次换来的是「粘贴不能撤销」。别把这类代价藏着，写进文档和交付说明里，以后有人想优化才知道边界在哪。

## 九、别人也遇到：这是 iOS 27 的系统级 bug

排查时只写到「WebKit 内部哪一层没查到」。2026-11-21 上网搜了一轮，发现这不是我们一个页面的事，而且有措辞几乎一模一样的报告：

| 来源 | 说了什么 |
|---|---|
| [Apple 中文讨论区《ios27键盘粘贴bug》](https://discussionschinese.apple.com/thread/256360227) | 粘贴后输入法失灵；给的规避是「别用键盘上方的快捷粘贴按钮，改成长按输入框选粘贴」，故障时退出 App 重开即恢复 |
| [NodeSeek《IOS27更新后的输入法Bug》](https://www.nodeseek.com/post-932326-1) | 几乎逐字对上：在聊天框点键盘上的「粘贴」，紧接着打中文拼音，九宫格没有候选，「直接变成了 ①②③ 这种带圈数字」 |
| [Anki 论坛（2026-09-30，iOS 27.0）](https://forums.ankiweb.net/t/bug-report-anki-25-09-on-ios-27-pasting/71265) | 用键盘上新出现的一键粘贴贴入日文后，罗马字输入法退化成英文键盘、还会把粘进去的内容再重复一遍；长按菜单粘贴不触发，退出该页面即恢复 |
| [Apple 英文讨论区《iOS 27: Paste sometimes duplicates text, then keyboard stops working》](https://discussions.apple.com/thread/256365306) | 同一套症状的英文版：粘贴内容重复，之后键盘打不了字 |

三条对原结论的修正：

1. **不是 Safari / WebKit 独有**。Anki 在 iOS 上是原生 App，照样中招。坏掉的层次比浏览器更高 —— 是「当前输入框的键盘输入连接」，所以页面侧没有根治手段，只能兜底。
2. **和 iOS 27 新加的一键粘贴按钮高度相关**。iOS 27（2026-09 发布）在键盘候选条上加了「Paste from …」按钮，上面几份报告都指向它；我们那个「输入框上方粘贴提示」很可能就是这个按钮。这也解释了为什么这个毛病最近才密集出现。
3. **「切走 / 换输入框 / 退出页面就好」是通用解法**，和我们的观察一致 —— 本质都是逼系统重建输入连接，我们只是用 JS 把这一步塞进了粘贴之后。

一点差异：外部报告多说「长按菜单粘贴不触发」，而我们真机上两个入口都能触发。所以别把「粘贴入口」当开关，两个入口都兜住才稳。
