# 用户画像 v2 · 人话版

> 配套技术文档：[design.md](./design.md)
> 这份只讲：为什么要改、改成什么样、你会看到什么变化、什么没做。

---

## 一、你截图里那三块，为什么长成那样

先看一个真 bug。

画像注入进模型时有个字数上限（1600 字）。超了怎么办？代码的做法是**把整个字段丢掉**，而且是从排序最前面开始丢。排序规则是"字段名的 Unicode 码位"——一个和内容重要性完全无关的东西。

按码位排下来，前七个是：出生日期、性别、称呼、籍贯、职业领域、补充说明、财务概况。后三个是：重要关系、长期目标、饮食习惯。

于是**每次超字数，被丢掉的都是前七个，留下的永远是后三个**。你截图里只剩这三块，不是巧合，是排序算出来的。也就是说：模型现在很可能根本不知道你叫什么、多大、老家在哪、在北京做什么、有房贷。

这是 P0 第一件要修的事，跟后面所有设计无关。

剩下两个毛病，是另一层原因：

**「饮食习惯」为什么像日记。**
字段的更新方式是"每次整字段重写，你没提到的就算过时"。字段又是列表，允许 5 条。于是模型面对"11-13 青岛鲜啤""11-14 起泡酒为例外""喝了打 200 块"这种信息，唯一能放的地方就是这个字段——它不放进来就得丢掉。而写进去之后，除非下次重写主动省略，它永远出不去。日积月累，一个"习惯"字段变成了一条时间线。

**为什么"已戒酒"和"喝了泡酒"能同时存在。**
因为系统里没有"这条什么时候说的、什么时候被推翻"这件事。它只有 active / outdated 两个状态，且 outdated 是"整字段重写时被省略"的副产品。没有单条失效，没有时间戳，谁也判断不了哪条新。

一句话总结：**身份（永不改）、偏好（慢慢改）、近况（天天改）被塞进了同一个格子，还共用一个很小的预算。**

## 二、改成什么样

### 2.1 画像只留 13 个格子，分六层

**第一层：身份——永不丢**

称呼、性别、出生日期、籍贯、常驻地。

这一层加了个「常驻地」，因为你现在在北京、打算回西安，这是两件事，籍贯答不了。

**第二层：怎么跟你说话——永不丢（全新）**

「协作偏好」：结论先行、别反问、别写鸡汤、预算敏感、别用 emoji 这类。

现在**完全没有这一类**。但它是唯一每轮对话都会直接影响输出的东西。以前你说一次"别反问"，它进的是记忆库，下次检索到才可能生效；放在画像里就是常驻。

**第三层：硬约束——永不丢（全新）**

「硬约束」：过敏、忌口、健康限制、宗教或法律身份上的"不能"。

"不能做什么"比"喜欢什么"稳定一个数量级，值得单独一栏。

**第四层：基本盘——有预算才进**

职业阶段、家庭结构（骨架一句：已婚 / 父母在焦作 / 弟有一子）、财务轮廓。

**第五层：偏好——有预算才进**

「饮食偏好」。注意是**偏好**，不是「饮食习惯」——只留"喜欢气泡水、无糖、不喝咖啡因"这种，啤酒节那几条会被判成事件，不进画像。

**第六层：骨架——有预算才进**

「重要关系」**保持现状**（10 条 × 80 字，一字不改）。你说了未来要直接换成事件/实体那套新机制，现在瘦身等于白做，还会给以后的迁移添麻烦。本期只让它受"禁时间锚"那条硬规矩约束——不改结构，但能立刻把"10-24 头疼强撑见小吴"这种流水账挡在门外。

「长期目标」从 5 条砍到 3 条，只留纯目标；行程、立场、历史去记忆和事件。

**删掉：「补充说明」**
它存在的意义是"没分类的东西放这"，结果就是垃圾桶。删掉，内容由前面几栏接住。

### 2.2 注入不再乱丢

- 排序改成按"层"，身份永远在前
- 超预算时**从最后一层往前丢**，先丢偏好和骨架，身份和协作偏好永远保住
- 字数上限从 **1600 提到 3000**——你说得对，1600 太紧了

  三个数字讲清楚：一是这个单位是**字符**不是 token，3000 个中文字大约 2000 token；二是「重要关系」保持 10×80 之后，13 个字段全部写满的最坏情况约 2470 字，3000 仍有余量；三是这段进的是 system prompt 的**前缀**，前缀缓存命中后基本不重复计费，真正的成本是第一次构建，不是每轮。

### 2.3 三条硬规矩（P0 就生效）

1. **画像里不许出现具体日期、金额、地点组合**。出现即判定为事件，不写。`11-13青岛鲜啤`、`10-17东京`、`喝了打200块` 这类当场出局。
2. **每条必须能脱离上下文独立成立**，不许写"以前""上周""某天"。
3. **同栏互斥取最新**。"已戒酒"覆盖"喝酒"，不许并存。

### 2.4 每条事实开始有时间（P1）

加四样东西：

- 第一次是什么时候知道的（现在那个时间会被每次重写刷新，所以看不出来）
- 最近一次是什么时候被证实的
- 被独立提到过几次
- 来自哪句话（能点回去看原文）

再补一个"失效时间"：某事结束时记下时间，而不是直接删掉。

### 2.5 有证据才进画像（P1）

- 你自己明确说的（"我就是不吃辣"）→ 直接进
- 模型自己推断的（从一顿饭推"爱吃辣"）→ 先进"观察中"，**不参与注入**
- 同一件事在别的会话里再出现一次 → 才转正

这一条会直接干掉你现在「饮食习惯」里 80% 的噪声。

### 2.6 你能自己改（P1）

**放设置里，不放右侧栏**——右侧栏是"看内容"的地方，改画像属于设置。加一个「关于我」分组：按层排列，每条显示"最近证实 11-15 · 来自「…」"，可以改、可以删、可以自己加。样式沿用设置页现有的卡片规范，不新造一套外观。

- 你手写的条目，模型永远不能覆盖，只能建议
- 你删掉的条目，模型永远不能重新写回来

这是 ChatGPT 和 Gemini 现在都在做、你完全缺失的一环。画像最怕的不是记错，是**记错了你还看不见、改不了**。

### 2.7 每周重写一次（P2）

现在的更新是"每次会话结束补一点儿"，只加不减，越堆越乱。

P2 加一个每周的整体重写：拿最近一周的事件 + 现有画像 + 高价值记忆，重新写一份干净的（有硬顶）。

关键是**重写时要喂事件**。现在抽取只看对话字面，所以它只能反复抄日期；有了事件聚合，"喝过几次酒"和"戒酒了"才有可能被正确归并。

## 三、老数据怎么修

只有一个用户，所以不做通用迁移工具，就三步，顺序不能反。

**第一步：字段搬家（跟 P0 一起，纯 SQL）**

只改格子名，不清内容：职业领域→职业阶段、财务概况→财务轮廓、饮食习惯→饮食偏好、补充说明标过时。**「重要关系」整字段跳过，一个字节不动。**

这一步必须跟 P0 同步做，否则会出现"旧格子还在喂、新格子一直空"——而且系统真的会把同一个意思存两遍。

**第二步：全量备份（跑重建之前）**

现在每次重写只保留最近 3 批历史，重建不满意时老数据可能已经被物理删了。所以先 dump 一份到 `server/data/profile-backup-<日期>.json`。

这份备份顺带当"隔离区"：被剔掉的事件条目都在里面，将来做人物/事件机制时是原料，现在不用造导入管线。

**第三步：一次性重建（P1 之后，我跑，你审）**

一条命令，默认**只看不改**，把每个字段的改动打成 diff：

```
饮食偏好
  [保留] 偏好带气、无糖、无咖啡因饮料
  [丢弃] 10-17东京…喝三杯380ml札幌啤酒共1140ml
  [丢弃] 以前330ml就微醺，现2000ml才晕
  [丢弃] 喝了打200块
硬约束
  [新增] 已戒酒 / 喝酒后头晕
常驻地
  [新增] 北京（计划回西安）
长期目标
  [保留] 回西安定居，看重生活质量与子女教育
  [丢弃] 明年与 CJ 去意大利 7 天，预算 3-4 万
  [丢弃] 2023年法国12-13天5万
```

你逐条看完，觉得行，我再加 `--write` 落库。

重建的取证顺序是**事件 → 记忆 → 旧画像**，不能让旧画像当主体——否则它会照着抄同样的噪声。「重要关系」在重建里整字段跳过。

**要接受两个"不完美"**

1. 每条事实的"第一次知道是什么时候"只能是近似值（历史时间被每次重写刷新过）。
2. 重建后画像会一次性变薄，这是预期；之后靠每周重写和证据门槛慢慢长回来。

## 四、你会看到什么变化

**P0 上线后（一轮）**

- 画像里开始出现 称呼 / 性别 / 籍贯 / 常驻地 / 协作偏好 / 硬约束
- 「饮食习惯」里不再有日期、金额、地点；啤酒那几条消失
- 「重要关系」内容不变（结构也不动），只是不再往里灌日期和流水账
- 模型终于知道你是谁、该怎么跟你说话

**P1 上线后**

- 能打开「关于我」，看见每条从哪来、什么时候被证实，能改能删
- 单次推断的东西不再立刻进画像，画质变薄但变准

**P2（本次没做）**

- 每周自动收敛一次。这次先没做：它要新存一个"上次重写时间"、还要把事件接进提取输入，方案里本来就单列一期。现在靠"每次会话增量提取 + 证据门槛 + 你能手改"已经能兜住大部分。

---

## 五、没做的事

- **人物关系完全不动**（结构不动，容量也不动，还是 10 条 × 80 字）。你说得对，这块得整个换成"事件 + 实体"那套，本次动它等于白做。只让它受"禁时间锚"那条硬规矩约束。
- **不做目标的完整状态机**。本期只把「长期目标」缩到 3 条纯目标，状态机等 P2 再评估（要不要并进 plan/todo）。
- **不做画像的语义检索**。字段有限，全量注入就够，不做向量。
- **不动 `facts` 那套表**。它没接线，保持原样。

---

## 六、按推荐已经定下的六点（不同意就说）

1. **「协作偏好」合成一栏**（沟通风格 + 硬性指令），不拆两栏——省注入字数，语义上本来就是"怎么跟我说话"。
2. **保留「常驻地」**——北京 / 西安这件事迟早要问，籍贯答不了。
3. **P0 单独先上**，不等 P1 的面板——它修的是 bug，一轮就能看出效果。
4. **「补充说明」删掉**，存量只标过时、不物理删，随时能回滚。
5. **「重要关系」一字不改**（10 条 × 80 字），等未来的事件/实体机制整体替换。
6. **「关于我」放设置页**，右侧栏保持"看内容"的定位。

## 附：怎么一眼验证那个 bug

没核对线上 MySQL 的真实数据量，所以"1600 字砍掉了 7 个字段"是从代码路径 + 截图内容（约 1450 字 + 标签 ≈ 1600，且留下的恰好是码位最大的三个字段）反推的**高置信推断**。验证只需一步：在 prompt 调试页翻完整 XML，数一下 `<profile>` 里有几个 `item`、是哪几个字段。

如果 `<profile>` 里只有「重要关系 / 长期目标 / 饮食习惯」三项，推断成立，P0 的收益会非常直接。
