# 顶栏按钮「收一半」：放不下的时候，别再整组藏起来

> 2026-10-12 · **人话版**（给人看的那份）。技术口径与文件清单在文末一小节。
> 相关：`../mac-topbar-degrade/design.md`（顶栏降级本体）、`docs/bugs/034`（"按钮不能压到聊天卡片上"那条规矩）
> 状态：已实现（单测全绿 + 双端编译通过）；真机怎么看见最后一节。

估算（开工）：5 面 / 1 缝（0 条需先建探针）/ 1 次真机往返 / 3 个待拍决定 · ~1–1.5h
估算（定稿）：4 面 / 1 缝（0 条需先建探针）/ 1 次真机往返 / 0 个待拍决定 · ~1h（0.5–1.5h）

## 一句话

窗口窄到顶栏放不下所有按钮时，原来会把**整组**按钮一次性塞进「⋯」；现在改成**能留几个留几个**，剩下的才进「⋯」。

## 原来是怎么回事

顶栏从左到右：红绿灯 → 会话下拉（"新对话"）→ 中间空一段 → 右边一串按钮。
最右边那串是你正在用的功能，比如开着浏览器时它是 7 个键
（清除数据 / 新页面 / 下载记录 / 浏览器配置 / 收藏夹栏 / 收藏夹 / 浏览历史）。

放不下的时候，之前只有两种选择：**一个不少地全显示**，或者**整组塞进「⋯」**。
所以出现了你截图那一幕：屏幕上明明还剩一大段空白，7 个键却一个都没了。

按那一屏实际量（窗口约 995、右侧栏你拖到了约 600）：

| | 数值 |
|---|---|
| 顶栏上除了中间这组按钮，其他东西一共占 | 827 |
| 因此留给中间这组按钮的宽度 | **160** |
| 一个按钮连它旁边的分隔线占 35 | 放 4 个 = 143 ✅／放 5 个 = 178 ❌ |

结论：**那一屏本来放得下 4 个**。以前是"要么 7 个、要么 0 个"，这 160 就这么浪费了。

## 现在是怎么回事

同一个位置，现在能放几个就放几个 → **露出 4 个**（清除数据 / 新页面 / 下载记录 / 浏览器配置），
剩下 3 个（收藏夹栏 / 收藏夹 / 浏览历史）进「⋯」。
**「⋯」就长在这个组的末尾**（同一个胶囊里，是那个组的最后一个按钮），不是旁边单开一个胶囊；
点它才弹出那 3 个。窗口再宽点，露出的更多，直到全露；再窄点，就一个个退回「⋯」；
**窄到一个都放不下时，才退回"整组进一颗独立的 `⋯` 胶囊"**（就是你最早那张截图的样子）。

四条规矩，免得它乱来（前三条是我定的，最后一条是你拍的）：

1. **留谁按注册顺序**：代码里排在前面的留得久。想让某个键更"抗收"，把它往前挪就行。
2. **不抢别人的位置**：中间多露一个，**不会**把右边的导航组（⌘1–6）或工具组（侧栏 / 深浅色 / 设置）挤进「⋯」。
   拿带快捷键的按钮去换一个中间按钮不划算。
3. **不压到聊天卡片上**：右栏开着时，按钮只能待在聊天卡片右边那条道里（就是 `docs/bugs/034` 修的那条）；
   那条道不够宽就一个都不露，绝不过界。**右簇（导航 / 工具两组）不参与收缩** —— 它的宽度只由按钮数决定，
   所以「绝不过界」靠右栏最小宽兜底（2026-11-18 起 424；此前 380 时 6 颗导航组会越界 36pt，
   见 `../mac-topbar-degrade/design.md` §7）。dev 构建（DEV 徽标 +52）在最小右栏下仍会越界 44pt，已接受。
4. **`⋯` 就是一个点**，不显示"还有 3 个"这样的数字；会话标题（"新对话"）也还是**最后**才收窄。

## 可选行为：不是每个组都自动省略

这套"放不下就收一部分"是**开关**，默认关：

- 右侧那两个组（浏览器~事件 / 最大化~设置）**不开** → 永远"整组在 / 整组不在"，不会变成 `⋯`，
  也不会被别的组抢位置。你截图里那两颗胶囊就是它们，永远纹丝不动。
- 中间那组（浏览器 7 键 / 文档详情 3 键）**开** → 走上面那套自动省略。

所以以后新加一组按钮，默认是"老实"的（不自动省略）；想让它省，得显式打开 —— 这就是"可选，不是必备"。

## 你会看到什么

- 那一屏：中间空白大约减半（≈320 → ≈160），多出 4 个按钮。
- 拖宽 / 拖窄：露出个数跟着变，不再是"0 或全部"。
- 拖到最窄（双栏 822 那档）：跟以前一样整组进「⋯」。
- 关掉右侧栏 / 画中画：跟以前一样（那两种形态下卡片铺满整窗，按钮本来就落在卡片上）。

## 还剩一个不完美的地方（先说清）

**会话标题短的时候，中间仍会留一段空白**（你截图里大约 150）。
原因：判断"还剩多少地方"时，代码一律**按标题最长时的宽度**预留（最多 240），
这样切换会话时按钮数量才不会一闪一闪（切到长标题会话就变一下，看着乱）。
所以标题实际只有"新对话"这么短时，多出来的那 150 只能空着 —— 你截图里剩的那段就是它。

想把这 150 也填掉，就得让"留几个"跟着标题**实际宽度**变。代价：切会话时按钮会增减。
这是口味问题，你说要，我再改（一处入参 + 一条测试）。

## 真机想看这 6 件事

1. 上图那一屏：应露出 4 个浏览器键、同一颗胶囊的末尾是 `⋯`，点 `⋯` 里每个都真的生效。
2. 拖宽拖窄：露出个数随之增减；**拖到最窄**应回到整组进「⋯」。
3. 右栏窄 + 窗口宽：中间那组**不许压到左边聊天卡片上**。
4. **窗口要能一路拖窄**：不能因为多露了按钮就卡住。
   （机制上我认为没问题——每拖一步都会重算；但这条只有真机能证，是我最想让你验的一条。）
5. 边角：`⋯` 就在中心组那颗胶囊的末尾（组内分隔线、hover 圈、点开菜单都正常），不是旁边的独立胶囊；
   右侧那两组（浏览器~事件 / 最大化~设置）**完全不变形**；⌘1–6 和设置齿轮始终在栏上。
6. 窄到"一个都放不下"时：中心组整组消失、右槽单开一颗 `⋯` 胶囊（最早那张截图的样子），里头按钮点得动。

## 技术口径与影响文件（不想看可跳过）

- **契约**：容器告诉组件「这次分到多宽」，组件回「露前 k 个 + 剩下的挂末尾 `⋯`」；它的占宽还要能被容器对账，
  所以 k 由容器用 `TopBarLayout` 的宽度账算出来，**组件自己不量宽** —— 换个地方用只需接上"这次分到多宽"。
  但今天它是 `TopBarView.swift` 里的 `private` 组件（同文件抽屉）：**真要挪去侧栏按钮行 / 输入栏 pill 行，
  得先把类型和配套的宽度口径一起提出来**（现在不做）。
- **可选开关**：`TopBarGroup.autoOverflow`（默认 `false` = 不自动省略）。两个中心组置 `true`；右侧导航/工具组不置，
  于是它们永远"整组在 / 整组不在"。宽度模型按组带这个标志，算 k 时只动开着开关的组。
- 口径：顶栏原有的四档降级（DEV 徽标 → 中心这组按钮 → 会话标题宽度）**不动**；只把其中"中心这组按钮"
  从"整组显示／整组收"改成"按剩余空间留前 k 个"。判据两道：装得进窗口宽，且不越聊天卡片右缘。
- `⋯` 的占宽：**长在组内** = 一个图标 26 + 组内分隔线 9 = **35**；**独立胶囊**（中心组一个都留不下时）
  = 38 + 组间线 9 = **47**。
- 新增一节通用小函数"一行里能露几项"（`fittingVisibleCount(count:fits:)`）+ 一个视图组件
  `OverflowCapsuleGroup`（胶囊 + 前 k 个 + 末尾 `⋯` 菜单）。**没有**去合并缩略图行那套类似逻辑
  （它已有自己的实现，目前没必要动）。
- 影响文件：`Shared/Views/TopBarLayout.swift`（口径 + 留几个的算法 + `⋯` 落位）、
  `Shared/Views/TopBarView.swift`（`OverflowCapsuleGroup` 组件、按留几个渲染、`⋯` 菜单）、
  `Shared/Services/TopBarRegistry.swift`（组的新开关）、`Tools/BrowserToolProvider.swift` +
  `Services/DocumentSelectionCoordinator.swift`（两个中心组打开开关）、
  `Tests/TopBarLayoutCoreTests/TopBarLayoutTests.swift`（纯逻辑那层尽量覆盖）、
  `../mac-topbar-degrade/design.md`（宽度表口径 + 决定 + 验收）、本文件。
- 未做：`⋯` 显示数量；右侧两组（浏览器~事件 / 最大化~设置）**不参与**部分收（开关默认关，要开得显式声明）；
  缩略图行迁移。
