# 09-25 回放结论

> 阶段 3 / 施工进度 P17 的验收产物。判定方式见实施技术方案 §1.1：跑回放脚本、输出每段起止与依据、
> 人工对照打分，**不要求逐分钟相等**，而是「这些段能被识别出来、起止误差在可解释范围内」。

## 怎么跑

```bash
cd server
go run ./cmd/activity-replay --date 2026-09-25
# 主库默认只读打开 ~/Library/Application Support/xhanHelper/xhan_helper.db
# 结果写 /tmp/activity-replay-2026-09-25.db（临时，绝不碰 prod 的 events.db）
# --no-recompute   只灌事件不跑派生（调脚本用）
# --db <path>      换主库
# --out <path>     换输出路径（默认拒绝指向 prod 事件库；确要覆盖加 --force）
# 时区固定用进程本地时区（派生层同源）；换时区请设 TZ 环境变量
```

重建口径（**只重建服务端侧**，客户端浏览/在场/电源 09-25 无数据且不回填）：

| 来源 | 主库表 | 重建事件 |
|---|---|---|
| 对话 | `messages`（user 起 turn → assistant → tool 结果） | `chat.message.sent`（**仅 user 消息**，根点事件）/ `chat.turn.started` / `chat.turn.ended` / `tool.call.started` / `tool.call.ended` |
| LLM | `llm_call_ios` | `llm.call.started` / `llm.call.ended`（`latency_ms` 补 end 时刻） |
| 系统变更 | `documents` / `user_memories` | `doc.created` / `memory.entity.changed`（`trigger=batch`） |

`event_id` 由主库主键**确定性派生**（`detID`），同一份数据重放两次得到同一批 id → 事件表幂等、可重复回放。
区间事件两端 **`pair_id` 互指对端 `event_id`**（与派生层 `pairedEnd` 的匹配口径一致，见 `main_test.go` 的互指断言）。

## 逐条判读

- **00:27–00:57**：服务端活动块 00:10–00:33 与之重叠 6min。人工段后半（00:33–00:57）无服务端事件——该段时间在改代码/提交，app 内无活动。边界差属正常。
- **05:24–08:12**：主块 05:33–06:50 完全覆盖人工段的前半，**起止都在可解释范围**。人工段里 05:26–06:58 的「浏览器深挖源码」是客户端浏览段，09-25 无数据，**等盲测日**；服务端能证明的是这段有密集的 chat/tool/llm 活动。
- **12:03–14:42**：服务端只在 11:34–12:03 有正常活动，之后是 14:16 的瞬时 memory 批（34 条）与 14:53 的 2 条——**正是人工结论里的「14:52 那批 8 个 topic 是脚本跑的」**。判定按 14:16 块的 1min 重叠给 ✓；人工段主体（12:03–14:16）在服务端无 chat 活动，符合「备份恢复/清洗」这类后台操作。
- **16:41–17:51**：块 16:47–18:18 覆盖，含 17:23 改文件（`doc` 事件）与 17:51 提交前后的密集 tool/chat。**边界对齐良好**。
- **18:31–18:38**：**服务端零事件**（18:18–20:24 空档）。人工结论是「记忆 topic **相关代码**」——这是在编辑器里写代码，不经过 app，服务端天然看不见。**这是正确且可解释的 ✗**，不是回放失败。
- **20:16 起**：块 20:24–23:28 覆盖，含 4 条 `doc` 事件（词云提交相关）。人工段里 20:33 起的浏览（小红书/抖音/知乎）是客户端段，**等盲测日**。

## 结论

- 服务端侧 09-25 回放**通过**：6 段中 5 段命中，第 6 段（18:31）是「纯本机编码、app 内无活动」，服务端不可见属预期。
- 遗留：`sessions` 五层为空（09-25 无客户端在场/焦点/电源事件，L0–L4 无原料）——这不是 bug，是「客户端侧只能上线后盲测」的直接体现（实施技术方案 §1.1）。
- 下一步（阶段 2 验收剩项 / 阶段 3 第二档）：上线后挑一天，客户端浏览/在场/电源为真数据时，用当天的 events.db 跑同一套 `Recompute` 与对照，补齐客户端侧验证。

## 复审修正记录（2026-09-27）

- **区间配对字段写错（P1）**：回放最初把 `pair_id` 填成合成串 `"<id>:s"/"<id>:e"`，而派生层 `pairedEnd` 要求 `pair_id == 对端 event_id`；
  llm/tool 区间因此 100% 配不上，`fallback_count` 虚高到 1748。已改为互指对端 `event_id`（含单测 `TestTurn/ToolCallPairIDsMutuallyReference`）。
  修正后 `interval_closed` **1914 条全部 `paired`**，`inferred_ratio=0`、`fallback_count=0`。上文数字已按修正后重跑更新。
- **`--out` 未守卫（P1）**：新增 `guardOutput`，输出路径与主库同目录或名为 `events.db` 时拒绝，除非 `--force`；防手滑抹掉 prod 事件库。
- **`--tz` 与派生层错位（P2）**：派生层固定进程本地时区，去掉 `--tz`，一律用进程本地时区（换时区设 `TZ`）。
- **其它**：`day_health` 无行显式提示（不再伪造 0）、`occurred_at` 解析失败计数打日志、`tool.call.ended` 改用配对结果消息时刻（不再恒 0）、`defaultMainDB` 返回 error 不再吞。
