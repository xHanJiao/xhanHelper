## 结论

**通过，无 P0/P1。** 2 个 P2 建议在本阶段内修掉（都只影响冷启动这个一次性工具，不影响线上链路），5 个 P3 可在阶段 8 验收前顺手收。

核心判断：**把拼装器构建抽到 `appinit.BuildEventAssembler`、让冷启动和生产共用同一个 `EventAssembler` 是本阶段最有价值的改动**——冷启动的边界校验、去重阈值、只读工具白名单全部走生产代码，不存在「两套 prompt 漂移」的老问题。游标（`db + user + created_at + memory_id`）与 `--reset` 的设计也对：不靠 `event_id IS NULL` 判进度、重置时用 `UpdateColumn` 不刷 `updated_at`（避免触发运行时的「记忆被改过」恢复路径），这两点都有单测钉住。`ResetUser` 放在事务里、`saveCursor` 走 tmp + rename，也没有半写风险。

## 发现

### P2 - Medium

1. **`--reset` 解不开「游标属于另一个库/用户」，错误提示给的自救办法正好失效**
   - 位置：`server/cmd/event-bootstrap/main.go:106`（`loadCursor`）先于 `:111`（`if *reset`）；提示文案在 `:467`（「确认后用 --reset 重跑或删除 …」）。
   - 现象：游标里 `db` / `user_id` 与本次不一致时，`loadCursor` 直接 `log.Fatalf`，进程在进入 `--reset` 分支之前就退出了。用户按提示加 `--reset` 会再次撞到同一个错，只能自己 `rm` 游标。
   - 场景：从 `dev`（MySQL `xhan_helper_test`）切到 `local.dev`，或换 `--user` 后重跑；`--dry-run` 也会被这个历史游标挡住（它只想看现状，不该依赖游标）。
   - 建议：把 `loadCursor` 移到 `--reset` 分支之后（`--reset` 本来就要删游标），或在 `loadCursor` 的 `db/user` 不一致分支里区分 `*reset`：不一致时告警、返回 `nil` 让重置照常进行；顺手让 `--dry-run` 跳过游标校验。

2. **整批 LLM 没有产出（终止早 / 空内容 / JSON 解析失败）时，游标照常前进，这批记忆永久跳过**
   - 位置：`server/internal/agent/event_assembler.go:166-174`（三种情况都 `return AssemblyStats{}, nil`）；`server/cmd/event-bootstrap/main.go:160-174`（`Assemble` 返回 nil error 就保存游标并继续）。
   - 现象：冷启动时某一批（40 条）如果 Flash 返回空/坏 JSON，`stats` 全 0，进度日志看起来和「这批全是习惯、本来就一条不分配」一模一样；游标已经越过这 40 条，**再跑不会重试**，只能 `--reset` 全部重来。§10.2 的「未分配」也就分不清是「模型判断不该建」还是「这批根本没被处理」。
   - 影响：一次性迁移的质量风险；记忆本身不丢，但事件覆盖率会静默偏低。
   - 建议（不动生产语义）：给 `AssemblyStats` 加一个 `Unparsed`（或 `Skipped`）计数，在 `assembleBatch` 的 `TerminatedEarly` / 空内容 / 解析失败分支 +1；`cmd/event-bootstrap` 每批发现有 `Unparsed > 0` 就 `log.Fatalf`（保留游标、提示重跑该批），或在收尾报告里单列「未产出批次」并让退出码非 0。`applyPlan` 的 `Failed` 同理，建议在 bootstrap 侧也当作中止条件。

### P3 - Low

3. **`--dry-run` 说「不写库」，但 `app.InitDB` 会跑 AutoMigrate，且 `resolveUser` 在本地单用户空库时可能建用户**
   - 位置：`server/cmd/event-bootstrap/main.go:88`（`app.InitDB` → `AutoMigrate`，见 `internal/app/init_db.go:82`）、`:91`（`EnsureLocalUser` 可能 `EnsureByUsername`）、`:130-133`（dry-run 提前返回）。
   - 影响：对 prod 库跑 `--dry-run` 时，护栏还没检查（`:102-104` 只在 `!*dryRun` 时调用），但 DDL 已经执行了；`EnsureLocalUser` 也可能先写一行用户再退出。护栏「写之前先问」的语义在这里不成立。
   - 说明：`GuardProdWrite` 放在 `InitDB` 之后是 `entity-gc` / `topic-clean` 等既有 cmd 的共同写法，属于仓库级老问题；本次只是新增了一个同样模式的入口。
   - 建议：至少把帮助里的「不写库」改成「不调 LLM、不改事件/记忆数据」（不承诺 schema 只读）；更彻底的做法是把 `GuardProdWrite` 提到 `InitDB` 之前（需要先能只读配置，`config.Load` 已经满足）。

4. **§10.2 要求统计「事件名两两相似 > 0.9 的对数」，`printReport` 没算**
   - 位置：`server/cmd/event-bootstrap/main.go:252`（注释「名称相似度需人工抽查，未计算」）、`:262-280`（只算 p50/p90/max、超 20 条、>3 个月、未分配）；设计要求见 `docs/design/event-threads/design.md:700`。
   - 影响：这正是结构复盘之外的重复事件信号；现在只能靠 `--review` 的 LLM 判断。改成「零」也没有可复核的数字。
   - 建议：`printReport` 里对所有事件名算两两字符/语义相似度（事件只有 23 个，O(n²) 完全够），输出 >0.9 的对数；或者把该条从 §10.2 划掉并注明「由 --review 覆盖」。

5. **`--reset` 不清 `Conversation.Extra.EventFocus` 里的旧事件 ID**
   - 位置：`server/internal/service/event_repo.go:339-359`（`ResetUser` 只清 `user_memories.event_id` + 删 events），钉住状态在 `internal/model/conversation.go:65,70`。
   - 影响：重置后这些会话的钉住列表指向已不存在的 ID。`EventSource.Fetch` 对 `active[id] == nil` 是 `continue`（`internal/agent/retrieval/event_source.go:169`），不会报错；`event.enable` 也会顺手剔除旧 ID，所以只是残留，不会坏功能。
   - 建议：若要干净，`ResetUser` 之后加一句「说明钉住列表会被下一次 `event.enable` 自动清洗」，或顺手把含 `event_focus` 的会话 Extra 也清空（一次性脚本，代价可接受）。

6. **冷启动与线上 worker 没有互斥，设计/帮助里没写「先停服务」**
   - 位置：`server/cmd/event-bootstrap/main.go:1-13`（用法说明）、`server/internal/service/event_repo.go:339`（`ResetUser` 未走 `lockRows`）。
   - 影响：如果 dev 服务同时开着，`session_end` 的 EventWorker 会和冷启动并发拼装同一批记忆；`--reset` 也可能和正在跑的拼装互相穿插。最坏是同一段记忆被两套计划分别建事件（随后靠去重/合并在下一轮收敛），不会丢数据，但会污染一次性的冷启动结果。
   - 建议：在帮助与 §8.5 加一句「冷启动期间停掉服务；`--reset` 前确认没有后台任务在跑」。

7. **`--review` 单条合并/改名失败只记日志，进程仍以 0 退出**
   - 位置：`server/cmd/event-bootstrap/main.go:388-428`（错误 `log.Printf` + `skipped++`，最后 `return nil`）。
   - 影响：脚本化跑「冷启动 + 复盘」时，失败与「没有任何改动」的退出码相同，只能靠翻日志区分（`[review] done: merged=.. skipped=..` 是可辨认的，但对 CI 不友好）。
   - 建议：`skipped > 0` 时返回 `fmt.Errorf` 或用 `os.Exit(1)`（日志已记原因，不必重复打印）。

8. **`--user` 不做存在性校验；用户不存在时静默跑出 `processed 0/0`**
   - 位置：`server/cmd/event-bootstrap/main.go:187-189`（`if userFlag != "" { return userFlag, nil }`）。
   - 影响：拼错 user_id 时不会报错，报告显示 0 事件、0 记忆，容易误判成「这个用户没有数据」。`--reset` 也不会误删（没有匹配行），所以只是误导。
   - 建议：`--user` 分支查一次 `repos.User`（`GetByID` 之类），不存在直接 `log.Fatalf`。

9. **`AGENTS.md` 的 `cmd/` 说明仍是「4 个入口」**
   - 位置：`AGENTS.md:24`（`cmd/ # 4 个入口：xhan-helper / analyze-cache / eval-export / eval-label`）。
   - 现状：`server/cmd/` 现在至少有 `topic-clean`、`entity-gc`、`backfill-audience`、`memory-reset-confirm`、`event-bootstrap`，这行在本阶段之前就已经不准，加新工具后更明显。
   - 建议：改成「主服务 + 维护/一次性脚本（见各自 `-h`）」，或列全并注明哪些是一次性工具；顺手把 §8.4 的 `cmd/entity-gc` 与 `event-bootstrap` 并列，方便验收时找工具。

## 做得好

- **只有一套拼装逻辑**：`appinit.BuildEventAssembler` 同时被 `InitAgents` 与 bootstrap 调用，只读清单（`unified_search` + `event.get`）和三项阈值（CandidateTop / DedupeSim / MaxIterations）完全同源，`ValidateNativeFC` / `ValidateReadOnlyFuncs` / `ValidateCatalog` 在冷启动也会跑，接线错了会当场 panic。
- **游标语义正确**：按 `(created_at, id)` 续跑，同秒用 ID 做 tiebreaker，`ORDER BY` 与游标谓词一致，不重不漏；GORM 会把两个 `Where` 各加括号，`OR` 不会漏掉 `user_id/source` 过滤（本轮实测生成 SQL 确认过）。
- **重置不刷 `updated_at`**：`UpdateColumn` 绕开 GORM 的 autoUpdateTime，避免把 412 条记忆全部标成「刚改过」而触发运行时的恢复拼装；单测覆盖了这一点。
- **`GuardProdWrite` 认 MySQL dev 库名**：`_test` 与 `-dev` 并列，dev 冷启动不必为了绕过护栏去 `CONFIRM_PROD=yes`；本地 prod 路径（`.../xhanHelper/xhan_helper.db`）仍然要求确认。注意这是**子串匹配**，将来若出现名为 `*_test*` 的 prod 库会误放行，属于可接受的取舍。
- **评测指标进文档**：§10.2 记了 23 事件 / p50-p90-max = 9/20/87 / 287-412 已分配 / 改名 2 合并 0，并诚实标注「30% 未分配比预期激进，prod 再看」。这些数字能直接支撑「`event_memories: 20` 要不要调」和风险 #1。
- **`server/data/` 已在 `server/.gitignore`**：游标不会被误提交。

## 冷启动 prod 前的操作建议（验收阶段用）

1. 停掉服务，确认没有 `session_end` 在跑（见 P3-6）。
2. 先 `--dry-run` 看基数，再 `--limit 40` 试一批，确认进度日志里 `created/assigned/rejected` 分布合理。
3. 全量跑完看每批日志：**如果某一批 `created/assigned/updated/merged/rejected/failed` 全 0，先怀疑是坏 JSON 而不是「全是不该建的习惯」**（见 P2-2），必要时 `--reset` 重跑该段。
4. `--review` 后人工抽查 §10.2 的「两两相似」「跨事件污染」「未分配样本」三件事。
5. 仓库里还有一份未跟踪的 `docs/design/event-threads/bootstrap-result-2026-11-05.md`（622 行，dev 事件快照，含真实记忆正文）。它是人工核查用的证据，不是工具产物；**提交前先确认是否要入库**——里面是 dev 的个人数据，且重新 `--reset` 后就会过期。
