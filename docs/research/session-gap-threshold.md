# 会话间隔阈值调研（session_gap_minutes）

**日期**: 2026-09-21
**背景**: `chat.session_gap_minutes` 同时驱动两件事——会话窗口重置（`controller/chat.go:computeWindowSize`）
和 `session_end` 后处理提取延迟（`agent/cron_runner.go`）。原值 30min 来自 2026-06 的单会话调研
（[deepseek-cache-chunk-analysis](../learning/2026-06-19-deepseek-cache-chunk-analysis.md)）。
用户体感"纯聊一般不会隔这么久"，故用全量数据复核。
**结论**: 降到 **15min**，配置与代码默认值已同步。

---

## 方法

- 数据源：本地 dev MySQL（`xhan_helper_test`），只读查询
- 口径：`role='user' AND status=1 AND is_sub_agent=0`，按 `conversation_id` 分组、按时间升序求相邻间隔
- 样本：2026-05-04 ~ 2026-09-21，361 个会话（≥2 条 user 消息的 286 个），6453 个相邻间隔
- **纯聊**定义：该会话 0 条 `tool_calls_json`、且 user 消息 ≥ 8 条（27 个会话，381 个间隔）
- 复算：`cd server && python3 ../docs/learning/responses/analyze_session_gaps.py`（加会话 id 参数则单会话模式）

## 旧结论的两个问题

1. **样本是单个会话**。旧结论 "P90 = 29.3min" 只统计了 3b3f6e2f 一个会话。同会话现在数据量翻了 3 倍，P90 已漂到 **56.7min**——30min 从来不是一个稳定拐点。
2. **30min 附近没有分布谷底**。按"每分钟密度"看，密度从 0-1min 起单调衰减，15–30min 只是一段平坦台地（纯聊 0.6~1.2/min，全量 10~25/min），真正的会话间断点要 >2h（全量 8.8%、纯聊 10.8% 的间隔都落在那）。

## 数据

全量累计覆盖：`≤10m 79.4% / ≤15m 82.3% / ≤20m 83.9% / ≤30m 85.6%`。
纯聊累计覆盖：`≤10m 77.4% / ≤15m 80.3% / ≤20m 81.6% / ≤30m 84.0%`。

即 30 → 15 只会把 **~2%**（纯聊 ~4%）的过渡新切成两段；30 → 10 约翻倍到 4~7%。

阈值扫描（段数 ≈ 提取次数 + 窗口重置次数）：

| 阈值 | 全量段数 | 全量中位段长 | 纯聊段数 | 纯聊中位段长 |
|---|---|---|---|---|
| 5m | 2176 | 1.1m | 148 | 0.9m |
| 10m | 1618 | 2.0m | 113 | 1.2m |
| **15m** | **1428** | **2.5m** | **102** | **1.4m** |
| 20m | 1322 | 3.0m | 97 | 1.9m |
| 30m | 1213 | 3.9m | 88 | 5.5m |

15min 落在 10–30min 这段低密度台地上，代价（相对 30min）：全量多 ~18% 的段，纯聊多 ~16%。

## 决策

**`session_gap_minutes = 15`**（base `config.yaml` 与 `config.go` 兜底默认同步）。
`dev=1 / test=3` 保持不动（测试便利）。

## 已知取舍

本次**未解耦**提取延迟与窗口重置——降为 15min 同时会让窗口重置得更频繁（全量段数 1213 → 1428）。
影响面有限：落在 10–30min 的间隔只占 ~5%（全量），且这些间隔里多数本就是会话结束。
若后续发现 15–30min 的正常停顿被误切（表现为任务中途丢历史 / 重复提取），再考虑拆出独立的
`extract_gap_minutes`，让提取用短值、窗口保持长值。
