## 一、P0 — Critical

### 1. `Message.swift:25 / :45`：`artifacts` 非 Optional 却带默认值 + 进了 CodingKeys → 所有历史消息解码失败

服务端字段是：

```go
Artifacts []ArtifactRef `gorm:"-" json:"artifacts,omitempty"`
```

`omitempty` 对 **nil 和空 slice 都会省略**（实测 `json.Marshal` 输出 `{"id":"x"}`，键完全不出现）。而 Swift 合成的 `Decodable` **不会使用属性默认值**（实测：`struct A: Codable { var x: Int = 0 }` 解码 `{}` 抛 `keyNotFound`）。

后果：任何没有产物的消息（≈ 全部消息）在 `GET /api/conversations/:id/messages` 与 `/messages-v2` 的响应里都缺 `artifacts` 键 → `[Message]` / `CursorMessages` 整体解码抛错 → **打开任一历史会话直接失败**。

**建议改法（最小）**：

```swift
var artifacts: [ArtifactRef]? = nil
var artifactRefs: [ArtifactRef] { artifacts ?? [] }
```

调用点（`MessageListView` 1 处、`ChatViewModel` 3 处）改用计算属性。

不要改成服务端去掉 `omitempty`：nil slice 会序列化成 `null`，非 Optional 数组解 `null` 同样抛 `typeMismatch`。

## 二、P1 — High

### 2. `server/internal/tool/html_artifact.go::create`：配额在清洗校验**之前**自增，失败也扣次数

当前顺序：`title/summary 校验 → allowOne()（自增）→ Process()（截断/空壳校验）`。

设计 §7.2 明确「不合格 → 返回错误给模型重写」，而**截断恰恰是设计列出的最大现实风险**（全链路没有 `finish_reason == "length"` 处理，`max_tokens` 触顶是静默硬截断）。模型连撞 3 次截断后，**本轮彻底无法再生成**，只能等下一轮。

**建议**：把 `allowOne` 挪到 `Process()` 之后（并发下仍有极小 check-then-create 窗口，作为防刷屏护栏可接受），或改成「先 reserve，失败时 release」。

### 3. 右栏两处守卫完全没做（设计 §9.1 + §13 验收项）

- **`BrowserToolProvider.performCloseAll()`（`:1874`）仍是 `activeTabId = nil`。**
  它只关浏览器 session，artifact tab 留在 `manager.tabs` 里；而 `isBrowseActive == true` 会让**整条 tab 条一起消失**（`RightSidebarView:247`、`:77`）。手账变成不可见，只能靠再点卡片回来。tab 条上的「退出」按钮与 artifact tab 永远同屏，很容易点到。

- **全仓没有一处 `id.hasPrefix("artifact:")` 过滤。** 实测受影响的浏览器语义：
  - `enterBrowser()`（`:2148`）：`rs.activeTabId` 是 artifact id 时直接拿它当目标，`selectTab` 因查不到 session 而 no-op → 「一键进浏览器」进不去；
  - 顶栏浏览器操作组 `visible: rs.activeTabId != nil`（`:2223`）→ 清数据 / 新标签 / 下载 / 书签 / 历史 一排按钮挂在一个 HTML 页上；
  - `performCloseTab` / `performCloseScoped`（`:1968`、`:1910`）无条件把 `rs.activeTabId` 改回网页 tab → 正在看手账时 agent 关个后台网页，视野被抢走。

设计里说「约 11 处，集中在 RightSidebarView」，实际有效触点比这个少（多数是 favicon / 右键菜单这种无害 no-op）。建议只按上面 3 处补守卫，别全量铺开。

## 三、P2 — Medium

### 4. iOS 打开链路是死代码：写了 sheet，但没人接线

`ChatView` 的 iOS 分支加了 `.sheet(item:)` + `onAppear configure`，但 iOS 的 `ChatViewModel` 在 `ContentView.init`（`#else` 分支）创建，**没有** `vm.onOpenArtifact = ...`；`onOpenArtifact` 全仓只在 `ChatTabManager` 两处赋值（macOS only）。所以 iOS 上点卡片无反应，sheet 永远不会弹。

设计 §9.1 明确要求「iOS 用 sheet 代替 tab」。`onOpenDocument` 也是同样没接线（既有缺陷），这次等于把同样的坑又踩了一遍，且多写了半套死代码。建议在 iOS `init` 里补一行复用 `ArtifactOpenCoordinator`，或删掉 sheet 那 17 行。

### 5. `HTMLArtifactView` 没有 `navigationDelegate`

设计 §9.2 要求「非 about:blank 导航一律 cancel」。清洗后仍保留 `data:image/*` 的 `href` / `<a>`（`safeURL` 对所有 url 属性一视同仁放行 `data:image/`），点一下 WebView 就导航走且没有返回入口。

### 6. 加载失败无错误态

设计 §9.2 要求「别白屏 + Toast」。现在只有 API 拉取失败有 Toast；`loadHTMLString` 失败或内容渲染空白是纯白屏，没有任何兜底。

### 7. `ArtifactRepo.SoftDeleteByConversations` / `DeleteByConversations` 是死代码

`:55` / `:66`，全仓零调用。删除逻辑实际写在 `ConversationRepo.BeginPurge` / `FinishPurge` 里，重复了两份。

### 8. Web 前端（Vue）卡片没做

设计 §10 说「做不做随你」，故按可选项处理；但 §12「涉及文件」和 §13 验收都提了。至少确认 Vue 侧不会因新字段崩（不解析未知字段，安全）。

### 8.2 更正：第一轮 P1-3a 是误判（`performCloseAll` 确实不用改）

我在第一轮把 `BrowserToolProvider.activeTabId` 和 `rs.activeTabId` 混为一谈了。实际是：

- `performCloseAll()` 改的是 **provider 自己的** `activeTabId`，从不写 `rs.activeTabId`；
- 循环里逐个 `rightSidebar?.closeTab(id)` 由 `RightSidebarManager.closeTab` 维护侧栏 active —— 关掉最后一个网页 tab 时它回落到 `tabs` 里仍存在的 tab，**包括产物页**；
- `if tabs.isEmpty` 的分支不会命中（产物 tab 还在数组里）。

所以产物页不会被「退出浏览器」藏掉；唯一残留是「只剩产物 tab 时点退出」是个无效果的 no-op（没有浏览器 tab 可关）。开发者在 `design.md §9.1` 里写的「经实现时核对不用改」结论是正确的。

### 8.3 第二轮新发现

**P2（新）——版式基线现在没有任何测试，且被锁在视图文件里**

未提交改动把基线从服务端（入库时注入）搬到客户端（加载时注入），理由成立（表现层不进库、可回溯）。但：`injectingBaseline` 是**手写字符串解析**（找 `<head`、插在 `>` 之后，还有无 head 的兜底分支），如今是全仓唯一的版式兜底，却 `private` + 依赖 SwiftUI/WebKit，**无法镜像进 SwiftPM target**，也就没法测。

这和仓库既有做法不一致（`DocumentStaleGate.swift`、`ThumbRowLayout.swift` 都是把纯逻辑抽出来进 `Package.swift` 镜像 target 再写单测）。建议抽成 `Services/ArtifactHTMLInjection.swift`（只 `import Foundation`），补三个断言：有 `<head>` / 无 `<head>` / 注入段落在模型 `<style>` 之前。

**P3（新）**

1. `makeCoordinator(loadedHTML: html)` 传的是**未注入**的原串，而 `makeNSView` 加载的是注入后的串 → 首次 `updateNSView` 必然判定「内容变了」再 `loadHTMLString` 一次（每开一篇多一次重解析）。改成 `Coordinator(loadedHTML: injectingBaseline(html))`，或先抽 `let page = injectingBaseline(html)` 复用。
2. `loadFailed` 在 `html` 变化时不复位（同 tab 内容不可变，实际碰不到；但 `updateNSView` 有重载路径，留着是坑）。
3. 设计 §9.2 要求「加载失败走 `LogBuffer.error` + Toast」，实现只有 Toast，排查时服务端/客户端日志都没痕迹。
4. 顶栏浏览器操作组仍是 `visible: rs.activeTabId != nil` → 看清数据/新标签/下载/书签/历史一排浏览器按钮挂在产物页上（§9.1 语义过滤唯一没覆盖的一处）。
5. 产物 tab 仍可被拖拽重排 / 右键「移到右窗格」，「重新加载」对它也是 no-op（纯观感，可不做）。
6. `body > *{max-width:min(760px,100%)}` 的代价备忘：模型写满幅 `body > header{background:…}` 会被收窄到 760、两侧露底色；模型自己写 `max-width:900px` 反而能覆盖基线（基线在模型样式之前）。属设计已接受的取舍，只提醒别把它当 bug 改回去。
