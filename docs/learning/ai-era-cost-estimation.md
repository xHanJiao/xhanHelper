# AI 协作下的需求成本估算：面、缝、往返

**日期**: 2026-09-18（写在「文档划线批注 P5」结束当晚）
**背景**: 一个客户端特性（文档划线批注 P1–P5）在一晚 3.5 小时里只推进到「真机验收待做」，于是回头拆解：AI 在场的情况下，时间到底花在哪，怎样才能在开工前估出量级。
**结论**: 成本不在「写代码」。合理解法是三层——**面**（我自己能闭环验证的接线）、**缝**（我判不了对错、必须真跑的地方）、**往返**（只有真人能当传感器的闭环）。面便宜、缝贵、往返是固定成本。

---

## 0. 一句话

> 面 = 必须开发、且我能自己验证对错的地方。
> 缝 = 必须开发、但我不能验证对错的地方——**它是「验证」维度的属性，不是代码的固有属性**（同一个东西，建了探针就从缝搬到面那一侧）。

---

## 1. 成本分五层

用户口头说的「设计阶段 / 开发阶段」其实混了五样不同的东西，成本函数完全不同：

| 层 | 内容 | 谁出 | 能不能自动化 | 成本性质 |
|---|---|---|---|---|
| 决定 | 要做成什么样（落点、生命周期、入口位置、取值…） | 用户拍板 | 不能 | 用户的时间；越早越便宜，返工要重做面甚至重做缝 |
| 稿 | mockup / 预览 html | AI 写，用户读 | 生成能，**读不能** | 用户的时间 = 读了多少，与 AI 画了多少无关 |
| 面 | 接线（字段、状态、UI 元素、控制面） | AI | 能（编译 / 单测） | 线性、便宜 |
| 缝 | 两个「各自认为自己对」的系统交接处 | AI + 用户 | 不能，必须真跑 | 贵在「必须跑一次才知道」 |
| 验收 | 效果、手感、审美 | 用户 | 不能 | 唯一不可消除的人类时间 |

把「决定 + 稿」叫设计阶段没错，但要意识到**这两层的成本是用户的时间**——所以「出稿」并不消耗 AI 预算，消耗的是用户读稿和拍板的注意力。

### 1.1 为什么不设「审」（人工 review）层

用户明确不 review 代码。模型里就不设这一层，但要记在账上：**这是已知的质量敞口** —— AI 写的代码默认没有人读过。兜底手段：

- 收官出一份 **≤5 条风险清单**（只给结论，不要求用户读 diff）
- 能自动判的东西**不要依赖人眼**：面靠单测、缝靠探针（§2.2）—— 把「本该靠 review 发现的」尽量改成机器可判
- 长期代价列进 §8 待观察：以后真出问题时，回头对照「哪一票是没人读过的」

## 2. 面与缝

### 2.1 判据（可直接照用）

```
编译器 / 单测 / 探针，能不能替我把错判出来？
  能              → 面      —— 这条线我自己闭环
  不能，但能造探针 → 缝      —— 先投资探针，再动手（贵，但一次性）
  不能且造不了     → 真缝    —— 必须真人往返（审美 / 手感 / 最终验收）
```

补充两点：

1. **面不等于「正确」，只等于「符合我写下的规格」。** 规格本身错了，测试一样全绿。P5 里「`doc_quote` 只准进 `XMLContext`」测试能钉死「确实只进了那儿」，但「就该只进那儿」是人的决定，不是测试判的。
2. **缝不是「跨系统」的同义词。** 跨系统（前端↔客户端）只是最常见的一种。真判据是「验证能力够不够得着」，不是「跨了几个进程」。P5 那个长批注 bug 全在同一进程里（Swift 状态 → 模板字符串 → JS DOM → 事件冒泡），照样没有任何一层能替我们判错。

### 2.2 缝可以搬（这条最关键）

同一条缝，建了探针就从「只能真人往返」变成「可真引擎自动判」。P5 实例：

| 东西 | 一开始 | 现在 | 状态 |
|---|---|---|---|
| 长批注浮层「一滚就没了」 | 缝（事件捕获阶段从后代冒到 window，我判不了） | 建 `marks-longnote-scroll` 真引擎探针 + `innerScroll` 字段 | 半自动，代价是 ~213 行 harness |
| `doc_quote` 只进 XMLContext | 面（Go 单测能判） | 不变 | 面 |
| 「浅色琥珀太浅」 | 缝 | 搬不动（审美） | 真缝 |
| 8 个交互决定 | 既不是面也不是缝 | — | 规格输入（见 2.4） |

推论：**估算时要数「还没建探针的缝」**。已经建了自查脚本的地方，成本早就预付过了（折旧回面）——这也解释了为什么 P2 最贵（56 min，在造 harness），之后越做越快。

### 2.3 常见缝清单（开工时照着勾）

- 跨语言 / 跨进程边界：Swift ↔ JS（`postMessage` / `evaluateJavaScript`）
- 模板字符串里嵌 JS/HTML（多层转义：shell → python → JS → HTML）
- DOM 渲染 vs 服务端权威（谁是唯一事实来源、有没有乐观更新、中间态怎么办）
- 请求体字段「能出现在哪」（只该进 `XMLContext`，不能漏进 `Content` / 落库）
- 原生 ↔ Web 事件（滚动 / 悬停 / 点击的传播路径，谁负责复位状态）
- 跨会话 / 跨 tab 复用对象的状态所有权（`ChatViewModel` 是复用的那一个，谁负责清、何时清）
- 生命周期 / 时序（流式中、隐藏轮、缓存命中、首帧）

### 2.4 第三种东西：决定

「要做什么」既不是实现正确性，也不是验证能力问题。P5 一晚有 8 个决定：落点（复用聊天 vs 轻量进 PiP）、引用生命周期（会话级 vs 一次性）、入口位置（hover 浮层 vs 点击菜单）、点完是否闪一下、浮层封顶取值、是否动 textarea……

- 成本是**用户的时间**，不是 AI 的
- **越早越便宜**：决定晚一拍，等于面重写、有时缝重做
- 估算时要单列：「还有几个决定没拍」

## 3. 往返

### 3.1 定义

不是「你的测试」，而是**信息闭环**：

```
我改 → typecheck → 你构建 → 你看 → 你描述 → 我诊断
```

「打包、验收」只是中间一段。往返有两种，别混：
- **验收**：这个新功能好不好用
- **回环**：上次报的 bug 真修好了吗（P5 三个 bug 各至少一次）

### 3.2 成本结构

1. **用户是唯一的传感器**：颜色、手感、选中效果只有真机能产生，AI 无法自测。
2. **固定开销**：构建几分钟 + 注意力切换 + 描述 + AI 诊断。**与这次改动多大无关**——改一个字段和改十个字段，往返成本一样。
3. 所以压缩它的正确姿势不是「少测」，而是**提高每次往返的信息量** + **减少往返次数**。

### 3.3 四条压缩手段

1. **攒批**：不依赖视觉判断的改动凑一次构建，别一个字段一趟。
2. **机器先当眼睛**：能靠截图 / 探针自动判的，别进用户的验收清单（这正是两个自查脚本的收益：把「选区对不对、浮层滚不滚」从人手里拿走）。
3. **失败自带诊断**：卫语句 + 结构化日志 + 探针，目标是真机失败一次就能定位到缝。
   - 注意适用边界：**契约违反**（payload 形状、字段没传、该复位没复位）→ 卫语句/日志极有效；**引擎行为差异**（WebKit 怎么画选区、事件怎么冒）→ 卫语句无效，只能上真引擎探针。
4. **开工就列真机清单**：哪几件事必须真人看，提前点名（P5 是 `design.md` §十一 那 8 条）。往返次数因此可预知，而不是撞到一次算一次。

## 5. 修正后的系数（当前先验，待校准）

**第一近似（推荐）：轮次数 × 4 min。** 面数和缝数用户拍不出来，但「这个功能大概要来回多少轮」拍得出来——实测轮次单价就是 4.0 min/轮（§4.1），而且**这个数天然把设计讨论、缝上的 debug、往返全含在内了**。面/缝/往返是用来往上/往下修正它的：缝多 → 上调，纯逻辑零缝 → 下调。

分解式（用来解释和修正，不是用来当主估法）：

| 项 | 值 | 来源 |
|---|---|---|
| 纯接线的面（决定已定、不跨缝） | 5–15 min | 半反推（P5） |
| 带一个未定决定、或踩一条缝的面 | 30–90 min | 先验（拍脑袋） |
| 真机往返 | 10–25 min（用户的时间） | 先验 |
| 总吞吐（含文档/稿/测试/harness） | 1000–1500 改动行 / h | 实测（4 块） |
| 产品代码吞吐 | 500–800 行 / h | 半反推 |
| 跨语言边界或动像素的直觉估算 | ×1.5–2 | 先验 |
| 轮次单价 | **4.0 min / 轮** | 实测（§4.1，n=1） |

```
成本 ≈ 轮次数 × 4min
修正 ≈ 面数 × 15min + 缝数 × 60min + 往返次数 × 20min + 待拍决定数 × 15min
```

**跨语言边界或要动像素的活，凭直觉估完至少乘 1.5。**

## 6. 开机 5 问 + 估算戳

开工前问（用户问 AI 也行）：

1. 这个行为要在几个地方出现？= **N 面**
2. 对照 §2.3 清单，跨了几条？= **M 缝**，其中几条得先建探针？
3. 编译通过后，哪些事只有真机能判？= **R 次往返**（起步按 2 算）
4. 要不要回归钉（harness / 单测）？要就单列预算
5. 还有几个决定没拍？

在 `docs/design/<feature>/` 的计划文档开头落一行：

```
估算：N 面 / M 缝（K 条需先建探针）/ R 次真机往返 / D 个待拍决定
```

AI 不应在有缝的需求上给「几小时」，只给范围；**面少、缝为零的活才给钟点**——这是方差问题，不是推诿。

### 6.1 测量口径（长期固定，改了就不可比）

- 数据源：`~/.local/share/opencode/opencode.db` 的 `message.time_created`（每条消息都有）
- 活跃时长：相邻消息间隔 **封顶 300s** 后求和（排除走开 / 挂机）
- 只计**顶层会话**；子会话（subagent）单独计数、**不叠加时长**（并行会双算）
- `turns` = role='user' 的消息数；`min/轮` = 活跃分钟 / turns
- 人类延迟 = 用户消息 − 前一条 assistant；AI 生成 = 用户消息 → 下一条用户之前的最后一条消息
- 工具：
  ```
  python3 docs/learning/tools/estimate.py --since 'YYYY-MM-DD HH:MM' --until 'YYYY-MM-DD HH:MM' \
      --ticket <票名> --pre-designed yes|no --faces N --seams M --roundtrips R --decisions D --record
  python3 docs/learning/tools/estimate.py report     # 打印账本汇总表
  python3 docs/learning/tools/estimate.py --selftest # 口径自检
  ```
- **不要用 git 提交时间**（证据见 §4.2）

## 8. 待验证的命题（明说哪些是猜的）

1. 「纯接线的面 5–15 min」在**没有预先设计**的需求上是否还成立（P5 的稿和决定都在前面做完了，是最好情况）
2. 「带决定/缝的面 30–90 min」是高是低
3. 「真机往返 10–25 min」稳定吗（与改动大小无关的假设）
4. 吞吐 1000–1500 行/h 是否随熟悉度继续上升（P2 → P3 → P4 看是在升，但 n=1 晚）
5. **出稿能省掉多少面的时间**——最值得测：找一票不做 mockup 的需求对比
6. 「探针把缝搬回面」的投入产出比（P5 上 harness 是 ~213 行 / 换来 1 条缝半自动化，值不值）
7. **口径稳定性**：`CAP=300s` 的封顶是否合适（会不会把「想了很久但没动键盘」的时间算漏）、轮次单价 4 min 在不同需求上是否稳定（这条决定 §5 第一近似能不能用）
8. **不 review 的长期代价**（§1.1）：这是主动选择的敞口，没有度量手段——只能靠以后真出 bug 时回查「这一票有没有人读过」，所以每票收官的 ≤5 条风险清单要留档

## 附：用户（hanxiao）的原始四条观察

> 1. 设计阶段出预览图或者 html 是很有用的，但是它显著增加了时间（每次需要生成很多内容，然后真人来把控）不过这个我觉得是值得的
> 2. 商量确定之后，单纯的功能开发其实很迅速，ai 生成代码的速度真的很快，并且很多时候通过单测便足以验证代码的正确性，这是 happy path，开发验证起来一般很快
> 3. 有些场景涉及到两个系统之间的连接，甚至不是后端和前端，而是前端和客户端这种，这种情况下必须真机测试，时间就会长一些（打包编译真人测试）。我觉得在这种地方，可以加入一些 fail fast 的卫语句，并且做好 print 之类的调试输出。这样的话有问题可以及时发现。
> 4. UI 等的实现效果必须由真人来验收，这就是「往返」，人每次操作打包、验收，速度总是没有 ai 快的。这也是一个时间的大卡点。

对照本文的修正：

- 第 2 条的成立前提是**不跨缝**；单测能验「面的内部逻辑」，验不了缝（P5 对照：157 条断言 + 两端 typecheck 全绿，仍有 3 个真机 bug，全在缝上）。
- 第 3 条的判据从「跨系统」换成「验证能力够不够得着」（§2.1）；「卫语句 + print」只对**契约违反**有效，对**引擎行为差异**无效，后者要真引擎探针（§3.3）。
- 第 1 条的成本函数是**用户读了多少**，不是 AI 画了多少（§1 稿那行）。
