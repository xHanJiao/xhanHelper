## 发现

### P3 - Low

1. **新测试的「关闭」断言假绿：`Extractor` 为 nil，走的是同一个早退分支**
   - 位置：`server/internal/agent/event_assembler_test.go:443`（`NewMemoryWorker(&MemoryWorkerConfig{MemoryAutoExtract: false})`，没传 `Extractor`）、`server/internal/agent/memory_worker.go:39-42`（`if !w.memoryAutoExtract || w.extractor == nil`）。
   - 现象：即使 `MemoryAutoExtract` 误写成 true、或接线传错，只要 `Extractor` 是 nil，`Process` 仍然置 `MemoryPhaseDone` 并返回 nil，这个测试照样过。它的前半段还与既有 `TestMemoryWorker_SetsPhaseDoneWhenDisabled`（`event_assembler_test.go:344-353`）重复，同一个假绿点。
   - 影响：新增测试真正有价值的是后半段「EventWorker 仍能处理 inline 记忆」，这部分有效；但「关闭时置位」这条契约并没有真正锁死。生产里 `appinit/tools.go:90` 无条件构造了 `memExtractor`，`appinit/agents.go:168-172` 传的就是非 nil 的 `tools.MemExtractor`，所以「nil 早退」和「flag 早退」是两条不同的路径。
   - 建议：给 `MemoryWorkerConfig` 传一个非 nil 的 `Extractor`（复用现有 `syncMockLLM`；若被调用会走抽取、可断言调用次数为 0），这样才证明是 flag 分支生效；或者删掉前半段，只保留链式断言，避免制造「已覆盖」的错觉。

## 核对过的点

- **配置语义**：base `config.yaml:7` 本来就是 false，`config.test.yaml` 无覆盖（继承 false），四个环境文件改成 false 后行为一致；`AutoExtractMemory()` 在 nil 时返回 false（`config.go:156-159`），合并逻辑按非 nil 覆盖（`:460-462`），没有歧义。
- **事件链路**：`appinit/agents.go:167-180` 的 worker 顺序是 summary → memory → event → profile；`MemoryWorker` 关闭时置 `MemoryPhaseDone`，`EventWorker` 只检查这个标志（`event_worker.go:41`）；输入 `ListUpdatedSince` 只按 `user_id + updated_at`（`user_memory_repo.go:157-164`），不按 source 过滤——文档里「对事件系统无机制影响」成立。
- **无数据损失**：没有删除/迁移 post_chat 记忆；`event-bootstrap` 的 source 过滤不受影响（它显式传 `post_chat` + `inline`）。
- **测试夹具**：`seedMemory` 补 `Source: inline` 比空 source 更贴近生产，且不会掩盖 source 过滤回归（若将来 EventWorker 加了限制，测试会失败）。
- **文档**：第五轮记录与第四轮的「已回退」历史、A 档判据对齐；事件侧后续变更条目准确（测试名、`ListUpdatedSince` 不过滤 source 均与实际一致）。产量数字（inline 11 / post_chat 14、存量 242）与 prod 库现状未独立核对。
