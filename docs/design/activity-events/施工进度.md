## 一、施工约定（2026-09-26 定，勿擅自改）

- **基线分支**：`main`（已取消 `local-main`）。功能分支从 `main` 切。
- **包名**：`internal/activity`（emit + 存储，内聚独立）；后续派生放 `internal/activity/derive`。
- **存储层**：GORM（`gorm.io/driver/sqlite`，已在 `go.mod`）；events.db 与主库**不共用连接**。
- **Review 预算**：每期 Go 净改动（含测试）≤ ~250 行（S≤120 / M 120–250）。超了就拆下一期。
- **采集开关**：`activity.enabled` **默认开**（config 里 `*bool`，nil = 开）；云端 `APP_ENV=prod` 必须在 `conf/config.prod.yaml` 显式 `false`。非 sqlite（MySQL/云端）一律不启用。
- **验收**：主链路相关期给"真机跑一次聊天"的观察点；纯后台期只要求 `go build ./... && go test ./...` 绿。每期做完**停下等用户 review**，不自动进下一期。
- **只 `git add` 本期路径**，禁止 `-A`。提交前须用户同意。
- **施工中改文档**：设计/契约有变，先改附表 A/B 或设计篇，再改代码；进度记在本文件。

### P2 · emit 入口 ✅（2026-09-26）

**做了什么**
- `internal/activity/emit.go`（新）：`Event`（调用方只填语义字段）+ `eventRow`（events 表行，可空列用指针→落 NULL）+ `Emitter`（唯一 emit 入口）。
  - 公共字段由 `build` 补：`event_id`（空→uuid）、`occurred_at`（零→now，ISO8601 毫秒带时区）、`received_at`（UTC）、`schema_version`、`actor` 默认 system、`trigger` 默认 manual；调用方非空值不覆盖。
  - 背压：内存有界队列（1024），满则**丢最旧** + `Dropped()` 计数，`Emit` 非阻塞。
  - 批量：1 秒或 100 条先到先刷；`insertEvents` 一批一事务，`OnConflict{DoNothing}` 同时兜 `event_id` 主键与 `(type,biz_key)` 部分唯一索引。
  - `Flush()` 供里程碑立即刷；`Close()` 停 emitter 并刷完。
  - **空 `biz_key` 落 NULL**——空串会撞部分唯一索引，把无业务键事件互相吞掉。
- `internal/activity/db.go`：`Store` 持 `em`；`Open` 起 emitter；`Store.Emit/Flush` 委托；`Close` 先停 emitter。

**验收**
- `go build ./... && go test ./...` 绿，`go vet ./internal/activity/...` 干净。
- 单测：公共字段补全、调用方值不被覆盖、`event_id` 幂等、`(type,biz_key)` 幂等、无业务键多条都留、attrs JSON、队列满丢最旧且非阻塞。

### P6 · 系统变更事件（`doc.*` / `memory.*` / `bill.created` / `reminder.*`）✅（2026-09-26）

**决策/留下的口子**
- **放弃"逐方法 EmitChange"，改用 GORM 回调声明表**：改动从 O(写方法数) 收敛到"一张表 + 每模型一个 classify"，以后加实体近乎零成本（bill/reminder 就是这么进去的）。
- `size_delta` 仅 `Document` 正文变更算差值：BeforeUpdate 读一次旧正文存 `stmt.Settings`，Update 时可选；delete=0。
- `UpdateConfirm`/`BatchUpdateConfirm`、`Document.Restore/RestoreAll`、`Bill.SoftDelete`、`Reminder.Cancel/MarkMentioned/UpdateGeneratedContent` 均被 classify 吞掉（不发）。
- 事务回滚幻影：当前无 tracked 写入在事务内（唯一带事务的 `document.purge` 不采集）；将来若把 tracked 写塞进会回滚的事务，可能多记一条，事件 fire-and-forget 可接受。
- **命中 0 行不发事件**：GORM 在 `RowsAffected == 0` 时照样触发 After 回调，故 `handle` 的 update/delete 分支加了 `stmt.RowsAffected == 0` 跳过——避免 wrong-user 删文档、重复 ack、错 id 改 topic 发出幻影事件（`track_test.go::TestCallbackZeroRowsNoEvent`）。
- **空 id 是调用方责任，有意不防**：`Model(&T{ID: id})` 在 id 为空时 GORM 会丢弃 PK 条件（`update.go` 只对非零 PK 注入 WHERE）；若方法另有余件（doc/reminder/memory 的 `user_id` 等），空 id 会退化为批量更新。这是调用方传空 id 的 typo，非正常运行路径，**不加入口守卫**。（不要退回"从 WHERE 解析 PK"方案：GORM 把 `Where("id = ?")` 存成原始 `clause.Expr` SQL 串，解析脆弱。）
- `memory.topic.cleaned` 无 ctx 标记 → actor=assistant/batch（`system` 档保留）。
- 笔记已只读 → 无 `note.*`；`theme.*` 按附表 A 暂不实现。

### P8 · 上传接口 `POST /api/events/batch` ✅（2026-09-26）

**做了什么**
- `internal/activity/batch.go`（新）：`BatchEvent`（客户端上报 DTO，字段同 events 表）+ `Store.IngestBatch`——整段同步写（绕开 emit 队列，上传要当场 ack）：补 `received_at`/`schema_version`、缺省 `actor=system`/`trigger=manual`、`INSERT OR IGNORE`（`clause.OnConflict{DoNothing}` 覆盖 event_id 主键与 `(type,biz_key)` 唯一索引两道幂等），按 `RowsAffected` 统计 `accepted`/`duplicate`，返回水位。非法体（空批次 / 缺 event_id/type）返回 `ErrInvalidBatch`。
- `internal/controller/events.go`（新）：`eventsBatch(store)` handler——`http.MaxBytesReader` 1 MiB、单段 ≤ `MaxBatchEvents(500)`、`ErrInvalidBatch`→400、其余→500；返回 `{accepted, duplicate, watermark}`。
- 路由：`auth.POST("/events/batch", ...)`；`RouterConfig.Activity` + `InitRouter` 新增 `activityStore` 形参（`main.go` 传入）。
- 测试：`activity/batch_test.go`（幂等重投、biz_key 去重、水位、attrs/缺省 actor、非法体）；`controller/events_test.go`（HTTP 契约 + 重投 + 400 + store=nil→503）。

**决策/留下的口子（待 P9 对齐）**
- **水位做成"模式 + 值"**：响应带 `watermark_kind`（`time`/`segment`），客户端按 kind 决定删除策略；`watermark` 为不透明字符串，含义由 kind 定义（将来加第三种模式只加一个 kind 值，接口不破）。
  - `time`（默认）：`watermark` = 本批最大 `occurred_at`，客户端删"≤ 水位的本地段"；依赖两端同钟。
  - `segment`：`watermark` = 回显 `segment_id`，客户端逐段删除；**不依赖客户端时钟**，供服务端/客户端分离时切换。
  - 由**服务端配置** `activity.watermark_mode` 决定（单一事实源，客户端不自报）。`segment` 模式缺 `segment_id` → 400（`ErrInvalidBatch`）。启动日志打 `watermark_mode`。
- `segment_id` 除 `segment` 模式回显外，仅用于日志，不参与幂等（幂等只看 event_id / biz_key）。
- 采集关闭（`store==nil`，如云端 prod）→ 503，客户端据此保留本地段下次重投。
- 客户端与 `Shared/Services/APIClient.swift` 的上报/搬运/按 kind 删除是 **P9**，本期只做服务端。

**决策/留下的口子**
- **逐条即时落盘**（不做内存缓冲 + 5s/50 条定时刷）：量级 ~2000 条/天，缓冲省不下什么反而把崩溃窗口内事件丢掉（偏离设计篇"抄 LogFileWriter 调度"，理由如上）。
- **一段一请求，ack 即删该段**：故不比对 `watermark`/`watermark_kind`（那是"一次搬多段"才需要的口径）；响应字段仍收下备用。将来若改成一次搬多段，再按 kind 决定删哪些段。
- 上传节拍 30s + 启动立即补投（离线缓冲）；**未挂 app 失活 flush**（逐条落盘，无缓存可刷）。
- 采集开关放在 app 层（`DeviceManager.activityCollectionActive`），core 不依赖 `LocalBackendManager`。
- 失败日志 `failures.log` 每行一条「时间+原因」，次数/最后时间由此数；未做界面提示（设计篇 4.5）。
- 事件生产者（`client.app.*`、在场/电源、浏览、输入、`user.action.*`）留 **P10/P11**；P9 只有底座。

**review 修正（2026-09-26，P1/P2）**
- **P1 半行吞事件**：`append` 追加前用读写句柄探末字节，非 `\n` 先补一个——上次进程写盘中途被杀留下的半行不再与下一条拼成一行（那样会一起变坏行丢掉）。
- **P2 覆盖丢数据**：`append` 区分"文件不存在→`.atomic` 首建"与"已存在→只追加，打不开就 throw"（旧写法在"存在但打不开"时会整文件替换丢事件）。
- **P2 静默吞**：`remove`/`noteFailure`/`init` 读计数失败各自 `log.error` 留痕（不再 `try?` 无痕）。
- **P2 字节上限**：加 `maxSegmentBytes = 1 MiB`（对齐服务端），`count>=500 || bytes>=1MiB` 提前封段——避免超限段被服务端 400 隔离而永久丢。
- **P2 DTO 默认值**：`ActivityEvent` init 去掉 `actor`/`trigger` 默认值，强制生产者显式传（附表 A 要求按事件区分）。
- **P2/P3 注释钉边界**：`DeviceManager.updateActivityRecorder` 注明本地 token 固定故 transport 快照安全（轮换需重 configure）、configure/start 与 stop 的 Task 理论乱序但本地不可达。

**明确推迟（P9 口子）**
- 单条事件本身 > 1 MiB 时该段仍会被隔离（需"单事件截断"，清理阶段一起处理）。
- `.bad` 隔离段与 `failures.log` 无保留期/清理（只增不减）。
- 未做 type 白名单/attrs 敏感字段校验——建议 **P10/P11 接入生产者前**在 `record` 出口加一道按附表 A 的字典校验。
- transport 的 configure/start 与 stop 未串行化（本地模式不可达）。
