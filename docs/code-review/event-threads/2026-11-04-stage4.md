## 结论

**REQUEST_CHANGES**，无 P1。方向与设计对齐得不错：

- **只读是结构保证**：拼装注册表只放 `unified_search` + `eventTool.ReadOnly()`（`appinit/agents.go:97-99`），`eventReadTool.Functions()` 只吐 `get`、`Execute` 另有一层拒绝；MiniReAct 的 `AllowedTools{"event":{"get"}}` 是函数级 guard，注册表过滤 + 运行时 guard 双保险，比只靠 prompt 自觉稳。
- **pinned 全链路打通**：`chat.go` 解析 `Conversation.Extra.EventFocus` → `RunRequest.PinnedEventIDs` → `mkSearchOptions` → `EventSource` 无条件 full；悬空 ID 不占名额（`event_source.go:163-177`），`enable` 写入前顺手剔除旧 ID（有测试）。
- `merge` / `delete` 的事务语义沿用阶段 2 的实现（记忆搬移 + 软删同事务、行锁、幂等、delete 后记忆回池），工具层只做参数与「已删除」判定，没有绕开 repo。
- `unified_search` 的 `theme` 域按设计换成 `event` 域，默认域同步；拼装 prompt、`profile_worker` 冷启动 prompt 都改了。
- 测试覆盖：event 工具 CRUD / 钉住上限与幂等 / 旧 ID 剔除 / 只读视图 / 关键词搜索，`unified_search` 域改写，pinned 接线。

下面 3 个 P2 里，**P2-1 是并发下会真实丢写入**，P2-2 是 design 自己两处规则打架，P2-3 是硬上限只在后台一侧执行。其余是口径/效率/测试盲区。

### P1 - High

### P2 - Medium

1. **并发 `event.enable` / `disable` 会丢更新，且两个工具都报成功**
   - 位置：`server/internal/service/conversation_repo.go:361-384`（`UpdateExtraField` 读-改-写无行锁）、`server/internal/tool/event.go:389` /`:436`（两个调用方）、`server/internal/agent/orchestrator.go:706`（`persistExposure` 也在写同一个 Extra）。
   - 主循环的服务端工具是**并发执行**的（`orchestrator.go:1866` 起 `executeConcurrently`）。模型完全可能在一轮里并列调 `event.enable(e1)` + `event.enable(e2)`（用户说"把 A 和 B 都拉出来"），两个事务都读到同一份旧 Extra，各自 append 后整列覆盖写回 → 只剩一个被钉住，另一个工具结果仍返回 `status=enabled`。
   - MySQL（REPEATABLE READ）下 `UPDATE extra=?` 会在 tx1 提交后继续写入 tx2 **基于旧快照算出的完整 JSON**，所以是静默丢更新；SQLite 单测复现不了（会先撞写锁/BUSY）。
   - 同一把锁还护着 `ToolExposure`（`persistExposure` 的注释写着"绝不覆盖并发写入的其它字段"，在当前实现下这句不成立）。
   - 建议：`UpdateExtraField` 的 `Select("extra").First(&c)` 加 `clause.Locking{Strength: "UPDATE"}`（SQLite 跳过，可复用 `event_repo.go` 里 `lockRows` 的写法）；或者对 `convID` 做进程内串行化。改完补一个并发 enable 的用例（MySQL 集成测或 sqlite 加锁后串行化断言）。这是共享代码的一行修复，收益同时给到 exposure。

2. **跨窗口的短消息轮会把 pinned 事件从 full 降成 summary，直接丢掉记忆**
   - 位置：`server/internal/agent/orchestrator.go:455-472`（`eventZonePackets` 的携带分支）、`server/internal/agent/ctxflow/resource_zone.go:246-279`（`CarryEventPackets`）、`controller/chat.go:319-328`（本轮拿得到 `PinnedEventIDs`）、设计 §6.6（"下一轮起 EventSource 无条件注入它，标记 pinned=1，跨窗口保留"）与 §6.10（"跨窗口把 full/compact 降为 summary carried，并清掉 pinned 标签"）。
   - 链路：`computeWindowSize` 判新 session + 用户只说"继续"（≤5 字 → `SkipRetrieval`）→ `retrieveResult == nil` → 走 `CarryEventPackets(prev, true)` → pinned 事件被降成 `summary carried` 且 `Memories=nil`。这一轮模型拿不到任何事件记忆，而这恰恰是"继续"最需要上下文的时刻；下一轮 EventSource 正常跑时才恢复 full。
   - 阶段 3 写下"这条路径读不到 Extra"是当时的实情，阶段 4 已经把 `PinnedEventIDs` 放进 `RunRequest` 了，前提变了但代码没跟上。设计 §6.6 与 §6.10 现在互相矛盾，验收时不知道按哪条。
   - 建议（择一，都要同步改 §6.10）：
     - 推荐：`CarryEventPackets` 增加 `pinnedIDs` 参数，命中的事件跨窗口**保持 full + 原 memories**（prev XML 里本来已经解析出记忆体，无需查库），只对其余事件降级；
     - 或者明确写"跳过检索那一轮 pinned 降为 summary，下一轮自愈"，并把 §6.6 改成"正常检索轮无条件 full"。

3. **`event.update` 写 summary 不执行 §4.4 的 200 字硬上限**
   - 位置：`server/internal/tool/event.go:474`（直接 `UpdateSummary(..., a.Summary)`）、对比 `server/internal/agent/event_assembler.go:545`（`truncateRunes(up.Summary, eventSummaryMaxRunes)`）与 `:629-630`（常量 `eventSummaryMaxRunes = 200`）。`EventRepo.UpdateSummary` 也不做长度校验（只校验 name ≤100）。
   - 工具描述里写着"≤200 字"，但没有任何强制：模型被要求"改一下这个事件的现状"时可能写几百上千字。summary 每轮都注入（pinned 更是每轮 full），会长期占事件区预算（`budget_event: 12000`），且超出 §4.4 的口径。
   - 建议：把上限下沉到 `service`（`UpdateSummary` 里截断/校验，常量移到 `model` 或 `service`），或在 tool 层复刻 200 字截断；顺带补一条超长 summary 的用例。

### P3 - Low

4. **拼装循环拿到的 `event` 工具描述是写操作版**
   - 位置：`server/internal/tool/event.go:212-231`——`eventReadTool` 覆盖了 `Functions` / `Catalog` / `ReadOnlyFuncs` / `Execute`，但没覆盖 `Description()`，仍继承 `EventTool.Description()`："只在用户明确要求查看、钉住、改名、删除或合并事件时使用；不要主动创建事件"。
   - 拼装循环里没有"用户明确要求"，这句会和 `eventAssemblySystemPrompt` 的"拿到事件 ID 后读完整事件"打架，可能让模型不敢调 `event.get`。建议覆盖一句只读描述（"读取事件全文，用于判断新记忆是否属于该事件"）。

5. **`event.get` 对已删事件返回正常 detail，与设计 §5.3 / §7.1 的"返回「事件已删除」"不一致**
   - 位置：`server/internal/tool/event.go:272-284` + `:537`（`resolveEvent` 带 `includeDeleted=true`，返回 `IsDeleted:true` 的 detail）。
   - 实现其实比设计更可用（模型能看到 `is_deleted` 与空记忆），但两份口径得统一：要么改设计，要么 `get` 命中已删时返回错误文案。别停在"代码说 A、文档说 B"。

6. **`event.search` 语义结果按注入形态排序后再截 topK，相关度高但被降级的事件会被截掉**
   - 位置：`server/internal/tool/event.go:314-345`（`t.source.Fetch` 的输出保持 EventSource 的 `pinned→full→compact→summary→index` 顺序，随后 `hits[:TopK]`）。
   - 搜索不是注入，排序应该按 score（`p.Score`）降序再截。现在 `top_k=5` 时，一个有 4 个 full 的低分事件会挤掉高分的 summary 事件。建议在 tool 侧 `sort.Slice` 一次（或让 EventSource 支持"搜索模式不按形态排"）。

7. **关键词搜事件的召回只扫最近 `top_k*4`（上限 100）条命中记忆**
   - 位置：`server/internal/tool/event_query.go:109-112`。
   - 事件名/summary 命中不受影响；只靠记忆文本命中的事件，记忆多、更新频繁时可能搜不到。属可接受的近似，建议在设计 §7.2 或工具描述里写明"记忆侧取最近 N 条"。

8. **`event.list` 为拿记忆数把事件的全部记忆整行拉回**
   - 位置：`server/internal/tool/event_query.go:54-82`（`ListByEventIDs` 取回完整 `user_memories`，包含 `facts` / `raw_json` / `extract_prompt` 等大字段）。
   - `list` 只需要计数。事件多时（冷启动后几十上百个、每个几十条记忆）一次 list 会读几百上千行。建议改成 `SELECT event_id, COUNT(*) ... GROUP BY event_id` 的 repo 方法（`event.get`/`search` 仍按需取全文）。

9. **`resolveEvent` 按 name 解析时可能命中已删事件**
   - 位置：`server/internal/tool/event.go:537-560`（`listAllEvents(..., true)` 后取第一个 `EqualFold` 命中，顺序是 `last_memory_at DESC`）。
   - 同名事件被删后重新长出来时，`enable`/`update` 可能先命中已删的那条并直接报"事件已删除"。建议优先在 active 集合里匹配，找不到再回落到含已删（`get` 需要后者）。

10. **`BudgetResourceZone` 的 `demoteEvent` 不看 `Pinned`，极端预算下 pinned 也会被降级**
    - 位置：`server/internal/agent/ctxflow/resource_zone.go:649-673`（`demoteEvent` 不检查 `meta.Pinned`；`EventSource.degrade` 是检查的）。
    - 事件区 12000 字符、pinned ≤3 时基本撞不到（3×20 条记忆 + XML 开销约 5-7k），但与 §6.5"pinned 不被降级"不一致。要么在 `demoteEvent`/`demoteLastEvent` 里跳过 pinned（注意 `budgetPerType` 的循环要能退出），要么在设计里注明"总预算兜底时 pinned 也降"。

11. **测试盲区**
    - `chat.go` 的 `Extra → PinnedEventIDs` 没有测试（只有 `mkSearchOptions` 的直传测试）；建议把那段解析抽成小函数（如 `pinnedEventIDsFromExtra(conv.Extra)`）并补 3 条：空 / `{}` / 损坏 JSON。
    - pinned 与配额/预算的交互没测：`pinned=3` + 大量 fresh 时 pinned 仍 full、fresh 先降级（`EventSource` 已实现，但没有用例钉住）。
    - 并发写入 Extra（P2-1）没有用例。
    - `event.get` 在拼装注册表里会被 `MaxToolResult: 2000` 截断（设计值），没有用例验证截断后 JSON 仍可读。

12. **文档漂移**
    - §8.5 阶段 4 列的是 `appinit/tools.go`，实际接线在 `appinit/agents.go`。
    - §7.2 "语义搜索：搜事件 summary + 聚合记忆"——实现只用记忆向量（`EventSource.searchMemoryScores`）加事件名的字面子串，summary 没有自己的向量；建议改成"以聚合记忆向量为主 + 事件名字面命中"。
    - §7.3 说拼装注册表只放 `unified_search`（memory + event 域），实际 `unified_search` 的 note / summary / history 域也照样可查（只读、无害）。要么在设计里注明"整工具放行、域不受限"，要么后续按域再收。

**通过，无阻塞项。** 三个 P2 都修到了根上，P3 全部处理（只留一条 MaxToolResult 用例，明确留阶段 8）：

- **P2-1**：`UpdateExtraField` 进程内按 `convID` 串行化（`sync.Map` + `Mutex`）+ MySQL `FOR UPDATE`（SQLite 走 `lockRows` 跳过），8 并发追加用例钉住。两层锁的定位是对的：进程内锁覆盖单实例（本地版 SQLite），行锁覆盖多进程。
- **P2-2**：`CarryEventPackets` 新增 `pinnedIDs`，pinned 跨窗口保持 full + 记忆，其余照旧降 summary carried / index 保持 index；`eventZonePackets` 从 `req.PinnedEventIDs` 传下来，端到端用例覆盖"新 session + pinned"。§6.5 / §6.6 / §6.10 的口径也一起改了，不再自相矛盾。
- **P2-3**：`MaxEventSummaryRunes` 下沉到 `service`，`UpdateSummary` 统一截断，拼装侧删掉本地常量改用同一个；超长用例验证 250 字写进去落库 200 字。
- **P3**：只读描述覆盖、`event.search` 按 score 排序、`CountByEventIDs` 聚合计数、`resolveEvent` 优先 active、`demoteEvent`/`demoteLastEvent`/预算兜底保护 pinned（含"全是 pinned 时接受超预算"且不会死循环）、`pinnedEventIDsFromExtra` 抽函数 + 5 条用例、pinned 不被 fresh 配额降级的用例、设计五处口径同步。

新代码只留三处非阻塞的小瑕疵，不影响合并：

**N1 `sync.Map` 里的 convID 互斥锁永不回收**
- `server/internal/service/conversation_repo.go:18-33`。每个会话留一个 `*sync.Mutex` + 一个 map entry，个人尺度（几千会话）几十 KB，无功能影响；若以后多租户/会话量大再换引用计数的 keyed mutex。加一行 `// shortcut:` 注明即可。

**N2 按名字操作已删事件时错误文案变了**
- `server/internal/tool/event.go:540-580`：`enable`/`update`/`delete`/`disable` 现在按名字只在 active 集合里找，命中不到时返回「事件不存在」，而按 ID 仍返回「事件已删除」（`enable` 的 `IsDeleted` 分支只剩 ID 路径可达）。
- 附带：`delete` 按名字重复调用不再幂等（按 ID 仍幂等）。
- 不是 bug（文档只约束 ID 路径），但同一个事件换个入参给两种说法，模型容易误判。建议名字路径找不到时再判一次"是否存在已删同名事件"，返回同一句「事件已删除」。

**N3 `truncateEventSummary` 不 trim**
- `server/internal/service/event_repo.go:339-345`：截断只按 rune 数切，不 `TrimSpace`。拼装路径外面包了 `strings.TrimSpace`，`event.update` 路径没有，LLM 带前导换行的 summary 会原样落库。一行 `strings.TrimSpace` 即可；不修也无功能问题。

另一个已知一次性空档（无需修）：`event.enable` 之后如果紧接着一条短消息，本轮 carry 的来源（上一轮 XML）里还没有这个事件，所以它那一轮不出现，下一轮 EventSource 才 full —— 内容仍在上一轮的工具结果/历史里，属可接受。

阶段 4 可以过。下一阶段开工前记着两条既有欠账：`event.get` 的 `MaxToolResult: 2000` 截断用例（阶段 8 验收）、`buildUserMessage` 的事件接线没有端到端测试（动这段接线时补）。
