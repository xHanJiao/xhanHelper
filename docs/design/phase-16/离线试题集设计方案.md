# 离线试题集设计方案

> 2026-06-15 · 基于 RAG 检索评测框架 Phase 1 细化
>
> 核心目标：构建一套**可重复、可版本管理、冻结不可修改**的检索评测数据集。

---

## 一、设计目标

| 目标 | 说明 |
|------|------|
| **数据驱动** | 试题源于真实用户 query，覆盖实际使用场景 |
| **可重复** | 锁死试题集后，任何检索策略改动都能回放对比 |
| **自包含** | 一个 SQLite 文件 = 一个完整数据集项目，可搬运、可 git 管理 |
| **不可篡改** | 导出数据冻死不变，标注累进式修改 |

---

## 二、数据集架构

### 2.1 项目概念

每次构建数据集都是一个**不可修改的项目**，做完冻结，下次新开一个：

```
dataset/projects/
├── 2026-06-15-retrieval-baseline/
│   └── eval.db                  # 自包含 SQLite
├── 2027-01-10-expanded-dataset/
│   └── eval.db
└── ...
```

每个项目一个 SQLite 文件，一个 `eval.db` 内包含该项目的全部数据。

### 2.2 模型设计

核心数据关系：

```
一次导出（数据快照，冻死）
    ├── 多次标注批次（累进，batch1 标 10 条 → batch2 扩 50 条）
    └── 多次评估（读标注结果，跑不同检索策略，随便折腾）
```

### 2.3 表结构

共 8 张表：

#### `eval_projects` — 项目注册

```sql
CREATE TABLE eval_projects (
    id          TEXT PRIMARY KEY,        -- 项目名，如 "2026-06-15-retrieval-baseline"
    name        TEXT NOT NULL,           -- 项目名称
    description TEXT,                    -- 描述说明
    status      TEXT NOT NULL DEFAULT 'draft',  -- draft | annotating | locked | archived
    created_at  TEXT NOT NULL DEFAULT (datetime('now')),
    locked_at   TEXT                          -- 冻结时间
);
```

> 状态流转：`draft` → `annotating` → `locked` → `archived`

#### `raw_queries` — 裸导出数据（只读，不存状态）

```sql
CREATE TABLE raw_queries (
    id               TEXT PRIMARY KEY,        -- UUID，与 messages.id 一致
    content          TEXT NOT NULL,           -- 原始用户消息内容
    source_msg_id    TEXT NOT NULL,           -- 来源 messages 表的 id
    source_conv_id   TEXT,                    -- 来源 conversation id
    created_at       TEXT                     -- 原始消息时间
);
```

- 数据来源：`messages` 表，过滤掉过短消息（≤5 字符，或 ≤10 字符且 ≤15 字节）
- **不存状态字段**：`selected_at`、`label_status`、`has_answer`、`difficulty` 等全部去掉
- 纯数据快照，导出即冻死

#### `eval_corpus` — 被检索的语料库（只读）

```sql
CREATE TABLE eval_corpus (
    id          TEXT PRIMARY KEY,        -- 对应来源表原始 ID
    content     TEXT NOT NULL,           -- 文本内容
    source_type TEXT NOT NULL,           -- 'note' | 'memory'
    source_id   TEXT NOT NULL,           -- 来源表原始 ID（notes.id 或 user_memories.id）
    topic       TEXT,                    -- 主题
    tags        TEXT,                    -- 标签
    created_at  TEXT                     -- 原始创建时间
);
```

- 数据来源：`notes` 表（status=0） + `user_memories` 表（全量）
- 不包含：documents（文档）、历史消息

#### `annotation_sessions` — 标注批次

```sql
CREATE TABLE annotation_sessions (
    id           TEXT PRIMARY KEY,        -- session 标识，如 "batch-1"
    project_id   TEXT NOT NULL,           -- 所属项目
    name         TEXT,                    -- 批次名称
    status       TEXT NOT NULL DEFAULT 'draft',   -- draft | prelabeled | reviewed | locked
    query_count  INTEGER NOT NULL,        -- 本批次标注的 query 数量
    created_at   TEXT NOT NULL DEFAULT (datetime('now'))
);
```

- 一项目多个 session，累进推进：batch-1 标 10 条 → batch-2 扩到 50 → batch-3 扩到 200
- 每个 session 独立追踪进度

#### `annotation_session_queries` — 批次 ↔ query 关联

```sql
CREATE TABLE annotation_session_queries (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id    TEXT NOT NULL,
    query_id      TEXT NOT NULL,         -- 对应 raw_queries.id
    label_status  TEXT NOT NULL DEFAULT 'selected',  -- selected | prelabeled | reviewed | finalized
    selected_at   TEXT NOT NULL DEFAULT (datetime('now')),
    UNIQUE(session_id, query_id)
);
```

- 一个新 session 选 query 时，跳过已有标注在 `ground_truth` 中的 query
- 每条 query 在此 session 的标注进度独立追踪

#### `eval_ground_truth` — 五档相关性标注（累进式）

```sql
CREATE TABLE eval_ground_truth (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    query_id      TEXT NOT NULL,         -- 对应 raw_queries.id
    corpus_id     TEXT NOT NULL,         -- 对应 eval_corpus.id
    relevance     INTEGER NOT NULL,      -- 0 ~ 4，五档相关性
    label_source  TEXT DEFAULT 'llm',    -- 'llm' | 'human' | 'corrected'
    labeled_at    TEXT NOT NULL DEFAULT (datetime('now')),
    notes         TEXT,                  -- 标注备注

    UNIQUE(query_id, corpus_id)
);
```

- 不分 session，标注结果累进式存储
- 修正时直接 `INSERT OR REPLACE`，最新覆盖
- batch-1 标 10 条后有 10×M 行，batch-2 追加后增长到 50×M 行

#### `eval_embedding_cache` — 向量缓存

```sql
CREATE TABLE eval_embedding_cache (
    source_type TEXT NOT NULL,           -- 'query' | 'corpus'
    source_id   TEXT NOT NULL,           -- raw_queries.id 或 eval_corpus.id
    model_name  TEXT NOT NULL,           -- 嵌入模型名，如 'doubao-embedding-vision-251215'
    embedding   TEXT NOT NULL,           -- JSON 文本 blob，如 "[0.12, -0.34, ...]"
    dimension   INTEGER NOT NULL,        -- 向量维度
    created_at  TEXT NOT NULL DEFAULT (datetime('now')),

    UNIQUE(source_type, source_id, model_name)
);
```

- B1 导出时：同步读取 MySQL `embeddings` 表中 `entity_type IN ('message','note','memory')` 的 full-content 向量，写入缓存
- 评测引擎运行时：先查缓存，命中直接用；未命中则调 API 计算后写入
- 支持多模型共存，换模型做对比时开新行
- B2 预筛时：从缓存读向量 → 本地 cosine → 取 top 20 候选

#### `eval_metadata` — 元信息

```sql
CREATE TABLE eval_metadata (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
```

- 建议记录：`version`（如 `v1.0`）、`annotator`（标注人）、`self_consistency_rate`（自洽率）、`annotation_date`（标注日期）、`corpus_source_count`、各批次统计等

## 三、五档相关性标注标准

评测用 NDCG（归一化折损累计增益）做排名质量评估，需要分档权重。

| 档位 | 分数 | 标签 | 含义 | 示例（query: 我上个月吃饭花了多少） |
|------|------|------|------|------|
| **0** | 0 | `irrelevant` | 完全无关 | 「减肥计划」「股票涨了」 |
| **1** | 1 | `tangential` | 同话题但无帮助 | 「餐饮行业趋势」「做菜教程」 |
| **2** | 2 | `partial` | 弱相关，有线索但答题不够 | 「外卖比堂食贵」「最近胃口不好」 |
| **3** | 3 | `relevant` | 直接相关，回答可用 | 「5月食品支出概览」 |
| **4** | 4 | `perfect` | 完美命中，最优答案 | 「5月餐饮月度明细：¥2,847」 |

### 标注规范（标注时顺手记录）

- **算「相关」**：结果直接回答了问题或提供了关键上下文
- **算「不相关」**：结果与问题无关或仅有微弱关联
- **边界案例**：标注备注里记录模糊题的判断依据

## 四、标注流程

### 4.1 整体流水线

```
MySQL 原始数据
    │
    ▼  [B1] 导出脚本：筛选 + 灌入 SQLite + 预灌嵌入向量
    │
raw_queries (~1496) + eval_corpus (~453) + embedding_cache 已灌
    │
    ▼  [B2] 开 annotation_session_1（--query-limit 10）
    │       LLM 精选 10 条 → 检索预筛（读取 cache 向量算 cosine，top 20）
    │       → LLM 逐条五档预标注 → 写入 ground_truth
    │
    ▼  [B2] 开 annotation_session_2（--query-limit 40）
    │       跳过 session_1 已标的 query，流程同上 → ground_truth 增长到 50×M
    │
    ▼  [B2] 开 annotation_session_3（--query-limit 150）→ ground_truth 增长到 200×M
    │
    ▼  [B3] 人工在标注页面复核修正（所有 session 合集）
    │
eval_ground_truth 人工确认版
    │
    ▼  [B4] 两周后抽 20% 复标 → 自洽率校验
    │
自洽率 ≥ 90% → locked ✅
自洽率 < 90% → 检查分歧原因，补充标注规范，重标
```

### 4.2 增量构建

不一次全量标注，渐进式推高数量：

```
10 条 → 验证流程 → 50 条 → 验证 → 100 条 → 200 条 → 500 条
```

每批一个 `annotation_session`，新 session 自动跳过已有 ground_truth 的 query。同一 session 重跑则标记其 query 为未处理，重新标注。

### 4.3 自洽率

自己隔一段时间重标同一批题，看两次结果一致的比例。目标 ≥ 90%。

### 4.4 单人标注说明

目前只有一个人标注（hx），用**自洽标注**替代多人 Kappa 校验：
- 第一轮：LLM 预标注后人工复核
- 第二轮：过两周随机抽 20% 复标，计算自洽率

## 五、MySQL 导出策略

### 5.1 queries 导出

数据源：`messages` 表。

过滤条件：只保留消息长度足够触发检索的 query。

导出 SQL（纯长度过滤，与 pipeline 一致）：

```sql
SELECT id, content, conversation_id, created_at
FROM messages
WHERE role = 'user'
  AND status = 1
ORDER BY created_at ASC;
```

在 Go 代码中独立实现过滤逻辑（不引用 pipeline 包）：

```go
func shouldSkip(content string) bool {
    charLen := utf8.RuneCountInString(content)
    byteLen := len(content)
    return charLen <= 5 || (charLen <= 10 && byteLen <= 15)
}
```

- 不限制时间范围，导出所有历史数据
- 不过滤 user_id（目前仅一个用户）

### 5.2 corpus 导出

数据源：`notes` + `user_memories` 表，全量导出，无需过滤。

```sql
-- notes
SELECT id, content, topic, tags, created_at
FROM notes
WHERE status = 0;

-- user_memories
SELECT id, memory_value AS content, topic, tags, created_at
FROM user_memories;
```

### 5.3 嵌入向量预灌

B1 导出时同步从 MySQL `embeddings` 表读取 full-content 向量，写入 `eval_embedding_cache`：

| 源表 | entity_type | source_type（cache 中） | source_id |
|------|------------|------------------------|-----------|
| messages（query） | `'message'` | `'query'` | `raw_queries.id` |
| notes（corpus） | `'note'` | `'corpus'` | `eval_corpus.id` |
| user_memories（corpus） | `'memory'` | `'corpus'` | `eval_corpus.id` |

- **只取 full-content 向量**（方案 A），不取 chunk 级别的向量
- 格式：JSON float64 数组 → 直接存进 SQLite TEXT 字段
- 模型名从 `embeddings.model` 字段读取

## 六、B2 预筛策略

### 6.1 方案

采用方案 A（full-content 向量 cosine）：

```
query id → eval_embedding_cache 读向量
corpus ids → eval_embedding_cache 读向量
→ 本地 cosine 相似度计算 → 排序 → 取 top 20 → 送给 LLM 打 0~4 分
```

- 预筛不是最终答案，只为 LLM 缩小候选范围
- LLM 只对 20 条候选评分，减少 95%+ 调用量
- 漏掉的边缘 case 由 B3 人工复核补上

### 6.2 后续可升级为方案 B

方案 B 复制线上两阶段搜索（chunk 搜 + full-content 搜 + parent 聚合），对检索行为模拟更准确，但实现复杂度高。方案 A 跑通后视效果决定是否升级。

---

## 七、Embedding 缓存策略

- B1 导出时预灌 full-content 向量，后续零嵌入成本
- 评测引擎运行时查 `eval_embedding_cache`
  - 有缓存（匹配 `source_type + source_id + model_name`）→ 直接用
  - 无缓存 → 调 embedding API 计算，结果写回缓存
- 换 embedding 模型时，新模型的向量需调 API 计算一次（后续缓存）
- 向量以 JSON 文本 blob 存 SQLite

## 八、开发批次

分 4 批交付，每批独立 review。

### B1 — 基础设施

| 项 | 内容 |
|----|------|
| 目标 | SQLite schema 建表 + Go eval 模块骨架 + 导数据脚本 + 预灌 embedding |
| 后端 | `server/internal/eval/` 模块：DB 初始化、表迁移 |
| 脚本 | MySQL → SQLite 导出（raw_queries + corpus + embedding_cache） |
| 产出 | `eval.db` 含 raw_queries、corpus、embedding_cache 三张表有数据 |
| Review | schema 设计、代码结构 |

### B2 — LLM 数据加工

| 项 | 内容 |
|----|------|
| 目标 | LLM 精选 query + 检索预筛 + 五档预标注 |
| 内容 1 | 开 annotation_session → LLM 从 raw_queries 中挑 N 条（跳过已标的） |
| 内容 2 | embedding_cache 读向量 → 本地 cosine → top 20 候选 |
| 内容 3 | LLM 逐条对 top 20 候选打 0~4 分 → 写入 ground_truth |
| 产出 | ground_truth 累进增长 |
| Review | prompt 设计、预标注质量抽样 |
| CLI | `eval-label --project --session --query-limit N --candidate-limit 20` |

### B3 — 标注前端

| 项 | 内容 |
|----|------|
| 目标 | 前端 Admin 标注页面，个人工复核修正标注 |
| 后端 | 标注 API：query 列表、检索结果展示、标注保存 |
| 前端 | Admin 标注页：显示 query → 展示相关 corpus → 五档切换 + 备注 + 保存 |
| 产出 | 你在浏览器逐条复核，产出人工确认版 ground_truth |
| Review | UI 交互、接口逻辑 |

### B4 — 质检锁定

| 项 | 内容 |
|----|------|
| 目标 | 自洽率校验 → 冻结项目 |
| 内容 | 抽 20% query 复标 → 计算自洽率 → 写入 metadata → 项目状态切 locked |
| 产出 | `self_consistency_rate ≥ 90%` 且 `status = locked` |
| Review | 自洽率是否达标 |

- `dataset/projects/` 目录纳入 git 管理
- `.db` 文件通过 `.gitignore` 例外规则放行（`!dataset/projects/**/*.db`）

## 十、与评测引擎的关系

```
┌─────────────────────┐        ┌─────────────────────┐
│  dataset/projects/   │        │  server/internal/eval/│
│  (数据，冻结)          │  ←读取  │  (评测引擎，可运行)      │
│                     │        │                     │
│  eval.db            │        │  evaluator.go       │
│  ├── raw_queries    │        │  ├── 加载 query      │
│  ├── corpus         │        │  ├── 调用 retriever  │
│  ├── ground_truth   │        │  ├── 对比 ground_truth│
│  └── cache          │        │  └── 输出指标        │
└─────────────────────┘        └─────────────────────┘
```

数据集项目只存**数据**（queries、corpus、标注、缓存），不包含检索逻辑。评测引擎是独立模块，读取冻死的数据集跑检索，计算 Recall@K、Precision@K、NDCG@K、MRR 等指标。

## 十一、总结

离线试题集构建四步走：

1. **导数据**：MySQL → SQLite（过滤短消息 + 预灌 full-content embedding）
2. **LLM 预加工**：开 annotation_session → 精选 query → 本地 cosine 预筛 → 五档预标注
3. **人工复核**：前端页面逐条确认
4. **质检冻结**：自洽率 ≥ 90%，项目上锁

核心设计原则：**导出冻死 + 标注累进 + 评估灵活重跑**。做完后的数据集可重复用于对比任意检索策略，每次改动都能回答：「这是优化还是回退？」
