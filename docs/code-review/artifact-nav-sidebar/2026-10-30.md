## P1 · 侧栏列没有底色，直接压在照片底图上

**位置**：`ArtifactDetailView.swift:23-43`（根 `HStack` 只做了 `.ignoresSafeArea()`）

**问题**：右栏没有任何卡片 / 材质底（`ContentView` 里 `RightSidebarView` 直接坐 `AppBackdrop`，见 AGENTS「右栏无描边直接坐底图」）。改之前整幅 tab 由 `HTMLArtifactView` 的 `Color.white` 铺满；现在白的只有页面列，**新增的 220 侧栏列是透明的**，标题 / 次信息 / hover 底色 / 当前项 `appAccent.opacity(0.10)` 全落在模糊照片（浅色 40% 白霜）上。

**后果**：文档侧栏有 `DocumentFullView` 的 `.regularMaterial` 纸底，灵阅侧栏没有 → 同一个「侧栏 + 正文」在两个详情页观感不一致，且照片偏暗的角落会把 11pt 次信息行吞掉。

**修（最小）**：根 `HStack` 补一层底，取与页面同族的白（`Color.white`）或纸底（`.regularMaterial`，与文档对齐）。因为页面本身已经是 `Color.white`，铺整块白最省事、也不会跟 WKWebView 白底错色。材质类观感以真机为准（离屏渲染不可信）。

## P2 · 设计文档 AN-8 / §六 与实现相反：拖宽**会**自动展开

**位置**：`ArtifactDetailView.swift:55-57`；`docs/design/artifact-nav-sidebar/design.md` AN-8、§六

**问题**：实现是 `!navCollapsed && (width <= 0 || width >= floor)`。硬地板收起**不写回** `@AppStorage`，所以窄 → 收、再拖宽 → `navCollapsed` 仍是 `false` → **自动展开**。文档却写「拖宽后不自动展开」，验证清单也按这个写（「右栏拖窄到 < 600 → 自动收成窄条；拖宽不自动展开」）。

**后果**：按文档验收会把这当成 bug；实现本身与母本 `DocumentFullView.tocExpanded` 一致（手动收起才粘住），代码不用改。

**修**：改文档措辞为「手动收起粘住；被硬地板强制收起时不写回，拖宽即恢复展开」，同步 §六 那条验收项。

**位置**：`ArtifactDetailView.swift:42`；`ChatView.swift:65`

**修（若真机确认有问题）**：只让页面列忽略安全区（`page.ignoresSafeArea()`），侧栏列留在安全区内。

## N1（P2）· 从聊天卡片首次打开时，当前项**不会**被滚到视口（AN-4 / AN-9 那条路径）

**位置**：`ArtifactDetailView.swift:36-41`（`.task` 补 `load()`）+ `ArtifactDetailView.swift` 里 `ArtifactNavList` 的 `ScrollView.onAppear`

**问题**：定位靠 `ScrollView` 的 `.onAppear`；同一次 appear 里，列表还是空的（`items` 要等 `.task` 里的 `await load()` 回来）。`onAppear` 时 `currentInList == false` → 直接 return，之后再没有任何时机补 `scrollTo`。

**后果**：从聊天卡片打开一篇**不在第一页、且在列表靠后**的产物时，侧栏列表加载完后停在顶部，当前行既不高亮在视野里、也没有钉行兜底（它**在** `items` 里，所以不触发 AN-6 的钉行）。用户只看到列表开头，跟「点哪篇停哪篇」的预期相反。从灵阅面板点开的路径不受影响（`items` 早已加载，`onAppear` 时有数据）—— 所以这个坑只在 AN-4 专门补的那条路径上出现，真机自测很容易漏。

**修（最小）**：给列表加一次「数据到位后再定位」：`.onChange(of: viewModel.items.count) { _, _ in 若 !didAutoScroll { 包 withAnimation 滚到 currentID } }`（或用 `task(id: items.count)`），`didAutoScroll` 只跑一次/每次进入重置。别改成无条件每次 onChange 都滚——面板刷新/续拉会抢用户的手动滚动。

## N2（P2）· `artifactVM` 为 nil 时静默降级，且降级路径还丢了全铺

**位置**：`ArtifactOpenCoordinator.swift:20-23`、`88-95`

**问题一**：`artifactVM` 是 `ContentView` 注入的必需依赖（`@StateObject`，生命周期与右栏一致）。为 nil 只可能是接线 bug，但这里默默退化成「没有侧栏」的页面 —— 与项目约定「必需依赖为 nil 意味接线 bug，让它炸在明处；可选依赖才 nil 检查」冲突，而且用户看到的是一个**看起来正常、功能缺一半**的页面，没人会报。

**问题二**：这条降级路径直接返回 `HTMLArtifactView` / `ArtifactLoadingView`，而这两个视图的 `.ignoresSafeArea()` 已经删掉（改由 `ArtifactDetailView` 负责）→ 一旦真走到降级，页面**还少一块全铺**，两个问题叠在一起更难定位。

**修**：至少 `LogBuffer.shared.error("ArtifactOpenCoordinator: artifactVM 未注入")`；按项目规矩则应去掉可选（`guard let artifactVM else { fatalError(...) }` 之类），或改成在 `configure` 时注入并断言。若确实要保留优雅降级，就顺手给降级路径补 `.ignoresSafeArea()`，别只降级一半。

## 第二轮确认「没问题」的点

- tab 关闭：`artifact:` 前缀的 tab 在 `BrowserToolProvider.tabs` 里没有 session，`closeTab` 直接落到 `rightSidebar?.closeTab`，能正常关（每点一篇就多一个 tab 的取舍不会连带关不掉）。
- `isArtifactTab(_:)` 的既有判断（浏览器工具不抢产物 tab 的 active）不受侧栏影响。
- iOS 那条 `.sheet` 整段在 `#if os(iOS)` 里，`ChatView` 补的 `.ignoresSafeArea()` 不会落到 macOS 上。
- `updateTabContent` 前后都是 `ArtifactDetailView`（同类型），`@State width` / `@AppStorage` 不会被重置；`reloadIfOpen` 不会让侧栏收起态或 hover 丢了。
- 删除产物 / 批量删除 → `removeFromList` → `closeTabIfOpen`，共享 VM 下侧栏与面板同时减一条，不会留下已删项。
- 并发：两个 tab 同时首次出现时，第二个的 `.task` 会被 `isLoading` 挡住，不会双拉；`loadMore` 的 `isLoadingMore` / `isLoading` 双闸也在。

### T3（P3·新增暴露面）· `.task` 被取消时 `load()` 会把共享列表打成错误态

`ArtifactDetailView.swift:37-42` 新加的 `.task` 在切 tab 时会被 SwiftUI 取消；取消会一路抛到 `ArtifactViewModel.load()` 的 `catch` 里 —— 记一条 `LogBuffer.error` 并把 `errorMessage` 设成取消信息。于是**共享 VM 进入错误态**：若此时 `items` 仍为空（首次打开即切走），灵阅面板会显示「加载失败 + 重试」，其实只是用户换了 tab。

**触发面**：这次新增的 `.task` 是唯一入口（面板那条 `.task` 生命周期跟面板绑定），窄但真实。

**修（一行级）**：`load()` 的 `catch` 里先判 `error is CancellationError`（或 `URLError.cancelled`）→ 复位 `isLoading` 后直接 `return`，不当失败。顺带 `loadMore()` 同理。

### T4（P3·待真机）· 深色下「深玻璃侧栏 + 固定纯白页面」并排

页面固定 `Color.white`（既有），侧栏从透明改成 `.regularMaterial`。浅色下两者和谐；深色下是深玻璃紧贴一块纯白 —— 比之前（侧栏透明融进底图）更"跳"，但不影响可读性。真机看一眼，觉得跳就把页面列在深色下也压一层暗（那属于 `HTMLArtifactView` 的既有取舍，别在这次改）。

## 仍挂着（前两轮已记，未处理，判断为可接受）
