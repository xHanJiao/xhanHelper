# 多模态图片输入 — 技术方案

> 状态：**P0 + P1 + P3-1 + P3-2 已实现**（2026-09-16）；P1 的验收已过（选图发送/历史可见/15 天与 3 天清理任务日志已实测）。
> P0 = 模型切到 V4.1-Flash；P1 = 用户显式给图（选图 → 压缩 → 上传 → 模型看图 → 历史可见 + 自动清理）；
> P3-1 = `⌘V` 粘贴图片进待发托盘；P3-2 = 右侧栏「图片」管理页（预览 / 删除）。
> 未做：P2（agent 发现的图 + L3 审批预览，已决定暂不实现，见 §十一）。
> 范围：server（Go）+ macOS 客户端（SwiftUI）。iOS 已弃用，仅保持可编译、不做新功能。
> 关联：与 `document-images.md`（文档图床，已定稿未实现）共用存储层，本文不另建一套

## 一、一句话

让 xhanHelper 能"看图"：用户随手选一张图，agent 也能在探索本地或网页时把图带回来，
模型直接理解图片内容，同时这些图有一处地方可以查看和管理。

---

## 二、要做的体验

### 路径 A：用户显式给图（主路径）
1. 点输入框的回形针，从本地选一张或多张图（也可直接把文件拖进来）
2. 输入框下方出现缩略图，可删可加，可配文字也可**只发图**
3. 发送 → 模型看图回答
4. 消息气泡里能看到自己发的图，点开可放大

> **粘贴已在 P3-1 做掉**（`⌘V`）。原判断"`TextEditor` 会吞掉 `⌘V`、可能要换自绘 `NSTextView`"只对了一半：
> `TextEditor` 确实自己处理粘贴，但不必换编辑器 —— 在已有的 `NSEvent keyDown` 监听里拦 Cmd+V 即可
> （见 §十一 P3-1）。截图现在可以直接 ⌘V 进来。

### 路径 B：agent 发现的图（本地 + 网页）
让它读一个含设计稿/截图的目录，或浏览一个小红书图文页。工具把图片抓回来后**不直接喂给模型**，
而是先弹一个带缩略图的确认条——**你看过、点允许，模型才看图**；拒绝则 agent 只拿到文字，继续干活。

这样做的直接目的就是省钱：图片 token 上限 1024/张，agent 一次"随手看一眼目录"可能带出十几张，
每次都自动送模型是纯浪费；由你当场判断"这张值不值得看"才是对的。

### 附加：图片管理
所有"入过模型"的图有一处列表可看：缩略图、大小、来源、时间，可删除。

## 三、现状与约束

### 3.1 DeepSeek 侧能力（已核对官方文档）

| 项 | 事实 | 对我们的影响 |
|---|---|---|
| 模型 | **DeepSeek-V4.1-Flash**（2026-09-10 发布）**原生多模态**，1M 上下文 / 384K 输出 | 主模型切到它即可，**不需要单独的视觉模型**，也不需要 `vision_enabled` 之类的开关 |
| 旧模型名 | `deepseek-v4-flash` / `deepseek-v4-flash-vision-exp` 已退役；名字仍被接受但请求路由到 V4.1-Flash | 配置里的旧名早已在跑 V4.1-Flash，只是名字没更新 |
| Pro 模型 | **V4-Pro 正在下线**：2026-09-14 起 `deepseek-v4-pro` 请求全部路由到 V4.1-Flash、按其价格计费，直到 V4.1-Pro 发布 | "深"这一档暂时没有独立模型；带图在深档同样可用，不必为图片做降级 |
| 传图方式 | ① base64 data URL ② 外部公开 URL ③ Files API `file_id` | 选 ③，见 D1 |
| 消息位置 | Chat Completions 下**图片只能出现在 `user` 消息**；system/assistant 带图 400 | 工具（`tool`）消息不能带图，见 D6 |
| 单图 token | 上限 **1024** token，按尺寸自动缩放（总像素约 1300×1300） | 成本可估算，见第十节 |
| 限制 | 单请求 ≤600 图；请求体 ≤48 MiB；base64/URL 单图 ≤32 MiB；file_id 单图 ≤64 MiB | 我们远够用 |
| detail | `low` 降采样到 512×512（更省）/ `original` 保原图。**仅对 `image_url`（base64/URL）生效，`file_id` 传图时被忽略** | 我们走 file_id，因此用不到这个杠杆（见第十节） |
| Files API | `POST /files`（multipart，`purpose=user_data`）；可选有效期 1 小时～30 天，**不传 = 永久**；单文件 ≤64 MiB；账户 25 GiB / 10000 文件 | 默认永久有效 |
| Files API 归属 | **文件归属于 API key**，且没有下载接口、无删除接口 | 决定了上传必须在服务端；且**必须自己留副本**，否则历史消息再也显示不出图 |

### 3.2 代码现状

- 全链路 `content` 都是**纯字符串**（HTTP 请求 → 编排器 → LLM 适配层 → DB）。要支持图片必须引入 content block 数组。
- 服务端目前**没有**任何上传、静态资源、multipart 代码。
- 客户端目前**没有**任何附件 UI；macOS 输入框是 SwiftUI `TextEditor`。
- 图片**不能存进 `messages.content`**（TEXT 字段），而且工具结果有截断逻辑会把 base64 腰斩——所以图片必须走"引用"，不能内联。

上传 `POST /api/images/upload`、按文件名寻址。设计定稿但**尚未实现**。

图片输入和文档配图需要的存储是同一件事，**不另建一套**。本文在它基础上补：
DB 记录、DeepSeek Files API 上传、消息引用关系、两级自动清理、管理页。

## 四、存储与可见性：同一套存储，两种鉴权

这是本文与 `document-images.md` 原设计唯一需要调和的地方。原设计是"UUID 文件名即能力凭证、完全公开"，
理由是 `<img>` 标签带不了请求头。但两类图的要求不同：

| | 文档配图 | 聊天图片输入 |
|---|---|---|
| 要不要对外分享 | 要（分享链接给别人看，对方没登录） | **不要** |
| 读取 | 可以公开 | 必须鉴权 |
| 原设计的公开 URL | 刚好合适 | 等于把聊天内容挂在公网上 |

所以共用一套存储，加一个 `visibility` 字段分流：

| 项 | 设计 |
|---|---|
| 落盘 | 同一目录 `data/images/<uuid>.<ext>` |
| `visibility` | `private`（默认：聊天图、本地图、网页图）/ `public`（文档配图） |
| 公开读 | `GET /images/:file`——**仅当该记录是 public**；查不到记录一律 404 |
| 私有读 | `GET /api/images/:id/file`——鉴权 + owner 校验 |
| 写 | 一律鉴权 + 记 owner，**没有任何匿名入口** |

**"保证图床不会被别人所用"** 的落实点：
- 上传必须登录，每张图记 owner；删除/读取都校验 owner
- UUID 不可枚举；非 public 一律 404，不做目录列举
- 魔数校验（只收 png/jpeg/webp/gif，**拒 svg**，防脚本注入），单图大小上限
- 每用户存储配额（见第十节清理）
- 公开路由只服务显式标记 public 的资源

**代价（已确认接受）**：私有图不能用 SwiftUI `AsyncImage`（它加不了请求头），
客户端要写一个约 20 行的鉴权图片视图（`APIClient` 拉字节 → `Image(nsImage:)`）。

> 公开路由本期一并注册（10 行）。这样 `document-images.md` 实现时零改动，
> 只需在其 v1 边界里去掉"❌ 图片 DB 记录与孤儿清理"——清理能力由本文提供。

## 五、总体设计

```
                             ┌──────────────────────────────────────────┐
                             │             服务端 (Go)                   │
                             │                                          │
  用户选图                    │  POST /api/images/upload                 │
   ┌──────────┐  multipart   │    ├─ 魔数校验 / sha256 去重              │
   │ macOS    │─────────────▶│    ├─ 落盘 data/images/<uuid>.<ext>       │
   │ 客户端    │              │    └─ 写 ImageAsset(visibility=private)   │
   └──────────┘              │       （不在这里传 DeepSeek：外网往返     │
        │  ① 先上传拿 image_id │        0.5-1.4s 会卡住交互式发送）        │
        │                     │                                          │
        │  ② POST /api/chat   │  Orchestrator                            │
        └────────────────────▶│    ├─ 组装 user 消息 content blocks       │
          attachments:[id…]   │    │   [{text}, {image: file_id}]         │
                              │    ├─ 首次用时懒补 file_id 并回填落库      │
                              │    └─ 重放历史时按窗口回填                 │
                              │                                          │
  agent 发现图（本地/网页）    │                                          │
    ├─ 抓字节 → 强制 L3 审批 ─▶│  GET  /images/:file      （公开，仅 public）│
    │   └─ 通过 → 上传拿 id ──▶│  GET  /api/images/:id/file （私有，鉴权）  │
    └─ 拒绝 → 只回文字 ───────▶│  GET/DELETE /api/images  （管理，鉴权）    │
                             └──────────────────────────────────────────┘
```

**一次带图对话的数据流**

```
客户端                        服务端                         DeepSeek
  │  POST /api/images/upload   │                               │
  ├───────────────────────────▶│  落盘 + Files API 上传         │
  │◀── {image_id, url} ────────┤──────────────────────────────▶│
  │                            │                               │
  │  POST /api/chat            │  组装 content blocks           │
  │  {message, attachments:[…]}├──────────────────────────────▶│ 看图
  │◀══ SSE 流式回复 ════════════┤◀──────────────────────────────┤
```

**agent 发现图的审批门**（与上面并发，不占主链路）

```
本地工具/浏览器抓到图片字节
   │
   ├─ 工具本身不碰网络（本地工具的执行上下文里没有服务器地址/token，也不该有）
   ├─ 工具把字节作为"附件载荷"返回
   │
   └─ 客户端工具执行层：
        ├─ 1. 强制弹确认条 + 缩略图预览（信任模式也跳不过，队首 180s 超时视为拒绝）
        ├─ 2. 拒绝 → 结果照常回传，只是不带图，agent 继续
        └─ 3. 允许 → 上传拿 image_id → 工具结果里带 __images:[…]
                        └─ 服务端在 tool 消息之后追加合成 user 消息（带图块）
```

关键点：**先审批、后上传**（拒绝时零浪费）；**工具保持纯粹，网络收口在工具执行层**。

## 六、关键决策

| # | 问题 | 决策 | 理由 | 备选与代价 |
|---|------|------|------|-----------|
| D0 | 用哪个模型 | **主模型与后台模型升级到 `deepseek-flash`（V4.1-Flash）；`strong_model` 不动** | 原生多模态、性能超过 V4-Pro、价格更低；旧名已退役 | 不升级：拿不到视觉能力。改 strong_model：目前无对应新模型，等 V4.1-Pro |
| D1 | 图片怎么送给模型 | **Files API `file_id`**（服务端中转） | 同一张图跨轮复用只传一个 id，请求体不膨胀，历史重放前缀稳定、缓存可命中 | base64 内联：每次重放重传数 MB。外部 URL：dev 环境 localhost 模型抓不到 |
| D2 | 上传放哪一侧 | **服务端** | 文档明确 file_id 归属 API key，而 LLM 调用用的是服务端那把全局 key；客户端直连会导致 file_id 引用不到 | 客户端直连：需把 key 下发到客户端，且必须与服务端同 key，得不偿失 |
| D3 | 图片副本存哪 | **磁盘 `data/images/`**，复用文档图床 | 已有定稿设计，别造第二套；Files API 无下载接口，不留副本历史消息就显示不出图 | DB BLOB：DB 膨胀，SQLite 下读写更重 |
| D4 | 公开还是鉴权 | **同一套存储 + `visibility` 分流**：聊天图私有鉴权，文档图公开 | 聊天内容不愿泄露到公网；文档图要能分享给未登录的人 | 全部公开：聊天图变公网可访问（UUID 虽不可猜，但仍是泄露面） |
| D5 | 历史消息里的图怎么重放 | **只重放最近 N 轮**（默认 10，可配） | 图片 token 不复用文本缓存，全量重放每轮都烧钱；最近的图才和当前对话相关 | 全部重放：长会话成本失控 |
| D6 | agent 找到的图怎么给模型 | **在工具结果之后追加一条合成的 user 消息带图** | 官方规定图片只能在 user 消息，`tool` 消息带图必 400 | 塞进工具结果：必然 400 |
| D7 | agent 找到的图要不要自动送模型 | **不自动，强制 L3 审批 + 缩略图预览，不可跳过** | 1024 token/张，agent"顺手扫一眼目录"可能带出十几张，全部自动送纯浪费；让用户当场判断 | 自动送：沉默烧钱。仅靠 prompt 约束：不可靠 |
| D8 | 网页图要不要单独走 URL | **不走，与本地图同一条路径：先落地再送模型** | 要预览就必须先把字节抓到本地；既然抓了，就统一存下来，顺带解决"外链失效/超大小"一整类分支 | 直传 URL：零存储，但无法预览、无法审批、外链会失效 |
| D9 | 磁盘总会满，怎么办 | **两级按时清理**：被引用过 15 天、孤儿 3 天 | 云盘有限；复用已有 `CronRunner` 定时循环范式，不新建调度器 | 一把按创建时间清：会直接清掉仍在用的历史图 |

## 七、三条路径的详细设计

### 7.1 路径 A：用户选图

**输入框**
- 回形针按钮 → SwiftUI 原生 `.fileImporter(allowsMultipleSelection: true)`；`⌘V` 粘贴（截图/Finder 里的图片文件，见 §十一 P3-1）；拖拽入框未做
- 草稿区缩略图 tray：可单个删除、可继续追加
- 允许"只发图不写字"（服务端放宽 `message == ""` 校验，改为"文字与附件至少要有一个"）

**消息与历史**
- 消息新增一列 `image_ids`（JSON 数组，抄现成的 `memory_ids` 范式）。**不加关联表**：重放时消息本就在手，解析内存 JSON 零额外查询
- 消息气泡上方显示缩略图条，点击看大图
- 客户端消息模型要新增 `attachments` 字段，**并补进加载时的字段拷贝逻辑**——现有实现只拷 6 个字段，新增字段不补会被静默丢弃

### 7.2 路径 B：agent 发现的图（本地 / 网页，同一条路）

- **抓取**：本地文件读图（当前是把 base64 塞进结果，改为返回附件载荷）；网页图复用浏览器已有的下载能力（真实 UA / Referer / Cookie），内存拿到字节
- **不落盘、不上传**，先把字节交给工具执行层
- **强制审批**：复用现有 L3 确认机制（`ToolConfirmation` 加一个 `imagePreviews` 字段，与现有 `diffText` 完全同构），确认条加缩略图分支
  - `force = true` → **信任模式也跳不过**
  - 180 秒无操作（队首计时）= 拒绝
  - 确认文案要写清代价：「识别 N 张图片？约消耗 N×1024 token」
- **拒绝**：结果照常回传（不带图），agent 继续，不中断
- **允许**：上传 → 工具结果带 `__images` → 服务端在 tool 消息后追加合成 user 消息（D6）

### 7.3 给模型的引导

在工具结果约定里声明图片可观察；System Prompt 补一句"工具带回的图片你可以直接看，
但你会先问用户是否值得看"。

## 八、图片管理

**入口**：macOS 右侧浏览面板新增「图片」格子（与账单/记忆/笔记/文档/主题同级）。加了这一格后
入口网格从 4×2 改成 **3×3**（`BrowsePanelView.adaptiveColumns` 宽态 3 列；窄态仍 2 列）。

**列表**：缩略图网格 + 分页加载（50/页，滚到末位自动拉下一页），每项显示来源（聊天/文档/本地/网页）
与体积，`referenced` 的额外挂「使用中」角标；时间/mime/是否已传 DeepSeek 放在悬停提示里。

**详情**：点缩略图开大图浮层（复用 `LightboxCenter` + `AttachmentPreviewView`，不做单独详情页）。
大图走 `AttachmentImageLoader` 按需拉，只有点开过的图才进内存。

**删除**：格子右上角「X」。**只有"删了会裂图"的才弹确认**（`referenced == true` 或 `source != chat`），
聊天里从没用过的孤儿图直接删。DeepSeek Files API **没有删除接口**，删不了，如实说明`has_file_id`。
被删除的图仍出现在历史消息里时显示占位（不做"反向查找哪些消息用了它"，YAGNI）——为此
删除成功后会调 `AttachmentImageLoader.forget(id:)` 清共享缓存，否则消息里还会拿内存里的旧图继续显示。

**缩略图不复用 `AttachmentImageLoader`**：那边存全尺寸解码图、会话内不回收（它服务的是消息里几张图和
点开的大图），一页 50 张 2048px 解码就是几百 MB。图片库单独按 id 拉字节 → `ImageCompressor.thumbnail(_:maxPixel:)`
（复用 `shrink` 的同一套 ImageIO 参数，含 EXIF 转正）降到 256px 再存，条数上限 300 按插入序淘汰。

服务端零改动：`GET /api/images?limit=&offset=`（`image.go:126`）、`DELETE /api/images/:id`（`:160`）已够用。

## 九、自动清理

复用 `CronRunner` 里已有的 ticker 循环范式（会话自动归档就是这么做的），加一个图片清理循环，
不新建调度器。

```
被引用过的图：last_used_at 超过 15 天 → 删
孤儿图：      created_at  超过 3 天  → 删
```

- `last_used_at` 在"图被挂到某条消息"时刷新一次；从未被引用的图保持上传时间
- 先删文件、再删记录；失败只记日志，不打断调度

**要接受的后果**：15 天按"挂到消息的时间"算，所以**历史消息里的图 15 天后会变成占位符**
（文字仍在、对话可读）。这就是"云盘有限"的代价，换来的是磁盘不会无限增长。

## 十、成本

- 每张图最多 **1024 token**，按尺寸缩放后计费，**与文本 token 同价**（DeepSeek 不单独对图片定价）
- 一次请求最多 600 图，实际远用不到
- 成本杠杆有两个：
  - **审批门**（D7）——最有效，从源头不送不该看的图
  - 历史重放窗口 `image_replay_rounds`（默认 10 轮）
- **`detail: low` 这个杠杆用不了**：官方文档写明它只对 `image_url`（base64 / 外链）生效，
  而 `file_id` 传图时被忽略。我们走 file_id（D1），所以图片一律按原图缩放计费。
  （若哪天实测成本偏高，可对"只要粗看"的图改用 base64 + `detail: low`——那是另一条路径，先不做。）
- 计费链路本身不用动（图片 token 自动进 `prompt_tokens`）。**价目表在 Admin 网页补一行 V4.1-Flash 即可，零代码**——
  界面本来就带"以下模型无有效价格，按 0 计"的告警，改完刷新即可看到数字。
  V4.1-Flash 新价（每 1M token，off-peak / peak）：缓存命中 $0.003/$0.006、
  未命中 $0.15/$0.30、输出 $0.60/$1.20——比旧档便宜约三分之一。

### 附：缩略图溢出折叠（P1 验收后补）

图多了托盘会一直往右排，把输入框顶出窗口（`.frame(maxWidth:)` 只提议宽度、
不裁剪，固定尺寸子视图直接画到窗口外）。最窄情况：窗口最小 380、中栏最小 340 →
可用宽约 240pt，两张图加「+」就满。

- 折叠态：按实测可用宽算一行能放几张，放不下的收成一格「+N」
- **消息图片条另外固定最多露 3 张**（`maxCollapsedThumbs: 3`）：宽窗口下 6-7 张一眼看过去太占地方，
  也不希望张数随窗口宽度变。3 是上限不是承诺 —— 窄到让不出「+N」那格时降到 2 或 1，排布仍不溢出。
  草稿托盘不设上限（它是编辑区，要能一眼点到某张去删）
- 展开态：`LazyVGrid` 自适应换行，**消息图片条不封顶**（`maxExpandedRows: nil` —— 上限就 20 张、
  展开就全露出来；封 3 行会留个内部滚动条，翻长图很别扭），**草稿托盘封顶 3 行**（超出内部垂直滚，
  它是编辑区，20 张 × 56pt 在中栏能撑到 6 行 ≈ 384pt，把输入框顶掉大半），「+N」格变「收起」格。
  **一行装得下时不走网格、走和折叠行同一个 HStack**：LazyVGrid 会吃满父级提议宽度、列从前缘起排，
  多出的空档留在网格内部尾部 —— 外层 `frame(alignment: .trailing)` 就成了空操作，展开后整排跑到
  左边（它自带的 `alignment` 只管"格子在列内"，不管"列整体靠哪边"）。实测症状：7 张图展开后
  贴左、与右下角时间戳和正文不在同一侧。多行时末行仍是网格的前缘起排（常规网格表现）
- 抽公共组件 `CollapsibleThumbRow`，草稿托盘（56pt，靠左，行尾挂「+」「清空」两格）与
  消息图片条（88pt，靠右，无行尾）共用
- 排布算式抽成纯逻辑 `ThumbRowLayout`（无 SwiftUI 依赖），由 `swift test` 覆盖：
  折叠态不溢出、展开列数不溢出、折叠态不藏起本放得下的图、刚好放得下时不出现「+N」、
  钉住的高度与行数一致。这层曾漏减行尾间距，窄窗下溢出 8pt —— 回归见
  `testTrayMaxPerRowAccountsForTrailingSpacing`
- **可用宽度只能从 `GeometryReader` 拿**：它报回的是父级提议尺寸，与内容无关。
  反过来拿自身 frame 的宽度会被内容污染 —— HStack 里全是固定尺寸格子，内容比提议宽时
  报回的是内容理想宽，于是"图越多量到的越宽、越不折叠"，还会把这个宽度泄漏给
  `InputBar.barWidth`（它挂在 `.frame(maxWidth:)` 之前，同样不钳制）把编辑器一起撑变形。
  实测症状：18 张图时量到 ≈1152pt，托盘不折叠且输入框整体异常
- **高度必须显式钉住**：`GeometryReader` 纵向也贪婪，不钉会吸掉整个剩余空间
- 首帧还没拿到几何宽度时只渲染同高占位，绝不按"全部铺开"画一帧
- 「+」与上传进度圈共用同一格（上传中圈替代加号），格子尺寸不变，展开成网格时也不会错位
- 张数 ≥ 2 时行尾多一个「清空」格（一键清空全部待发图），不弹二次确认 —— 草稿而已，
  重选即恢复。只放折叠行、不只放展开态：3-8 张图时不会溢出、也就没有展开入口，
  那样"清空"就够不着了
- 张数上限 20（`Layout.maxDraftImages`），超出给提示。服务端上限远高于此（600 张/请求），
  这里只挡"全选整个文件夹"这类误操作
- 大图预览**不做翻页**：折叠一旦能展开，所有图都够得着，翻页器就不是必需的了

### 附：选图后压缩 / 重编码（P1 补充）

上传前在客户端缩到长边 2048 再重编码：`Shared/Services/ImageCompressor.swift`，
唯一接入点 `ChatView.handlePickedFiles`。

- **不是为了省 token**：模型侧单图上限 1024 token、自动缩到约 1300×1300（见 3.1），
  2048 已把模型能看到的都留下。省的是磁盘、上传/下载耗时、列表解码占的内存 ——
  十几兆照片解码后约 48MB/张，十张就几百兆，`NSCache` 会被压到回收
- 实测（现有测试图）：11207KB 6240×4160 → **393KB / 2048×1365**（124ms）；
  15338KB → 957KB；733KB PNG(带 alpha) 2805×3041 → 431KB 保 PNG；200×200 15KB → 跳过
- 规则：JPEG q0.85；**有 alpha 保 PNG**（判据以源属性 `kCGImagePropertyHasAlpha` 为准，缺失时
  只对 PNG 保守保留 —— HEIC 解码出来是 premultipliedLast，按像素格式判会误走 PNG、压完更大、
  再被"更大就留原图"兜住，等于没换格式）；长边 ≤2048 且 ≤2MB 的 JPEG/PNG 直接跳过（不叠代损）；
  **GIF 不碰**（重编码只剩第一帧）；压完更大就保留原图，**除非必须换格式**
- **顺带修好 HEIC**：服务端只认 png/jpg/gif/webp，iPhone 照片原本会被 400 拒。实测
  HEIC 1259KB → JPEG 341KB
- 压缩放后台（`Task.detached`，只跨 `Data`，图片回主线程再解码）：十几兆照片在主线程
  解码 + 编码要几百毫秒，一次选二十张会卡十几秒
- 边界：只覆盖"聊天里选图"。文档配图走另一条上传路径未接；已上传的历史图不会变小；
  没有缩略图接口，列表拉到的仍是 2048 的图（十张约 3-4MB、解码几十兆），真出现
  "几十张大图挤一屏"再加 `/api/images/:id/thumb`

### 附：缩略图的加载状态归共享存储（P1 补充）

症状：拖动窗口改变宽度时，已经正常显示的图退回"加载中"并一直转。

- 原因一（与尺寸无关）：已加载状态原本是缩略图视图自己的 `@State`，而 `CollapsibleThumbRow`
  有三处分支会随宽度换结构（首帧 / 折叠行 / 展开网格），一换结构整棵子树重建 → 状态清空
- 原因二（尺寸放大）：十几兆原图 + `NSCache` 在内存压力下回收条目 → 重建后缓存未命中 →
  重新拉取 + 主线程解码，拖动中反复重建 → 看着永远在转
- 改法：`AttachmentImageLoader` 从静态缓存改成 `@MainActor ObservableObject` 单例
  （`@Published images/failed`），取图任务归存储所有、不随视图生命周期取消，同 id 并发只发一次；
  `MessageAttachmentThumb` 删掉 `@State`，直接读 store。失败只有 404（图已被清理）记终局，
  网络类失败留给下次重建重试
- 与压缩的关系：各自解决一半 —— 存储治"回退"，压缩治"回退后恢复不过来"（大图不吃内存压力）
