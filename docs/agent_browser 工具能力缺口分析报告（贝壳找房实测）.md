# agent_browser 工具能力缺口分析报告

> 日期：2026-08-01
> 场景：使用 agent_browser 在贝壳找房（西安雁塔）完成「地图找房 + 列表筛选」任务
> 结论：工具在复杂 Web 交互场景下暴露 5 类能力缺口，本文档记录每个问题的暴露过程与修改建议

---

## 背景

目标任务：在贝壳找房筛选「西安雁塔区，两室、50㎡+、3000元/月以内」的公寓房源。

实际执行路径：
1. 打开地图找房页（map.ke.com）→ 登录墙
2. 列表页（xa.zu.ke.com）→ 已登录可访问
3. 尝试地图平移扫房 → 失败
4. 退回列表页，尝试筛选 → 反复试错

---

## 问题 1：拖拽交互缺失（最致命）

### 暴露过程
- 地图找房页是百度地图 canvas 渲染，小区标记（万象酒店式公寓等）只在地图当前视口内显示
- 尝试 3 种方式平移地图全部失败：
  1. `scroll(x, y)` 页面滚动 → 只动页面视口，地图纹丝不动（页面无滚动条）
  2. 点击地图区域后按方向键（ArrowDown）→ 无响应
  3. 多次 scroll 到边界 → 地图视口从未变化，只能读到初始视口内的小区
- 结论：地图只能看到「当前视口」那一小块，无法扫完整片区域

### 影响
所有依赖拖拽的 UI 全部不可用：地图、滑块、画布、拖拽排序、轮播图。这是最硬的交互缺口。

### 修改建议
**方案 A（推荐先做）：JS 合成鼠标事件**
- 注入 JS：`document.elementFromPoint(x, y)` 命中目标 → 依次派发 `mousedown → mousemove(多步) → mouseup`
- 事件带 `clientX/clientY`、`bubbles: true`
- 工具签名：`drag(x, y, dx, dy, steps=10)`
- 覆盖 90% 场景（百度地图监听标准鼠标事件）
- 已知局限：对使用 PointerEvent 或 nativeEvent 深度校验的页面可能无效

**方案 B（兜底）：CGEvent 系统级事件注入（macOS）**
- 用 `CGEventCreateMouseEvent` 注入真实鼠标事件，不依赖页面 JS
- 需要「辅助功能」权限（Accessibility），用户需授权一次
- 可通杀所有页面
- 建议做成配置开关，A 失效时启用

## 问题 2：DOM 定位是「盲点」（无按文本点击能力）

### 暴露过程
- 想点击筛选器「两居」，工具只有 CSS 选择器定位
- 第一次尝试 `ul li.filter__item--level3:nth-child(9) a` 点击「城南」→ 实际跳到了「碑林-城南」（区块错位，因为 DOM 里城南出现在多个区划下）
- 想点「两居」时数 nth-of-type 数错，点击后 URL 变成 `l1`，页面显示的是「三居」——**l1 是两居，l2 是三居，编码与直觉相反**，只能靠试错确认
- 尝试 `text=两居` 文本定位 → 直接抛 JS 异常，功能不存在

### 影响
筛选类交互全靠猜选择器 + 试错，一次操作经常要 3-5 次尝试，token 消耗成倍放大。

### 修改建议
**2a. click 支持 text 参数（快速修复）**
- 内部用 XPath：`document.evaluate("//*[text()='两居']", ...)` 定位元素坐标再点击
- 支持 `contains(text(), '关键词')` 模糊匹配

**2b. snapshot 返回可交互元素清单（推荐，收益最大）**
- 在 snapshot 输出中增加 `interactables` 数组，只列可交互元素（a/button/input/select）：
```json
[{ "text": "两居", "role": "link", "x": 412, "y": 158, "href": ".../l1/" }]
```
- agent 拿到清单后一眼可知「两居 → l1」，不用再猜
- **顺带解决问题 4**（URL 参数体系不透明）：href 直接暴露了参数规则

## 问题 3：表单交互脆弱

### 暴露过程
- 在搜索框 `fill("酒店式公寓")` + `press(Enter)` → 页面无任何变化，搜索结果仍是全部房源（44194套）
- 疑似 fill 只设置了 value 属性，未触发 `input` 事件，React/Vue 受控组件监听不到

### 修改建议
- fill 流程改为：`focus()` → 用原生 setter 赋值（`Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, 'value').set`）→ 手动派发 `input` + `change` 事件
- 最保险方案：逐字符模拟键盘输入（keydown/keypress/input）
- 建议 fill 后自动验证：读回 input.value 确认

---

## 问题 4：URL 参数体系不透明

### 暴露过程
- 贝壳筛选本质是 URL 参数（`l` = 居室数、`rt` = 租金区间），但工具不暴露这些
- 只能靠「点击后看 URL 变化」反推，第一次拼 `l2rt15003000a50100` 直接返回 0 条
- 拼 URL 前无法知道参数格式，全靠猜

### 修改建议
- 每次操作返回中自动带上 `url` + `title`
- URL 有变化时显式标注（如 `nav: true`）
- 实现 2b 后，href 会自然暴露参数规则，本问题大部分被覆盖

---

## 问题 5：状态感知弱

### 暴露过程
- 每次操作（点击/滚动/按压）后，不知道页面是否真的变了
- 必须手动 get_text / snapshot 确认，但全量返回内容巨大（一次 snapshot 5k+ 字符）
- 「操作 → 确认 → 再操作」每轮都带全量页面，token 浪费严重

### 修改建议
- 每个交互操作执行后：
  - 默认 wait 网络空闲或固定 300ms
  - 返回「页面变化摘要」：URL 是否变化、可见文本 diff 前 N 字
- 对 snapshot 做内容哈希，相同页面直接返回哈希引用，不重复传全文

## 附：顺带发现（不修）

- **WKWebView 登录态与主浏览器不互通**：首次打开贝壳被登录墙拦截，需用户手动登录一次
  - 决策：不修。agent 场景遇到登录墙让用户手动登即可，cookie 迁移性价比低

## 建议实施顺序

| 优先级 | 事项 | 解决的问题 | 预估收益 |
|--------|------|-----------|---------|
| P0 | 2b: snapshot 可交互元素清单 | 2 + 4 | 一次改动干掉两个痛点，交互不再靠猜 |
| P0 | 1A: JS 合成拖拽事件 | 1 | 地图/canvas 类站点可用 |
| P1 | 3: fill 触发 input 事件 | 3 | 搜索/表单类交互稳定 |
| P1 | 5: 操作后状态摘要 + 快照哈希 | 5 | 显著降 token 消耗 |
| P2 | 1B: CGEvent 真实事件（配置开关） | 1 兜底 | 覆盖 JS 合成失效的极端页面 |

## 关联：token 消耗优化（后续）

本次实测暴露交互类任务 token 大头 = snapshot 全文 + 每次全量 get_text。
除问题 5 的修复外，后端缓存命中率提升也已列入计划（不紧急，先修 agent_browser 工具本身）。
