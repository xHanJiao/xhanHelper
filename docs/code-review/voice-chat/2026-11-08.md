## 一、逻辑错误

### P1-1 Swift 停止录音时，尾部 PCM 排在 `end` 之后发出

`client/xHelper/xHelper/Shared/Services/VoiceChatService.swift:101`（`stop()`）、`VoiceAudioCapture.swift:50`（`stop()`）、`:158`（`sendAudio`）

```swift
state = .finishing
capture?.stop()        // onChunk(tail) → Task { @MainActor in self?.sendAudio(tail) }
capture = nil
sendControl("end")     // 同步立刻入队
```

- `VoiceAudioCapture.stop()` 里的 `onChunk?(tail)` 把尾巴交给 `Task { @MainActor ... }`，
  而 `sendControl("end")` 在同一个同步执行段内调用 —— 尾巴的 `send` 一定排在 `end` 之后。
- 按豆包协议，负包（`flags=0b0010`）之后不应再有音频帧。若服务端对此报错，服务端
  `asr.Read` 会返回 error 并给客户端发 `error`，客户端 `fail()` 会清空 `transcript`
  —— **用户正常说完一句话后，反而可能整段识别结果丢失 + 弹“语音识别失败”**。
- PWA 侧顺序是对的：`useVoiceChat.js:234-240` 先 `sendPCM(pending)` 再发 `end`。

建议：让 `VoiceAudioCapture.stop()` 返回 `Data?` 尾巴，由 `VoiceChatService.stop()` 先
`socket.send(.data(tail))` 再 `sendControl("end")`（`URLSessionWebSocketTask` 保证按调用顺序发送）。
真机联调时把这一项作为第一验证点。

### P1-2 末帧 payload 为空时 `Read` 永远不返回，只能等 90 秒读超时

`server/internal/voice/asr.go:196`

```go
if len(f.Payload) == 0 {
    continue        // 早于 final 判定
}
...
final := f.Flags == flagLastNoSequence || f.Flags == flagLastSequence
```

- 若服务端用「末帧 flags=0b0010/0b0011 + 空 payload」表示结束（协议允许负包不带内容），
  这里会 `continue`，永远不触发 `final`，`Read` 卡到 `readCtx`（`max_seconds+30`）超时，
  客户端表现为「说完话转圈 90 秒然后报语音识别失败」。
- 现有单测只覆盖了「末帧带 JSON」的情况（`asr_test.go:51`）。

建议：先算 `final`，再判空——

```go
final := f.Flags == flagLastNoSequence || f.Flags == flagLastSequence
if len(f.Payload) == 0 {
    if final { return nil }
    continue
}
```

并补一条「末帧空 payload 也返回」的单测。

### P1-3 录音达到 `max_seconds` 时直接报错并取消，已识别文本全部丢弃

`server/internal/voice/asr.go:135`、`server/internal/controller/voice.go:151`

```go
if c.written+len(pcm) > c.maxBytes {
    return fmt.Errorf("录音超过上限（%d 秒）", ...)
}
```

- 上限触发 → 上层 `send error` + `cancel` + `asr.Close()`，没有走 `Finish()`，
  已经识别出的 partial 文本一个字都不回传。
- 客户端侧没有任何 60 秒自动收口：PWA `stopTimer` 只在用户点停止后才启动；
  Swift 只在 `stop()` 里挂 15 秒超时。**用户长口述（>60s）必然踩到，且一次丢光。**

建议（二选一或都做）：
1. 服务端超限时改为 `asr.Finish()` 继续读完最后一包，再给客户端一条
   `{"type":"limit"}` 提示；
2. 客户端在 `max_seconds-2` 处自动 `stop()`（PWA 定时器 / Swift `Task.sleep`）。

### P2-4 `start()` 与 `cancel()`/页面卸载存在竞态：可能留下常开的麦克风

`VoiceChatService.swift:53`、`useVoiceChat.js:167`

- 两者都是在若干 `await`（麦克风权限、ticket、`getUserMedia`、`addModule`）之后才
  建 socket / 开采集，但都不检查「这段等待期间是否已被取消」。
- 场景：点麦克风 → 等待 ticket 期间切会话/离页 → `cancel()` 执行清理 →
  `start()` 续体恢复，重新建 socket、启动采集并把 `state = .recording`。
  此时已经没有 UI 能停止它（**麦克风保持开启**，隐私问题）。
- PWA 还有副作用：`socket.onopen` 命中 `if (finished ...) return` 提前返回，
  `busy.value = false` 被跳过 → 按钮若残留会永久 disabled。

建议：加一个 generation/`cancelled` 标记，每个 `await` 之后检查；或持有 `start` 的
`Task` 句柄，在 `cancel()` 里取消。

### P2-5 「开始新录音时停止旧朗读」只停了正在播的，没停正在请求的

`VoiceChatService.swift:128-149`、`useVoiceChat.js:251-264`（`speak`）、`:167-173`（`start`）

- `e4940f39` 在 `start()` 开头加了 `stopSpeaking()`，但 `speak()` 是
  `await synthesizeSpeech(...)` 之后才 `play()`。若上一段 TTS 请求还在飞，
  `stopSpeaking()` 执行时 player/audio 还是空的；请求返回后照样开始播放
  —— **录音过程中突然响起上一轮的回复**，正是该 commit 想修的问题。
- 同理，`onDisappear`/`onBeforeUnmount` 的 `stopSpeaking()` 也拦不住在途请求。

建议：给 `speak()` 加自增 epoch，`stopSpeaking()` 里 `epoch += 1`，`await` 回来后
`guard epoch == myEpoch` 再播放（两个客户端各自实现，几行）。

### P2-6 PWA 里 TTS 失败提示读错了后端字段，永远只显示 `HTTP 5xx`

`front-end/src/api/client.js:56-72`

```js
const data = await r.json()
msg = data?.error || data?.message || msg
```

- 后端统一错误体是 `view.apiResponse`：`{status, errorCode, errMsg, data}`
  （`server/internal/view/render.go:14-18`），既没有 `error` 也没有 `message`。
- 结果是服务端返回的「语音功能未配置」「语音合成失败」全被吞掉，用户只看到 `HTTP 503`。

建议：改成 `data?.errMsg || data?.errorCode`。同时 `useVoiceChat.js:261` 只
`console.error`，播放失败对用户完全静默（Swift 侧有 Toast），建议对齐。

### P2-7 WebSocket 入口没有读上限，也没有握手超时

`server/internal/controller/voice.go:102-113`

- `Upgrader` 未设 `HandshakeTimeout`，升级后也未 `client.SetReadLimit(...)`：
  持有有效 ticket 的客户端可以推超大二进制帧（gorilla 默认无限读），把
  单帧读进内存。虽然入口已由 ticket 保护（单用户场景风险低），但这是廉价的一行防护。
- 建议：`client.SetReadLimit(64 << 10)`、`HandshakeTimeout: 10 * time.Second`。

### P2-8 客户端不等服务端 `ready` 就开录

`useVoiceChat.js:204`、`VoiceChatService.swift:93`

- 服务端顺序是「升级 WS → 同步 `DialASR`（最长 15s）→ 才发 `ready` / 开始读客户端帧」。
- 两个客户端都在 WS 一 open 就开始推 PCM，Swift 甚至在收到 `ready` 时什么都不做
  （`handleSocketText` 的 `"ready": break`）。建链慢时音频只能堆在 socket 缓冲区，
  属于隐性的首字延迟/丢音风险。
- 建议：以 `ready` 作为「开始采集」的信号（服务端先发 ready 的语义也更清晰）。

## 四、安全与成本

- **一次性 ticket**：`crypto/rand` 24 字节、60 秒、单次、绑定 user_id，实现无问题。
  唯一的副作用是 ticket 在 URL query 里，`RequestLogger` 会记 `query=`
  （`server/internal/middleware/logging.go:32-33`），nginx access log 同样会记。
  已消费/已过期的 ticket 无价值，风险很低，仅登记。
- **TTS 请求体会被日志记录**：`/api/voice/tts` 是 `application/json`，`peekBody`
  会把最多 2000 字节正文写进 `[http]` 日志（同 `/api/chat` 的既有行为）。
  与设计「不记录识别文本」精神略有出入（这里记的是回复文本，不是 ASR），
  如果在意可把 `/api/voice/tts` 加进 `redactedBodyPaths` 的「只记长度」分支。
- **成本控制**：TTS 没有配额，只有单次 2000 字上限。单用户部署可接受；
  若将来多用户，需要按用户/按天额度（参考 `web_tools.daily_limit`）。
- **写入/关闭错误多用了 `_ =`**（`controller/voice.go:146/155/172/176`、
  `voice/asr.go:108/113/117/225`、`tts.go:117`）：按仓库硬规则「严禁静默吞错误」，
  这些多数是错误路径上的收尾动作，建议至少在 `tts.go:117`（读错误响应体）处
  打一条 debug 日志，其余可保持。

### P2-1 「等 ready 才开录」会吞掉开头几百毫秒

`front-end/src/composables/useVoiceChat.js:229`、`client/.../VoiceChatService.swift:264`

- 服务端顺序是「升级 WS → 同步 `DialASR`（连豆包 TLS+WS，通常 200–600ms）→ 发 `ready` → 才开始读客户端帧」。
  修复把采集起点从「WS open」推迟到「收到 ready」，用户点完麦克风立刻开口时，这段语音就没被采到。
- 早于 `ready` 的音频并不会丢：200ms 一包只有 6.4KB，服务端升级后由内核/socket 缓冲，
  等 `DialASR` 完成后照常读出。所以旧行为（WS open 就开录）更稳。
- 建议：采集改回 WS open / `task.resume()` 之后开始，其余 ready 相关逻辑不动；

### P1-2 新会话第一轮还没 `done` 时插话，第二轮会另起一个会话

`client/.../Views/ChatView.swift:203-212`（`onSentence`）、`ChatViewModel.swift:1145`（`connect` 用 `conversationId`）、

### P2-1 空闲/会话上限计时器不看「正在回答」，会在 AI 说话时把会话收掉

`VoiceChatService.swift:259-285`（两个计时器）、`:192-206`（`startCapture` 里 arm）、`:463-470`（收到 `sentence` 才重置）

- 30 秒空闲计时器只在「开录」和「收到新分句」时重置。用户说一句「讲讲 X」之后闭嘴，
  回答可能流式 20–60 秒、TTS 再念 20–40 秒 —— 这期间没有任何新分句，30 秒一到就
  `stopContinuous()`：麦克风关掉、连接关掉，而 TTS **还在念**，同时弹「30 秒没有听到说话，
  语音会话已结束」。用户想接着问，得重新点连续对话。
- 10 分钟硬上限同理，会在朗读中途收口（这个可以接受，但至少别在 `isSpeaking` 时收）。
- 建议：给 service 注入一个 `isChatBusy: () -> Bool`（ChatView 传 `{ viewModel.isStreaming }`），
  空闲计时器醒来时若 `isChatBusy() || isSpeaking` 就重新 arm，而不是结束会话；
  朗读开始/结束时也可以顺手重置一次。

### P2-2 结束/到上限后，残句仍会被提交并朗读

`VoiceChatService.swift:463-470`（`case "sentence"` 只校验 `continuousActive`）、`:225-234`（`stopContinuous` 先把 `state` 置 `.finishing`）

- 用户点「结束」或到了会话上限后，服务端还要 `Finish()` 取回残句，客户端此时
  `state == .finishing`、`continuousActive == true`。残句一到，`onSentence` 照常触发 →
  `sendMessage(..., speakReply: true)`：**会话都结束了，又提交一轮并开口朗读**，
  而且这时浮层可能已经消失。
- 建议：`case "sentence"` 增加 `state == .recording` 判断（与 `sendAudio` 一致）。
  如果希望「到上限」把最后半句也收下，就在 `limit` 分支单独放行（加一个 `acceptTrailing` 标记），
  用户主动结束时一律丢弃。

### P2-3 「先停旧轮再发新句」与 `/api/chat/stop` 抢跑，偶发把新轮停掉

`ChatViewModel.swift:1148-1172`（`stopStreaming` 里异步 post stop）、`server/internal/controller/chat_stop.go:52-66`（按会话关闭当前 channel）

- 已有会话里每次插话都可能遇到。最小改法：既然 `Register` 本身就会取消同会话的旧 loop，

### 这轮改变/确认的行为（测试时别当 bug 提）

### 真机反馈带出的第二个问题（远场打不断）

用户实测：不戴耳机、用内置麦时，**正常坐姿离电脑 0.5~1m 基本打不断，把头凑近才行**。

- 根因：0.10 是照着「凑近说话」的日志定的。远场说话电平只有 0.04~0.08，**低于阈值本身**，
  不是「偶尔判不中」而是「永远判不中」。
- 方案：残响本底从 EMA 换成**最近 30 帧（约 2s）门控电平的 p20**，阈值 `max(0.03, p20 × 2.2)`；
  250ms 预热期照样采样本底（原来清零，导致开头 1 秒只剩硬地板，正是最容易误触的时段）。
  p20 不会被 3 帧人声抬高，残响抖动也抬不动它，所以「远场/近场/漏音大的音箱」共用同一套余量。
- 已知下限：支持到约 1m（内置麦 + 外放）；更远需要外接麦或更大音量。开口第一声太轻会漏一次。
