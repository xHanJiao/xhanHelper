## P0（1 条）

### 1. `check-cef-version.sh:104`（以及同样的 `:112`）：`||` 与 `&&` 同级、从左到右结合，条件被读成「必须满 90/180 天」

- 现象：`if [ "$GAP" -ge 2 ] || [ -n "$DAYS" ] && [ "$DAYS" -ge 90 ]` 实际求值为 `(GAP≥2 || DAYS非空) && DAYS≥90`。
  - pin 落后 **4 个大版本**、但 `CEF_VERSION_AT` 是今天 → 一条 warning 都不打、`--strict` 也 exit 0。
  - `CEF_VERSION_AT` 文件缺失/为空 → `DAYS=""`，于是 `[ "" -ge 90 ]` 报 `integer expression expected` 并判假，**整个落后判断彻底失声**（连 ≥4 个版本都不报）。
  - `:112` 同理：`hard=1` 只在「pin ≥180 天」时成立，`≥4 个大版本` 这一半永不生效。
- 为什么是问题：这是本批的**唯一核心功能**，而且失败方向是静默假阴性——黄标不出现，你会以为「体检过了」。文档 §10.2 的阈值表（≥2 或 ≥90、≥4 或 ≥180）写成两种独立触发，代码里不是。提交说明里的自检用例是「落后 4 个版本 **+** 316 天」，正好落在两个条件都为真的位置，把 bug 完全盖住了。
- 复现：假 pin `156.0.7+…chromium-156.0.7240.0` + `CEF_VERSION_AT`=今天 + index 里有 `160.0.x` stable → `--strict` 输出为空、exit 0。
- 建议改法：加花括号分组，两处都改。
  ```sh
  if [ "$GAP" -ge 2 ] || { [ -n "$DAYS" ] && [ "$DAYS" -ge 90 ]; }; then
  # :112
  if [ "$GAP" -ge 4 ] || { [ -n "$DAYS" ] && [ "$DAYS" -ge 180 ]; }; then
  ```
  补一条自检用例：`落后 4 个版本 + 今天 pin`、`落后 0 个版本 + 缺 CEF_VERSION_AT`。

## P1（4 条）

### 1. `check-cef-version.sh:95`：index 解析失败被 `2>/dev/null` 吞掉，既不提示也不进入「无法检查更新」分支

- 现象：`if read -r LATEST LATEST_CHROMIUM <<<"$(latest_stable 2>/dev/null)"; then` 没有 `else`。`refresh_index` 只看「缓存文件存在且 24h 内」，不看内容是否可解析；一旦缓存是坏 JSON（并发写、半截 mv、手工改过），`latest_stable` 的 python 抛错 → 空输入 → `read` 返非零 → 整段跳过，**连 `problems+=("无法检查更新…")` 都不会进**，静默 exit 0。
- 为什么是问题：坏缓存在 24h 内不会被刷新（`find -mmin -1440` 命中），等于「升级提醒」整整一天全哑，而且没有任何一行日志能让你发现。这正是项目硬规则点名的「`err != nil` 却当没发生」，`2>/dev/null` 是这条例子的教科书形态。
- 复现：往 `$CEF_CACHE_DIR/index.json` 写 `{oops`（mtime 为现在）→ `--strict` 无输出 exit 0。
- 建议改法：`refresh_index` 里把「缓存可解析」并入判据（解析失败就当无缓存去拉），并把 `read` 补 `else`：
  ```sh
  if read -r LATEST LATEST_CHROMIUM <<<"$(latest_stable 2>&1)"; then …
  else problems+=("index 解析失败（缓存可能损坏）：跳过落后程度判断，可删 $INDEX_CACHE 重试") …
  ```
  顺手去掉 `2>/dev/null`；python 的 stderr 是排障的唯一线索。

### 2. `check-cef-version.sh:123`：`--strict` 不给 app 路径时，「framework 与 pin 一致」「跑过回归没有」两条检查整段跳过，仍然 exit 0

- 现象：`SHIPPED` 只在 `$APP` 非空时才算；`:123 if [ -n "$SHIPPED" ]` 把两个「更值钱」的检查都关在里面，`hard` 保持 0 → strict 通过。
- 为什么是问题：这是**发版闸门假绿**。而且三处文档/提示都在教这种跑法：`update-cef.sh:77`「`scripts/check-cef-version.sh --strict` 确认戳已更新」、设计文档 `:673`「发版前 `scripts/check-cef-version.sh --strict` 有明确结论」——按这两句跑，脚本除了查一下落后程度（P0 那条还基本不触发）什么都没验。只有 §10.5 的 `--strict "$APP"` 是对的。
- 建议改法：strict 档在 `SHIPPED` 为空时直接 fail（`fail "没给 app 路径，无法核对装进 app 的框架版本"`），或复用 `cef-regression.sh:21` 的「取最新 DerivedData Debug 产物」回落。同时把 `update-cef.sh:77` 与文档 `:673` 改成带 `"$APP"` 的形式。

### 3. `check-cef-version.sh:137-139`：戳的版本不一致时只 warning、不置 `hard=1`，与文档明写的「`--strict` 下算失败」相反

- 现象：`STAMPED != SHIPPED` 分支只 `problems+=(…)`，`hard` 不动。于是「升了 CEF、⌘B 装进去了、但没重跑 `cef-regression.sh`」这个**最该拦的场景**，`--strict` 照样 exit 0；只有「从来没写过戳」才 `hard=1`。
- 为什么是问题：戳的存在意义就是拦「新内核没验伪装」。设计文档 §10.2 第 2 条（`:567`）写的是「`shipped != stamp.version` → …（`--strict` 下算失败）」，代码没实现这半句。对比之下 `:128` 的框架/pin 不一致是 `hard=1` 的，说明这是漏写而不是有意。
- 复现：app 里 framework 报 `156.0.7.0`、戳里 `150.0.1.0` → 一条 warning、exit 0。
- 建议改法：该分支加 `hard=1`。一并考虑：届时戳按 HOME 共享（`~/Library/Caches/xhanHelper-cef`）会让两个 worktree 在两个 pin 之间来回翻，可把戳文件名按版本或 `$SRCROOT` 区分（现在不疼，只是因为这条不硬失败）。

### 4. `update-cef.sh:67-71`：先改版本文件再拉产物，`fetch-cef.sh` 失败就把 pin 留在脏状态且无回滚

- 现象：`printf > CEF_VERSION`、`date > CEF_VERSION_AT` 先落盘，之后才 `fetch-cef.sh`（300MB 下载 + cmake/ninja 编译 + 打 Helper）。这一步失败（断网、没装 ninja、磁盘满、Ctrl-C）→ 仓库里 pin 已是新版本、缓存还是旧的、`.app` 还是旧的。下一次 ⌘B 时 Bundle CEF 会用新版本号重装失败，构建直接红。
- 为什么是问题：脚本非零退出（符合不吞错误），但**它自己把仓库改成了不可构建状态**，恢复只能靠 `git checkout -- client/xHelper/CEF_VERSION*`——这条提示脚本没给。另外 `printf > file` 非原子：中断可能留下空文件，`fetch-cef.sh:22` 报「CEF_VERSION 是空的」，症状与真实原因（升级脚本中断）完全对不上。
- 建议改法：最小成本两处——
  1. 先存旧值，失败回滚并打印恢复命令：
     ```sh
     OLD_V="$(cat "$SRCROOT/CEF_VERSION")"; OLD_AT="$(cat "$SRCROOT/CEF_VERSION_AT" 2>/dev/null || true)"
     printf '%s\n' "$NEW" > "$SRCROOT/CEF_VERSION.tmp" && mv -f "$SRCROOT/CEF_VERSION.tmp" "$SRCROOT/CEF_VERSION"
     date +%Y-%m-%d > "$SRCROOT/CEF_VERSION_AT"
     if ! "$SRCROOT/scripts/fetch-cef.sh"; then
       printf '%s\n' "$OLD_V" > "$SRCROOT/CEF_VERSION"; printf '%s\n' "$OLD_AT" > "$SRCROOT/CEF_VERSION_AT"
       echo "error: [cef] 产物准备失败，已回滚 pin（或手动 git checkout -- client/xHelper/CEF_VERSION*）" >&2
       exit 1
     fi
     ```
  2. 写文件前先 `command -v cmake ninja`（`fetch-cef.sh:74-75` 已经会查，但那时 pin 已经脏了）。

## P2（4 条）

### 1. `update-cef.sh:47`：`startswith(want)` 无边界匹配，`156.0.1` 会命中 `156.0.10+…`

- 现象：`hit = [v for v in vs if v["cef_version"].startswith(want)]`，`want="156.0.1"` 同时命中 `156.0.1+…` 与 `156.0.10+…`（CEF 同一 branch 的 patch 号确实会到两位数），随后 `max()` 静默取最新的那个。
- 为什么是问题：用户明确点名升 `156.0.1`，装进来的是 `156.0.10`——不报错、不提示，pin 的日期也被写成今天。
- 建议改法：`v["cef_version"].startswith(want + "+")`（CEF 版本串里 patch 后必接 `+gHASH`），并在 `len(hit) > 1` 时把命中的版本打出来（一行 `log` 足够）。

### 2. `check-cef-version.sh:69`：缓存过期那天每次构建最多多等 ~16s，离线时没有负缓存（每构建都重试）

- 现象：`curl -fsSL --retry 1 -m 8`：单次 8s，加一次重试最坏 16s；且刷新失败不写任何「刚试过」标记，断网期间**每一次**构建（⌘B、预览、跑测试）都重来一遍。
- 为什么是问题：phase 是 `alwaysOutOfDate = 1`，构建越频繁越疼；这与「A 档只影响构建末尾多看一眼」以及文档 §10.2「缓存命中 ~50ms」的承诺不符（离线那天的真实体验是黄标 + 十几秒）。A 档「绝不阻塞构建」的初衷是别把日更卡住，8s 级别的阻塞已经算卡了。
- 建议改法：`-m 3 --retry 0`（CEF 发版节奏按周算，不需要为一次刷新死等），并加一个 `touch "$CACHE_ROOT/.last-attempt"` 的冷却（如 1h 内失败过就不再试）。

### 3. `docs/design/mac-apps/browser-chromium-migration.md:562`：阈值表还写着 `${ACTION}` 与 `CEF_STRICT=1`，脚本里都不存在

- 现象：表格第三行是「≥4 个大版本 **或** ≥180 天，且 `${ACTION}` 是 archive → 强提示（`CEF_STRICT=1` 时 `exit 1`）」。实际脚本：不分 archive/build（phase 对所有 `buildActionMask` 跑同一套），开关叫 `--strict`，`CEF_STRICT` 环境变量根本没人读。
- 为什么是问题：读文档的人会以为 archive 时会自动升级成强提示、或以为设 `CEF_STRICT=1` 能影响构建期行为——两者都不成立。
- 建议改法：把这行改成与代码一致：「≥4 个大版本 **或** ≥180 天 → `--strict` 下 `exit 1`；构建期永远只黄标」，并删掉 `${ACTION}` / `CEF_STRICT`。

### 4. `check-cef-version.sh:31` / `:36`：A 档里有两条 `error:` + `exit 1`，与「构建照常成功」的契约冲突

- 现象：`CEF_VERSION` 缺失、或形态不含 `+chromium-A.B.C.D` 时，脚本以 `error: [cef] …` 结束并 exit 1。Xcode 会把这两行解析成红色错误并判定 phase 失败。
- 为什么是问题：这两条在 `--strict` 与构建期共用，语义上属于「配置坏了」（该失败），但文档 §10.2 和脚本头注释都承诺「A 档只 warning，构建照常成功」。当前 `CEF_VERSION` 缺失时 Bundle CEF（前一 phase）已经会失败，所以实际不会新增构建失败；但形态不对（例如手改成短版 `156.0.7`）时 `fetch-cef.sh` 只校验非空、拦不住，这条例外就是唯一把构建搞红的地方——与契约的差异会在真出问题时让人怀疑是 CEF 脚本「乱报错」。
- 建议改法：二选一，别留中间态。要么 A 档（`STRICT=0`）降级为 `warn` 后 `exit 0`（反正后面的 Bundle CEF 会动手），要么在文档 §10.2 明写「配置错误直接失败，这是唯一例外」。推荐前者 + 文档一句话。

## P3（5 条）

1. **`check-cef-version.sh:69` / `update-cef.sh:39` 共用 `index.json.part`**：构建期刷新与手动 `update-cef.sh` 撞在一起时，一个 `rm -f …part` 会把另一个正在写的临时文件删掉（`mv` 失败、`set -e` 直接退出）。改成 `index.json.part.$$` 即可。
2. **`check-cef-version.sh:33`**：`CEF_VERSION_AT` 缺失时 `tr … < file 2>/dev/null` 的 `2>/dev/null` 管的是 `tr` 不是重定向，构建日志里会留一行 `…/check-cef-version.sh: line 33: …/CEF_VERSION_AT: No such file or directory`。改成 `[ -f ] && PINNED_AT=… || PINNED_AT=""`。
3. **`check-cef-version.sh:54-57`**：`APP="$BUILT_PRODUCTS_DIR/${FRAMEWORKS_FOLDER_PATH:-}"` 拼出来的路径不以 `.app` 结尾，`case` 不会命中，`FW_DIR` 会指到产物目录本身，`fw_version` 必然为空 → 静默跳过。这条只在「Xcode 不给参数」时走到（Xcode 现在都给了），要么删掉、要么按 `$WRAPPER_NAME` 拼。
4. **`update-cef.sh:59`**：给老版本号 = 静默降级，`log` 只打 `CEF_VERSION: 新 → 旧`，看不出这是降级。加一行比较 chromium 主次版本、降级时明说「这是降级，确认要这么做」。
5. **`docs/…/browser-chromium-migration.md:571`（§10.3）**：`ENABLE_USER_SCRIPT_SANDBOXING = NO（project.pbxproj 461/504 行）` 行号已过期（本批新增 19 行后是 523/581）。这种锚点建议改成「搜 key 名」而不是行号。

## 已确认没问题

- **phase 只加在 xHelperMac**，顺序为 `Prepare CEF → Sources → Frameworks → Resources → Bundle Backend → Bundle CEF → Check CEF`；`CodeSign` 是 target 全部 phase 之后的独立步骤，而 Check 只读（唯一写操作是 `~/Library/Caches` 下的 `.part` 与索引缓存），不会破坏签名——这一点和 `fetch-cef.sh:171-173` 那条「戳不能放进 bundle」的教训方向一致。
- **`ENABLE_USER_SCRIPT_SANDBOXING = NO`**：xHelperMac 的 Debug/Release 都显式设了 NO（pbxproj 523/581），脚本能联网、能写 `~/Library/Caches`；iOS target 是 YES，但该 phase 不在 iOS target 上。
- **`alwaysOutOfDate = 1` + 空 `inputPaths`/`outputPaths`** 是这种 phase 的正确写法（不设才会有「will be run during every build」警告）。
- **`warning:` 前缀会被 Xcode 认成黄标**，stdout 上的普通文本不会变红；`error:` 只出现在 `--strict` 与配置错误路径。
- **bash 3.2 + `set -u` + 空数组**：实测 `"${#problems[@]}"` 在 3.2 不报错、`"${problems[@]}"` 会报 `unbound variable` 并退出——当前代码先用 count 守卫再展开，路径安全（这条坑值得在这里留档：以后谁把 `if [ "${#problems[@]}" -gt 0 ]` 拆掉就炸）。
- **`/bin/sh`（= bash 3.2 posix 模式）下 `<<<` / 数组 / `+=` / `local` 实测可用**，与既有 `fetch-cef.sh` 同构；风险是「在 dash 环境下必挂」，但本项目只跑 macOS，不构成缺陷（`shellPath` 与 `fetch-cef.sh` 保持一致反而是对的）。
- **`cef-regression.sh:56-135` 的 `if … then :; else exit 1 fi` 包裹**语法有效（heredoc 在 if 条件里合法），失败明确非 0 且不写戳；通过后写戳的顺序也对。
- **版本归一化 `cut -d. -f1-3`**：实测 framework `156.0.7.0` vs pin `156.0.7` → 判等，不会误报。
- **24h 缓存 + 失败回落旧缓存 + `.part` 再 `mv`** 的原子写入思路正确；`.app` 里 framework 读不到时 `fw_version` 返回 1 而不是假版本号（不吞成 `""` 以外的垃圾值）。
- **`date -j -f` 失败**会走 `|| true` → `DAYS=""` → 跳过天数判断，不会算出错误的「停更 N 天」。
- **`fetch-cef.sh` 的增量判据**（版本号 + Helper sha）足以支撑「`update-cef.sh` 不碰 .app」这个设计：⌘B 时 Bundle CEF 会按新版本号真的重装。
- **戳放 `~/Library/Caches` 不进仓库**合适（机器本地事实、不该被 commit）；`XH_CEF_REGRESSION_STAMP` / `CEF_CACHE_DIR` 两个读写方（`cef-regression.sh:139`、`check-cef-version.sh:24/27`）口径一致。

## 建议的修复顺序

1. P0-1（两行花括号）——不修的话本批的主要交付等于没生效。
