# RAG 检索评测框架设计方案

> 2026-06-15 初稿 · 基于 2026-06-14 方案讨论整理
> 
> **两阶段：Phase 1 离线试题集 → Phase 2 在线旁路采样**

---

## 一、背景与动机

### 1.1 当前问题

Agent 系统中的检索效果长期**只能凭感觉调试**：

- Chunk 切分策略改了，体感搜索变好了，但**无法量化验证**
- 换 embedding 模型、调阈值、改排序逻辑——每一次改动都没法确认是优化还是回退
- 开发时"好像好了"，上线后"好像又差了"，没有数据支撑

### 1.2 数据基础已具备

系统运行至今积累了丰富的真实数据：
- **88 个笔记主题**，覆盖个人财务、健康、职业、房产、社交等各领域
- **21 篇文档**，涉及方案设计、行程规划、面试准备等
- **大量真实用户 query**（日常对话、记账、查询、讨论），构成试题集的天然素材

---

## 二、设计目标

| 目标 | 说明 |
|---|---|
| **数据驱动** | 试题源于真实用户 query，覆盖实际使用场景 |
| **可重复** | 锁死试题集后，任何检索策略改动都能回放对比 |
| **自动化** | CI 流水线集成，每次 PR 自动跑，回退自动报警 |
| **持续演进** | 试题集按需扩充，旁路采样持续补充线上数据 |

---

## 三、总体架构：两阶段

```
Phase 1（先做）                    Phase 2（后做）
┌───────────────────┐            ┌─────────────────────┐
│  离线试题集          │            │  在线旁路采样         │
│                     │            │                     │
│  真实 query         │            │  线上 1/N 采样       │
│  → 清洗/脱敏         │  互为补充    │  → 裁判 LLM 标注     │
│  → LLM 扩写变体      │ ←──────── →  → 指标计算           │
│  → 单人自洽标注       │    持续      │  → 锁死 GT          │
│  → CI 流水线         │    校准      │                     │
└───────────────────┘            └─────────────────────┘
```

## Phase 1：离线试题集（基准数据集）

### 4.1 试题来源（三层递进）

```
真实用户 query         清洗脱敏            LLM 扩写变体
                                        
┌──────────┐       ┌──────────┐       ┌──────────────┐
│ 用户日常问题 │  →  │ 去隐私/去噪音 │  →  │ 同义改写       │
│ 记账/查询   │       │ 标准化表述   │       │ 加噪音/干扰    │
│ 讨论/决策   │       │            │       │ 多语言/口语化  │
└──────────┘       └──────────┘       └──────────────┘
```

**一条真问题 → 扩成 10 条变体**，覆盖：

| 变体类型 | 示例 |
|---|---|
| **原版** | "我上个月在餐饮上花了多少钱" |
| **同义改写** | "查一下上个月饮食消费总计" |
| **加噪音** | "我记得我上个月…就是吃饭那个…花了多少来着" |
| **口语化** | "上个月吃饭花了多少啊" |
| **关键信息缺失** | "我花了多少钱"（需默认时间范围） |
| **否定/排除** | "不算外卖，光堂食花了多少" |
| **模糊查询** | "最近吃饭花挺多的，具体多少" |

### 4.2 试题规模与构成

| 维度 | 规格 |
|---|---|
| **总量** | 500~5,000 条 |
| **正样本** | **有明确正确答案**的 query，标注期望命中的文档/笔记片段 |
| **负样本** | **无相关结果**的 query（如系统外话题），用于测试拒绝检索能力 |
| **难度分层** | 简单（精确匹配）→ 中等（语义匹配）→ 困难（跨片段推理） |

### 4.3 单人标注流程

> 目前只有一个人标注（hx），所以用**自洽标注**替代多人 Kappa 校验。

```
第一轮：凭直觉标完全部试题
    │
    ▼
LLM 辅助过一遍，挑出可疑项
    │
    ▼
人工复核可疑项，修正标注
    │
    ▼
过两周，随机抽 20% 复标
    计算自洽率（同一人两次标注的一致性）
    │
    ├── 自洽率 ≥ 90% → 数据集可用 ✅
    └── 自洽率 < 90% → 检查分歧原因，补充标注规范，重标
```

**自洽率**：自己隔一段时间重标同一批题，看两次结果一致的比例。目标 ≥ 90%。

**标注规范文档**（第一次标注时顺手记录）：
- 什么算"相关"：结果直接回答了问题或提供了关键上下文
- 什么算"不相关"：结果与问题无关或仅有微弱关联
- 边界案例记录：哪些题比较模糊，为什么最终选择了某个答案

### 4.4 评估指标

| 指标 | 英文 | 含义 |
|---|---|---|
| **命中率@K** | Recall@K | 期望结果出现在 top K 中的比例 |
| **准确率@K** | Precision@K | top K 中有多少是真正相关的 |
| **NDCG@K** | NDCG@K | **排名加权**——相关结果排得越靠前越好 |
| **MRR** | Mean Reciprocal Rank | 第一个相关结果排在第几位（倒数的均值） |

**NDCG 为什么重要**：对检索来说，相关结果排在第 1 位 vs 第 10 位，体验天差地别。NDCG 能反映排名质量，而 Recall/Precision 只看"有没有"。

### 4.5 CI 流水线集成

```
开发者提交 PR（改了检索策略）
    │
    ▼
┌─────────────────────┐
│  CI Runner 启动      │
│  (GitHub Actions /   │
│   自建 CI)           │
└────────┬────────────┘
         │
         ▼
┌─────────────────────┐
│  加载试题集          │  ← 锁死版本，不可变
└────────┬────────────┘
         │
         ▼
┌─────────────────────┐
│  新策略跑全部试题     │  ← 逐条检索，记录结果
└────────┬────────────┘
         │
         ▼
┌─────────────────────┐
│  对比 baseline 指标   │  ← 与上一次 PR 或 master 对比
└────────┬────────────┘
         │
    ┌────┴────┐
    ▼         ▼
  达标       回退
  PR 可合    PR 阻塞 + 报警
```

**回退报警条件**（可配置）：
- Recall@10 下降超过 3%
- NDCG@5 下降超过 5%
- 任一分类的零召回率出现

### 4.6 试题集版本管理

试题集本身也要版本化：

```
dataset/
├── v1.0/              ← 初始版本
│   ├── queries.json    ← 500 条 query
│   ├── ground_truth.json  ← 每条 query 的期望结果 ID
│   └── metadata.yaml   ← 版本说明、标注日期、自洽率
├── v1.1/              ← 扩充 200 条
│   └── ...
└── v2.0/              ← 大规模重构
    └── ...
```

每次跑 CI 时**显式声明使用哪个版本**，保证对比可追溯。

## Phase 2：在线旁路采样（持续评估）

> Phase 1 跑通后，Phase 2 作为补充，覆盖真实流量中试题集覆盖不到的 corner case。

### 5.1 旁路采样流程

```
用户请求
    │
    ▼
┌─────────────────────┐
│  正常检索链路        │  ← 正常返回 top K 给 LLM
│  (不受采样影响)      │
└────────┬────────────┘
         │
         ▼
┌─────────────────────┐
│  旁路采样器          │  ← 1/N 概率触发
│  (不拦截线上流量)     │
└────────┬────────────┘
         │
         ▼
┌─────────────────────┐
│  裁判 LLM 标注       │  ← 将 top 20 全部喂给裁判
│  相关 / 不相关       │      LLM，逐条标注
└────────┬────────────┘
         │
         ▼
┌─────────────────────┐
│  指标计算            │  ← Precision / Recall /
│                      │     阈值误杀率 / 嵌入盲区
└────────┬────────────┘
         │
         ▼
┌─────────────────────┐
│  Ground Truth 库     │  ← 锁死采样数据，供重放
└─────────────────────┘
```

### 5.2 旁路采样细节

- **采样率**：配置化（如 1/10 请求），异步执行，不阻塞线上
- **裁判 LLM**：用最便宜的模型（DeepSeek Flash 级别），逐条标注 top 20
- **与 Phase 1 的关系**：Phase 2 发现的 bad case 可以回流补充到 Phase 1 试题集中

### 5.3 Phase 2 特有指标

| 指标 | 含义 |
|---|---|
| **阈值误杀率** | 因阈值过低/过高而被误杀的相关/不相关结果占比 |
| **嵌入盲区率** | top 20 中裁判标注为相关但向量分排在末尾的结果占比 |
| **零召回率** | 所有 top K 均为不相关的请求占比，反映系统性检索失效 |

## 六、可对比的维度

两阶段共用同一套对比框架，试题集和旁路采样数据锁死后可重放对比：

| 维度 | 示例 |
|---|---|
| **分段策略** | 不分 chunk vs 256字符 vs 512字符 |
| **重叠策略** | 无重叠 vs 32字符滑动窗口 |
| **Embedding 模型** | DeepSeek embedding vs OpenAI ada-002 vs BGE |
| **阈值** | 0.5 vs 0.6 vs 0.7 |
| **排序逻辑** | 纯向量分 vs 向量分×频次因子（当前方案） |
| **检索范围** | 全量检索 vs 主题限定检索 |

---

## 七、与现有系统的关系

当前检索链路（2026-06-11 重构后）：

```
memory 和 note → EntitySource[T]（泛型统一）
    → 向量检索（向量分 × 频次因子）
    → 过阈值 → 纯向量分排序 → top K
```

评测框架对现有链路**零侵入**：
- Phase 1：离线跑，不碰线上
- Phase 2：旁路抓取，不拦截不阻塞

---

## 八、迭代路线

| 阶段 | 内容 | 优先级 |
|---|---|---|
| **P0** | 从已有数据提取 200~500 条真实 query → 清洗脱敏 → 构建初版试题集 | 先做 |
| **P1** | LLM 扩写变体 → 扩充到 1000+ 条 → 单人标注 + 自洽率校验 | 紧接着 |
| **P2** | CI 流水线集成 → 每次 PR 自动跑 → 回退报警 | 试题集稳定后 |
| **P3** | Phase 2 旁路采样上线 → 持续补充 bad case → 形成闭环 | 持续优化 |
