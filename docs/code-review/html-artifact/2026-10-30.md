## 二、P1 — 高

### 1. `tool/html_artifact.go:308-315`、`:361-369`：outline / block 会把 `data:` 图片的整段 base64 吐进上下文

`create` 是允许模型直接写 `<img src="data:image/png;base64,…">` 的（`htmlsanitize` 明确放行，见 `sanitize_test.go:75`「data:image 应保留」），这类原文会整段进 `source_html`。而 outline / block 的图片分支是：

```go
item["image"] = b.Image   // 没有截断
```

后果：一张 3–5MB 的照片会让 `get(view="outline")` 从「1–3KB」变成「几 MB」，还顺着 `saveToolMsg` 落库（正是 `docs/bugs/042` 描述的那条链路）、下发客户端。设计 §4.3 本来就写了「老页面是 `data:` 时标 `legacy: true`，不可 patch」，只是没写**不能回传原串**。

**建议改法**：`b.Legacy` 时不要给 `image`，改成

```json
{"nid":"img1","tag":"img","legacy":true,"image_bytes":3145728,"hash":"…"}
```

（或 `"image": "data:…（已内联，不能 patch）"`）。`getBlock` 的图片分支同步改。

## 三、P2 — 中

### 2. `util/htmlpatch/htmlpatch.go:154-159`：`alt` 长度上限缺失

§4.5 写死 `alt ≤ 200 字`，实现里 `setAttr(b.node, "alt", *op.Alt)` 无任何校验（`text` 有 `MaxTextRunes`，`alt` 没有）。

**建议改法**：加 `MaxAltRunes = 200` + `ErrAltTooLong`，并在 `patchErrorMessage` 里放行到 `err.Error()`。

### 3. `util/htmlpatch/htmlpatch.go:191`：`style_hash` 可被省略 → 并发下会拿旧 CSS 覆盖别人的改动

```go
if expectHash != "" && expectHash != hashOf(rawText(n)) { … }
```

模型不传 `style_hash` 就完全跳过校验。而 `UpdateIfSourceUnchanged` 的乐观锁只覆盖「本次请求 读→写」那一小段窗口，**兜不住「模型上一轮 `get(style)` 拿到的样式」**——这恰好是 block `hash` 存在的原因（block hash 是拿当前 source 现场比对的，能抓住跨轮错位）。样式这条路目前少一层同类保护。

**建议改法**：`style != nil` 时 `style_hash` 必填，空则报「样式缺少 hash，请重新 get(view=\"style\")」；schema 里 `style_hash` 的描述同步改成必带。

### 4. `util/htmlpatch/htmlpatch.go:314-333`、`:346-348`：`textOf` 逐个文本节点 `collapse` → 内联元素之间的空格被吃掉

`collapse` 是 `strings.Join(strings.Fields(s), " ")`，会 **trim 首尾**：

```
<p>Hello <em>world</em></p>
→ "Hello" + "world" = "Helloworld"
```

中文页面看不出来（测试里 `含<span>标签</span>的段` 正好没空格，所以测试全绿），英文 / 中英混排的 outline 和 `get(block)` 会显示粘连文字，模型据此可能认错块。hash 用的是同一份归一化文本，所以**不会**导致 patch 错位——纯显示/可读性问题，但直接削弱「outline 够认出是哪一段」这个前提。

**建议改法**：加一个不 trim 的 `collapseSoft`（`\s+` → `" "`）给 `textOf` 用，`normalizeLines` 里的逐行 trim 保留。现有 `TestScanBlocksInDocumentOrder`（期望 `第一段 有缩进。`）仍然通过；补一个英文混排用例。

### 5. `util/htmlpatch/htmlpatch.go:25-29`：div 里的文字完全不可 patch —— 覆盖面和设计 §3.1 的证据不一致

`textTags` 只有 `h1–h6 / p / li / td / th / figcaption / blockquote / pre / dt / dd / caption`。而设计 §3.1 自己列的现有页面结构是「表格（财务页是 **div 拼的**）」「时间线（`.tl` / `.item`）」——这些单元格 / 时间线标题都是 `<div>`，在 outline 里根本不出现，模型只能退回 `get(full)` + `create`，也就是这个功能想避免的那条路。

严格按 §4.2 判定表实现是「没写错」，但 §七 验收剧本 1 在真机上很可能撞到。**需要拍板**：把 `div` 收进 `textTags`（前提：div 直接子节点只有文本/内联），还是在文档 §五 明确写清「div 段落不支持，必须整页改」，别让模型以为是 bug 反复重试。

### 6. `tool/html_artifact_test.go:832`：乐观锁的 false 分支没有被真正测到

`TestHTMLArtifactPatchRejectsStaleHash` 模拟并发改动后传**假 hash**，错误在 `htmlpatch.Apply` 就返回了（`ErrHashMismatch`），**根本没走到 `UpdateIfSourceUnchanged` 返回 `ok=false` 那条**。也就是说工具层「页面已变（另一处改过）」这句文案、以及 0 行不覆盖的行为，只有 repo 层单测覆盖。

**建议改法**：在 repo 测试里补一条「`newSource == oldSource` 幂等」断言（代码注释里承诺了这条，`artifact_repo.go:141-143`），并把工具层那条用例的断言范围写清（它测的是 hash 文案，不是锁）。

13. **测试缺口**：`ops > 50`、`style > 64KB`、`ops + style` 同时给、`alt` 上限（修完 P2-2 后）都没有用例；`get(view="block")` 传不存在 nid 也没测。

### 7.2 P1 — 删一张图会连带删掉同一 figure 里的另一张

`util/htmlpatch/htmlpatch.go:362-385` `figureOnlyHasImage` 只判「除了目标 img 之外**有没有别的非图内容**」——另一张 `<img>` 会走 `!walk(c)` 分支，而 img 没有子节点 → 返回 true → 不算「有别的内容」：

```
输入：<figure><img A><img B><figcaption>两张</figcaption></figure>
remove img1
实际：<html><head></head><body></body></html>     ← A、B 一起没了
```

`figure > div.grid > img×N` 同样中招。手账页把两三张照片放进同一个 figure 是常见写法，删一张 = 用户另一张照片静默消失。

**修法**：先数子树里的 `<img>`，只有恰好 1 张（就是目标）才允许折叠 figure：

```go
func figureOnlyHasImage(fig, img *html.Node) bool {
    if countImgs(fig) != 1 {
        return false
    }
    ... // 现有 walk 不变
}
```

### 7.3 P2 — `insertTags` 里的 `tr/td/th/thead/tbody` 永远插不进去

`parseFragment`（`htmlpatch.go:302-304`）用 `<div>` 当上下文做 `html.ParseFragment`；HTML5 在 "in body" 模式下会**丢弃**这些只在表格模式合法的标签：

```
insert after t1  html="<tr><td>y</td></tr>"
→ 错误：t1: 插入内容不合法: 片段顶层只能是块级元素，不能是散文本
```

模型收到「不能是散文本」完全指不到真正原因，会反复试；而 `insertTags`（`:330-336`）明确允许这些标签，文档 §五 又写「表格不能增删行列」——三方自相矛盾。

**修法**：把 `tr/td/th/thead/tbody` 从 `insertTags` 删掉，并对表格类顶层标签单独报「表格行列不支持增删，请整页重写」。

### 7.4 P2 — 没有「页尾锚点」，「加到最后一节」会落进 `<footer>`

`insert` 只能 `after` 某个块，而页面最后一个块通常是页脚里的 `<p>`：

```
页面：<div class="page"><p>正文</p><footer><p>页脚</p></footer></div>
insert after <页脚那块> html="<section>新一节</section>"
实际：<footer><p>页脚</p><section>新一节</section></footer>   ← 新一节变成页脚样式
```

模型看着 outline 里的页脚文字其实能挑对锚点，但没有提示就会顺手挑最后一个 nid，结果是灰小字里的正文，用户会以为「加失败了」。

**修法（二选一，倾向 1）**：
1. 工具描述 + outline tip 加一句：「要加在页面末尾，锚在**页脚之前**那块；锚在页脚块上会插进页脚里」；
2. 支持 `after: "end"`（追加到 body 最后一个顶层容器末尾）——多一条分支和一层校验，先不做。

### 7.5 P3

1. **insert 不幂等**：`patch` 的「内容没变直接成功」只兜住 `newSrc == src`；重复提交同一次 insert 会**插两份**（实测两次 → 两个 `<p>新增</p>`）。只有「响应丢了、模型重试」才踩到，不阻塞。
2. **锚在 `td` 上会造非法结构**：实测得到 `<tr><td>x</td><p>新段</p></tr>`，浏览器下次解析会把 `<p>` 寄养到表格外，位置在两次读取间「跳」。建议描述里限制「别锚在表格单元格上」。
3. **删光所有块后再也没法 insert**（没有锚点可指），只能 `get(full)` + `create`。建议文档 §五 记一行。
4. **幂等分支照报 `inserted` / `removed`**（`html_artifact.go:523-531`）：什么都没做却回 `inserted: 1`，纯展示噪音。
5. **限额只在工具层**：`MaxInsertOps` / `MaxRemoveOps` 常量在 `htmlpatch`，校验在 `tool`（`:453-458`），`ApplyEdit` 自身不设防。目前唯一调用方是工具，可接受。
6. **嵌套的 `script/style` 不被 `parseFragment` 拦**（只查顶层）：能进 `source_html`，成品由 sanitize 洗掉，`get(full)` 又会还给模型。与 `create` 老行为一致，不算新洞。
7. **文档 §五 有一行重复**：「表格只能改单元格文字，不能增删行列」在 326 / 329 各出现一次。

### 7.6 建议补的测试

- `figure` 里两张图删一张 → 另一张必须还在（P1 回归）；
- `figure > div.grid > img×2` 同上（走嵌套）；

- `insert` 锚在 `footer` 里的块 → 钉住当前位置语义（或改完后钉新语义）。

### 8.2 P2 — `pruneEmptyAncestors` 会把 `<body>` 摘掉（与文档「停在 body」不符）

`htmlpatch.go:377-389`：`n` 就是被删块的父节点。当被删块**直接挂在 `<body>` 下**且 body 因此变空时，`isEmptyish(n)` 为 true、向上循环又被 `p.Data != "body"` 挡住，于是 `top` 停在 body，最后 `top.Parent.RemoveChild(top)` **把 body 删了**：

```
输入：<html><head><style>body{margin:0}</style></head><body><p>唯一正文</p></body></html>
remove t1
实际：<html><head><style>body{margin:0}</style></head></html>     ← body 没了
```

`docs/design/html-artifact/fine-grained-edit.md:263` 明写「停在 `<body>`」，实现没停。

**后果**：body 里只剩「CSS 画的装饰」（无文字的图标 `<a>`、胶带/竖线那种空 div、放大层外壳）时，它们会被一起收走；`source_html` 丢 body。若整页还 >200 字节（大 `<style>` 很常见），`htmlsanitize` 不会拦，**直接写库**，页面变空白；若 <200 字节则报「HTML 太短，不像一个完整页面」——一个删除操作报「太短」，模型完全无法自愈。

**修法（2 行）**：

```go
func pruneEmptyAncestors(n *html.Node) {
	if n == nil || n.Data == "body" || n.Data == "html" {
		return
	}
	...
}
```

### 8.3 P2 — 删掉单元格里唯一的内容，会把整列（整格）一起收掉

收缩对「空的 `div`/`td`」一视同仁，而 **`td` / `div.cell` 里唯一的文字块是内层 `<p>`**（单元格本身不是块）：

```
输入：<tr><td><p>甲</p></td><td>乙</td></tr>
remove <p>甲</p>
实际：<tr><td>乙</td></tr>                      ← 少一列，与表头错位

输入：<div class="row"><div class="cell"><p>甲</p></div><div class="cell">乙</div></div>
实际：<div class="row"><div class="cell">乙</div></div>
```

同一机制在**卡片网格**上是想要的（实测删掉卡一的 `<p>` → 整张卡消失，网格自动补位），所以「删卡片」和「删单元格内容」用同一套判据区分不了。

**建议**：不改代码，在 §五 与 `patch` 描述里补一句「删掉某格/某卡里**唯一**的内容，这一格/这张卡会一起消失」——行为至少变得可预测。真要区分得给 `remove` 加 `scope`（block / container），或按「同 tag+class 兄弟」判据（但那会同时让「删卡片」留下空卡，更难看）。

### 8.4 P3

1. **`rejectTableParts` 只看第一个开始标签**（`htmlpatch.go:349-365`，命中首个 start tag 后直接 `return nil`）：`<div class="row"><tr><td>格</td></tr></div>` 能过校验，然后被解析器静默丢弃 → `<div class="row">格</div>`（表格标签没了，不报错）。改成扫完整个片段即可（`tablePartTags` 判定逻辑不用动）。
2. **`isEmptyish` 把「CSS 画的装饰」当空**：只有渐变/背景色/边框的空 div、无文字的图标 `<a>` 都算空。只在「它是容器最后一点内容」时才会被收（收缩从被删块的父节点向上），影响面窄；§五 已写「只认完全空」，可补半句「CSS 装饰不算内容」。
3. **删到整页 <200 字节时文案误导**：`htmlsanitize.MinBytes` 报「HTML 太短（不足 200 字节），不像一个完整页面」。真实页面有 `<style>` 基本不会触发，但删空一个极简页时会看到；可对 `patch` 的删除路径换成「删完这页就空了，改用 create 重建或保留至少一块」。
4. **限额仍只在工具层**：`MaxInsertOps` / `MaxRemoveOps` 定义在 `htmlpatch`，校验在 `tool`（`:453-458`），`ApplyEdit` 自身不设防。目前唯一调用方是工具，可接受。
5. **嵌套的 `script/style` 不被 `parseFragment` 拦**（只查顶层）：与 `create` 老行为一致，成品由 sanitize 洗掉，不算新洞。

### 8.5 建议补的测试

- `td` / `div.cell` 里删唯一段落 → 钉住「单元格一起消失」这个行为（先钉住，改判据时再改测试）；
- `<div class="row"><tr>…</tr></div>` → 应报「表格行列不能单独插入」而不是静默变成散文本（P3-1）。

## 九、第四轮 · 真机复现：删图后外层相框残留（`.fig` / 胶带 / `.cap`）

**来源**：真机实测（用户复现两次：一次删原图、一次删 `insert` 插进去的图，结果一致 → 与图片来源无关，是收缩逻辑）。
**结论**：⚠️ **P2（真机可复现，且现有兜底不成立）** —— 内层空 `.frame` 被正确收掉了，但外层 `.fig` 连同悬空胶带、没有图可配的图注一起留在页面上；因为 `.cap` 是 `<div>`（没有 nid），`patch` 摸不到它，**只能整页重写**。

### 9.1 复现

页面结构（手账风：相框 + 胶带 + 图注，外层 `.fig` 是定位容器）：

```html
<div class="fig">
  <div class="tape"></div>
  <div class="frame"><img src="image:2a408576" alt="照片"></div>
  <div class="cap">这张图的文件名是 2a408576，等下被删的就是它</div>
</div>
```

`patch(remove img1)` 实测输出：

```html
<div class="fig">
  <div class="tape"></div>
                     ← 原来 .frame 的位置，已被正确收掉
  <div class="cap">这张图的文件名是 2a408576，等下被删的就是它</div>
</div>
```

页面上剩下：一条悬空的胶带 + 一行没有对应图片的图注 + 一段空白（`.frame` 留下的高度由 `.fig` 撑开）。

### 9.2 根因

收缩判据是「容器**完全空**」才删（`isEmptyish`，`htmlpatch.go:398-424`）。删完图后：

- `.frame` 子树里没有 media、没有文字 → 判空 → 删掉 ✅（第一层是对的）；
- `.fig` 子树里有 `.cap` 的**非空文本** → 判不空 → 停在这里 ❌。

而 `.cap` 是 `<div>`，不在 `textTags` 里 → **没有 nid**，模型既不能在 `ops` 里改它，也不能在 `remove` 里删它。所以：

> `fine-grained-edit.md` §五 现在写的是「图注写成 `<div class="cap">…</div>` 时那个 div 有文字，相框不会被收掉，**得再 `remove` 一次**或整页改」——**「再 remove 一次」这条路不存在**，模型只能整页重写。这句要改。

### 9.3 建议修法

把收缩判据从「完全空」放宽成「**没有可寻址内容**」，并且**只对被删的是图片时生效**（避免删段落时误伤相邻说明）：

```
残留 = 子树里既没有 media（img/picture/svg/video/audio/canvas/iframe/embed/object/hr），
       也没有模型能寻址的文本块（isTextBlock，figcaption/caption 除外）
```

- `.fig`：只剩 `.tape`（空 div）+ `.cap`（div 文字）→ 无 media、无文本块 → 判残留 → 连 `.cap` 一起删 ✅
- `<div class="card"><img><h3>标题</h3><p>正文</p></div>`：还有 h3/p（有 nid）→ 保留 ✅（这条是放宽后的安全边界）
- `<figure><img><figcaption>`：figcaption 已在豁免名单 → 照旧整块删 ✅
- 图注写成 `<p class="cap">`：p 有 nid → 判「有可寻址内容」→ 相框保留；但这时**模型能自己 `remove` 那个 p**，删完再收缩就干净了。这条正好说明判据是自洽的：**收缩只处理模型没法寻址的残留**。

实现要点（约 15 行）：

```go
func removeBlock(b *scanned) {
	parent := b.node.Parent
	removeNode(b.node)
	if parent != nil {
		pruneEmptyAncestors(parent, b.Tag == "img") // 只有删图才放宽
	}
}

// leftover — mediaRemoved 时：没有 media 也没有可寻址文本块就算残留。
func leftover(n *html.Node, mediaRemoved bool) bool {
	return isEmptyish(n) || (mediaRemoved && hasNoMediaOrTextBlock(n))
}
```

**取舍（要写进 §五）**：放宽后，相框里那些**非语义块**的文字（`.cap`、`.note` 这类 div）会跟着照片一起走。想保留就得让它们写成 `<p>`/`<h3>`（有 nid，模型能单独处理）。

**已验证**（`go test -overlay` 把上面这段改法打到 `htmlpatch.go` 的临时副本上跑，未改仓库）：真机那个 `.fig` 结构删图后整块消失 ✅；`<div class="card"><img><h3>标题</h3><p>正文</p></div>` 删图后卡片与文字都还在 ✅；`<p class="cap">` 保留相框、模型可自行删 p ✅；`<body>` 守卫生效 ✅；**`htmlpatch` / `tool` / `agent` 三包全量用例无回归** ✅。

### 9.4 顺带

- 这一轮和 §8.2（`<body>` 可能被摘）叠加时更明显：如果整页只剩这个悬空 `.fig`，`.cap` 的文字让 body 不空 → 反而挡住了 body 被误删。修 9.3 时**先修 8.2 的 body 守卫**，否则放宽判据后「删掉最后一张图」会直接把 `<body>` 收走。
- 建议补的测试：
  - `.fig > (.tape + .frame>img + .cap)` 删图 → 整个 `.fig` 消失（真机回归）；
  - `<div class="card"><img><h3>标题</h3><p>正文</p></div>` 删图 → 卡片和文字都还在（安全边界）；
  - `<figure><img><figcaption>` 删图 → 整块消失（现有用例，防回归）。
