## 二、剩余 P3（可提交，后续处理）

1. **`NotificationManager` 的 deadline 解析仍静默**（`NotificationManager.swift:58`）：`guard let deadline = iso..., deadline > now else { return false }` 把「解析失败」和「已过点」一起丢弃；镜像侧已改 diag，这里没改。建议拆成两条：解析失败打一次 warning。
2. **`detectDropped` 仍是每条一次主线程查询**：每次前台同步最多 200 次 `event(withIdentifier:)`。`adoptCandidates` 已经合并成一次区间查询，可以用同一份结果比对 id，或补一句 `shortcut:` 说明。
3. **`update_event` 覆盖 `notes` 会抹掉 `[xhanhelper:<id>]` 标记**：之后若映射丢失就认领不到，会在日历里重建第二份。改备注时把标记补回去即可（一行）。
4. **`all_day: false` 未说明要同时给 `start`/`end`**：把全天事件改回定时会让它变成 00:00→次日 00:00 的 24 小时定时事件。schema 里补一句，或回落成 `start + 原时长`。
5. **超过 200 条 pending 时墓碑会被误清**：`pruneDropped` 以「本页 id」为准，第 4 页之外的墓碑在下一轮就被清掉 —— 那些提醒若被手删/清理过，之后会重新建事件。一天 200 条待办大概率不会发生，写进文档即可。
6. **清理与手删都不可逆**：没有「重新写回日历」入口，恢复只能靠取消提醒或等提醒离开 pending。若要给出口，最小做法是设置页加「恢复日历同步（清空墓碑）」。
7. **`mirroredCount` 不校验事件存活**：用户手删后、下一次同步前的窗口里，设置页数字偏大（点清理会得到「删除 0 条」）。影响很小。
8. **`CalendarCore.displayDate` 是为测试暴露的生产 API**：可接受；更干净的做法是测试里临时固定 `displayFormatter.timeZone`。留个注释说明用途即可。

**真机验收清单**（合并设计文档「验证清单」第 8~9 条）：

1. 重复日程（每周例会）改/删 → 只动列表里 `t=` 那一次，系列其他次不变
2. 关掉「提醒同步到日历」→ 已建事件保留、新提醒不进日历、这些提醒不再排通知（不双响）
3. 点「清理…」→ 事件消失，且**等一次前台同步后仍然消失**（本轮 P1 的复现/回归点）
4. 在日历 App 里手删一条镜像事件 → 该提醒变为系统通知、不再重建
5. 建 2 条提醒 → 系统设置撤销日历权限 → 不应双响（此路径现在按「假定存活」处理，只有一条日历闹钟）
