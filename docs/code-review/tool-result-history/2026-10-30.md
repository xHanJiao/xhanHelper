## 二、P2 —— `injectToolResult` 把同一段 JSON 解析了两遍（重复实现）

`server/internal/controller/conversations.go:451-468`

```go
var tcs []map[string]interface{}
json.Unmarshal([]byte(*msg.ToolCallsJSON), &tcs)      // 第一次：配对 + 写 result
var calls []struct{ Function struct{ Name string } }   // 只为拿 name
json.Unmarshal([]byte(*msg.ToolCallsJSON), &calls)     // 第二次：同一个字符串
```

`calls` 是 `tcs` 的真子集。除了多一次解析，还有一个行为问题：第二次解析失败只打日志、随后 `i < len(calls)` 直接为 false —— **静默跳过 stub**，而同一次调用里 `tcs` 却解析成功了。两套解析对同一份数据给出不同结论，属于「明知失败却当没发生」。

建议（净删代码）：

```go
fn, _ := tcs[i]["function"].(map[string]any)
name, _ := fn["name"].(string)
if stub, ok := agent.StubToolResultForHistory(resultJSON, name, 0); ok { ... }
```

可删掉 `calls` 结构、第二次 `json.Unmarshal` 和那条日志。

## 三、P3

1. **html 检测只看「键存在」，不看值类型** —— `history_stub.go:42-46`：`data.html` 为 `null` 或对象时也算命中，产出 `page_bytes: 0` 的 stub。改成 `page, ok := doc["html"].(string)` 一行即可。
2. **html stub 的 marshal 失败分支做不到文档说的「退回原文」** —— `history_stub.go:58-63` 返回 `("", false)`，调用方 `orchestrator.go:2106` 会落到 `truncateToolResult`，也就是**又变回头尾残片**（通用 stub 那条才是真退回原文）。实际不可达（`map[string]any` 里只有 string/bool/int），所以只是文档与代码的措辞差；要一致就让 html 路径失败时返回 `(content, true)`。
3. **测试缺口两条**：
   - 没有「一个 assistant 带多个 `tool_calls`、多个 tool 行交错/乱序」的回放用例 —— 设计 §五专门写了「按 id 映射，不依赖顺序」，值得一条；
   - 没有「`html__get` 结果 > 20000 且名字映射缺失（老数据/解析失败）」的用例，即验证它走通用 stub 而不是残片（现有 orphan 用例用的是纯文本）。
