# P4.2 — 真正的 ReAct Agent 设计方案

> 日期: 2026-05-02 | 状态: 讨论中

---

## 一、现状 vs 目标

### 当前（P1 版 ReAct）

```
用户消息 → LLM → 检测 tool_call? → 执行 → 回传结果 → 循环
```

本质是一个 `if tool_call { execute; loop }` —— LLM 没有自主决策空间，只是被动地"检测到工具调用就执行"。

### 目标（真正的 ReAct）

```
用户消息 → Thought → Plan → Action₁ → Action₂(并行) → Observation → Reflect → Reply
```

LLM 能看到思考过程、自主规划多步操作、根据中间结果调整策略、并行执行无依赖的操作。

### 对比示例

```
用户: "这周餐饮花了多少，超没超预算"

当前:
  LLM → 调 query_bills → 返回数字 → done
  问题: 没有预算概念，不知道"超没超"

真正的 ReAct:
  Thought: "需要查本周餐饮账单，还要知道预算"
  Plan: "先查账单，同时查记忆中是否有预算信息"
  Action₁: query_bills(本周, 餐饮)   ┐
  Action₂: recall_memory(餐饮预算)    ┘ 并行执行
  Observation: 本周320元，预算1500/月→375/周
  Thought: "320 < 375，没超预算"
  → "这周餐饮320元，在你的1500月度预算内，按周算还剩55元额度"
```

## 二、核心改动

### 2.1 Prompt 升级

在 `BuildSystemPrompt` 中增加 ReAct 思维引导：

```
你可以使用函数来完成用户请求。

当任务涉及多步操作时，请先思考再行动：
1. Thought: 分析用户意图，决定需要哪些信息
2. Plan: 列出需要的操作步骤
3. Action: 调用函数（互不依赖的函数可以同时调用）
4. Observation: 根据结果判断是否需要调整
5. 最后给出自然语言回复

如果函数执行失败，请根据错误信息调整参数重试，
不要直接告诉用户"失败了"。
```

### 2.2 可并行工具执行

当前工具串行执行，改造为：**工具调用可以在一次 LLM 回复中批量发出**。

```
LLM 返回:
{
  "tool_calls": [
    {"tool": "bookkeeping", "function": "query_bills", "args": {...}},
    {"tool": "memory", "function": "recall", "args": {...}}
  ]
}

Orchestrator:
  检测到多个 tool_call → 分析依赖 → 无依赖的并行执行 → 结果汇总 → 继续
```

### 2.3 思考链可见

新增 SSE 事件类型 `thought`，展示 LLM 的思考过程：

```
event: thought
data: {"content": "需要查本周账单，同时确认预算...", "step": "thinking"}

event: thought
data: {"content": "计划: 1.查账单 2.查预算", "step": "planning"}

event: tool_call
data: {...}

event: thought
data: {"content": "320元 < 375元预算，没超", "step": "reflecting"}
```

客户端显示为灰色思考气泡，让用户看到 Agent 的推理过程。

### 2.4 失败重试

工具返回 `success: false` 时，把错误信息回传给 LLM：

```
工具返回: {success: false, error: "bill not found: abc123"}

→ 回传 LLM: "函数 delete_bill 执行失败: bill not found: abc123。你可能需要先调用 query_bills 找到正确的账单ID"
→ LLM 调整: query_bills → 找到正确 ID → delete_bill
```

## 三、架构变化

### 当前（简单循环）

```
Orchestrator.Run()
  └── for iter in 5:
        └── LLM → parse → execute_one → loop
```

### 目标（DAG 执行）

```
Orchestrator.Run()
  └── for iter in 5:
        ├── LLM (含 Thought + Plan)
        ├── parse tool_calls
        ├── build DAG (分析依赖)
        ├── execute_parallel (独立节点并发)
        └── aggregate results → loop
```

## 四、SSE 事件扩展

| 事件 | 说明 |
|------|------|
| `thought` | LLM 的思考/规划/反思 |
| `tool_call` | 工具调用（不变） |
| `tool_result` | 工具结果（不变） |
| `status` | 状态提示（Memory 已加） |
| `message` | 文本增量（不变） |
| `done` | 完成（不变） |

## 五、客户端改动

- `ChatView` 新增灰色思考气泡（`thought` 事件），用斜体或更淡的灰色区分
- `ChatViewModel` 新增 `thoughtMessages` 数组，done 时清除
- 不持久化——思考过程只存在于当前流式中

## 六、渐进实施

不一次全上，分 3 个子阶段。

---

### P4.2a — Prompt 升级 + 思考链可见

**做什么**：让 LLM 在调用工具前先输出思考过程，用户能看到 Agent 的推理。

**具体改动**：

1. **`llm/doubao.go` + `llm/deepseek.go`** — `BuildSystemPrompt` 增加 ReAct 思维引导：
   ```
   当任务涉及多步操作时：
   第一步：分析用户意图（Thought）
   第二步：列出需要的操作（Plan）  
   第三步：调用函数（Action）
   第四步：根据结果判断是否需要调整（Reflect）
   第五步：给出回复
   ```

2. **`agent/orchestrator.go`** — 解析 LLM 回复时，如果发现 Thought/Plan/Reflect 文本，单独作为 `thought` 事件发送，不混入 text_delta。

3. **`llm/adapter.go`** — StreamEvent 扩展 `thought` 类型：
   ```go
   {"type": "thought", "step": "thinking", "content": "需要查本周账单，同时确认预算..."}
   {"type": "thought", "step": "planning", "content": "计划: 1.查账单 2.查预算 3.对比"}
   {"type": "thought", "step": "reflecting", "content": "320元 < 375元预算，没超"}
   ```

4. **客户端** — ChatView 加灰色斜体思考气泡，ChatViewModel 处理 `thought` 事件

**收益**：

| 改动前 | 改动后 |
|------|------|
| 用户只知道 Agent 调了什么工具 | 用户能看到 Agent 为什么调、怎么想的 |
| 工具调用错了用户看不出来 | 用户看到思考过程，能发现推理错误 |
| Agent 像个黑盒 | Agent 有透明度，更像"助手" |
| 调试 prompt 靠猜 | thought 直接暴露 LLM 推理质量 |

**改什么文件**：`llm/*.go`, `agent/orchestrator.go`, `llm/adapter.go`, `controller/chat.go`, 客户端 3 个文件

### P4.2b — 失败重试 + 自主纠错

**做什么**：工具执行失败时，把错误信息回传给 LLM，让它自己调整策略重试，而不是把错误直接抛给用户。

**现状**：

```
工具返回: {success: false, error: "bill not found: abc123"}

当前处理: 在 tool_result 事件中返回 success=false
LLM 收到: "[工具执行结果] {success:false, error:bill not found}"
LLM 回复: "账单abc123未找到，请检查ID是否正确"  ← 把皮球踢回给用户
```

**目标**：

```
工具返回: {success: false, error: "bill not found: abc123"}

新增处理:

tool_result 发出后，LLM 收到增强版上下文:
  "[工具执行结果] delete_bill(abc123) 失败: bill not found。
  建议: 先调用 query_bills 列出所有账单，找到正确的ID后再删除。"

LLM Thought: "ID不对，需要先查询账单列表"
LLM Action: query_bills → 找到正确ID
LLM Action: delete_bill(正确ID) → 成功
LLM: "已删除该账单"  ← 自主完成
```

**具体改动**：

1. **`agent/orchestrator.go`** — 工具执行失败时，把 `success=false` 的 error 信息增强后追加到对话历史，附加 "你可能需要换个方式重试" 的提示
2. **`BuildSystemPrompt`** — 加一条规则："如果收到错误信息，分析原因并尝试不同的参数或函数，不要直接告诉用户失败"
3. 不需要新 SSE 事件

**收益**：

| 改动前 | 改动后 |
|------|------|
| 一次失败 = 用户手动纠正 | Agent 自主解决，用户无感 |
| 用户需要知道技术细节（ID、参数等） | 用户只需要描述意图 |
| 修改账单时必须记住 ID | Agent 自己查 ID 再修改 |
| 删除时 ID 不对就报错 | Agent 先查后删 |

**改什么文件**：`agent/orchestrator.go`, `llm/*.go` BuildSystemPrompt

---

### P4.2c — 并行工具执行

**做什么**：互不依赖的工具调用同时执行，而不是串行排队。

**具体改动**：

1. **`agent/orchestrator.go`** — 当一个 LLM 回复中有多个 tool_call 时，用 goroutine + WaitGroup 并发执行：
   ```go
   var wg sync.WaitGroup
   results := make([]*tool.Result, len(toolCalls))
   for i, tc := range toolCalls {
       wg.Add(1)
       go func(idx int, call ToolCall) {
           defer wg.Done()
           results[idx] = registry.Execute(...)
       }(i, tc)
   }
   wg.Wait()
   ```

2. 不需要 LLM 改造——DeepSeek 原生 function calling 已经支持一次回复返回多个 tool_call。豆包 prompt engineering 也支持（JSON 里 tool_calls 是数组）。

**收益**：

```
"这周餐饮多少，超没超预算"

串行（当前）:                   并行（目标）:
  query_bills → 2s               query_bills ─┐
  recall_memory → 2s             recall_memory ┘ → 2s（同时）
  总: 4s                         总: 2s
```

**改什么文件**：`agent/orchestrator.go` 一处

## 七、API 兼容性

`POST /api/chat` 接口契约不变，只增加 `thought` 事件类型。旧客户端忽略新事件类型，不影响功能。

## 八、风险

| 风险 | 缓解 |
|------|------|
| Prompt 升级后 LLM 输出格式不稳定 | 先用 DeepSeek 测试，豆包逐步跟进 |
| Thought 过程太长增加延迟 | 限制单次 thought 200 字 |
| 并行工具调用出错概率增加 | 任一失败时全部结果一起回传 LLM |
| Token 消耗增加 | thought 不在对话历史中持久化，只存在当前流式 |
