# 上下文工程：对话摘要方案（第三层缓存）

## 一、问题定义

### 1.1 现象

LLM（即本 Agent）在长对话中会遗忘早期轮次的关键信息。具体表现为：

- **2026-06-17 晚发现的 bad case**：用户 21:06 明确说过"因为之前那两年打钱时候没跟她商量，所以她确实在这方面很不相信我"——这就是当晚吵架的导火索。但到 23:20 我回忆"导火索是什么"时，完全遗忘了这段信息，编了一个"她给她爸打电话"的假场景。
- **根本原因**：上下文窗口仅 10 轮，21:06 的关键信息到 23:20 已被踢出窗口。即使后来放开到 100 轮，信息虽然"在窗口里"，但 LLM 长上下文的注意力衰减导致中间部分的信息召回率大幅下降（Lost in the Middle 问题）。

### 1.2 尝试过的方案及失败原因

**方案①：历史消息检索（message_search tool）**

- 做法：当感觉信息丢失时，主动搜索历史对话
- 失败原因（6月17日验证）：
  - Query 构造太粗糙（例如搜 `"今晚 吵"`、`"一晚上没说话"`），语义向量表达差，召回效果不佳
  - 搜不到时没有降级策略，直接放弃了
- 结论：方案本身有意义，但不能作为主力方案——每次丢失都去搜一遍太被动了

**方案②：话题切换相似度断崖检测**

- 做法：检测用户说话与之前话题的语义相似度，在断崖处触发话题切换
- 用户评价：**"它是有用的东西，但是对我们这个工作不 work"**
- 结论：**不采用**

**方案③（选定）：上下文扩展 + 压缩（即本方案）**

- 核心思路：将窗口外的对话内容压缩成导航级摘要，放在上下文里，让 LLM 感知到"之前聊过什么"
- 替代了单纯的"扩大窗口"思路——因为即使窗口扩大到 100+ 轮，LLM 在长上下文中仍然存在注意力衰减

---

## 二、方案设计

### 2.1 核心架构：三层分层

```
┌─────────────────────────────────────────────┐
│  ③ 主题抽象层（Theme）—— 已有                │
│     "用户身上发生了什么"                      │
│     跨会话持久化，后台向量检索参与上下文       │
├─────────────────────────────────────────────┤
│  ② 会话摘要层 —— 本方案新增                  │
│     "本场对话窗口外聊了什么"（导航级）        │
│     只发 user messages 给 Flash 做增量合并    │
│     存储：conversation_summaries 新表         │
├─────────────────────────────────────────────┤
│  ① 原始对话窗口（最近 N 轮）—— 已有           │
│     "最近在聊什么，细节完整"                  │
│     N = history_rounds，默认 50               │
└─────────────────────────────────────────────┘
```

**三层的关系：**

| 层 | 内容 | 用途 | 为什么不能替代 |
|---|---|---|---|
| ① 原始窗口 | 最近 N 轮完整对话 | 即时查阅细节 | 长窗口注意力衰减，中间信息丢失 |
| ② 会话摘要 | 窗口外对话的高度压缩（导航级） | 让 LLM "知道有这回事" | 摘要丢失细节，无法精确回答 |
| ③ 主题抽象层 | 跨会话的用户长期认知聚合 | 让 LLM 了解用户全局画像 | 粒度太粗，不包含单次会话上下文 |

### 2.2 摘要粒度：仅粗粒度（导航级）

砍掉原方案中的"细粒度指针"，只保留粗粒度摘要：

- **生成时机**：每 N/10 轮入队一次 DelayedTask，worker 检查 `cover_to_msg_id` 到最新消息之间相差 ≥ N/2 轮 user messages 时生成
- **合并方式**：增量合并——每次生成时传入上一段摘要 + 新增 user messages → Flash 输出更新后的完整摘要。始终只有 1 段 active 摘要
- **内容**：导航级话题流叙事（"聊了什么方向、分岔何在、结论方向"），300 字以内，不记录具体事实细节
- **底料**：只发 `role=user` 的消息，不发 assistant/tool
- **存储**：`conversation_summaries` 新表，旧段标记 `superseded`
- **LLM 模型**：Flash（成本低，任务不需深度推理）

## 三、数据模型

### 3.1 conversation_summaries 表

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | varchar(36) PK | UUID |
| `conversation_id` | varchar(36) | 归属会话，加索引 |
| `user_id` | varchar(36) | 归属用户 |
| `summary_text` | text | 摘要正文（≤300字） |
| `cover_from_msg_id` | varchar(36) | 覆盖范围的起始消息 ID |
| `cover_to_msg_id` | varchar(36) | 覆盖范围的结束消息 ID |
| `parent_summary_id` | varchar(36) | 上一段摘要 ID（增量合并时指向旧摘要；首段为空） |
| `topics` | varchar(500) | 标签，逗号拼接（不用 JSON） |
| `status` | varchar(20) | `active` / `superseded` |
| `created_at` | timestamp | 自动 |

### 3.2 为什么不做成 note 或 document

| 存储方案 | 问题 |
|---|---|
| **note** | 每次对话后台自动向量检索，会拉入无关的旧会话摘要，污染上下文 |
| **document** | 接口语义不匹配（没有"取最新摘要"的概念） |
| **专用表** ✅ | 存储层独立，不参与后台检索，仅主动加载 |

### 3.3 为什么不暴露给 LLM 作为 tool

摘要由系统全自动管理（异步生成 + orchestrator 注入 UserMessagePrefix），LLM 不需要主动调用 save/get summary。接口退化为内部函数，不注册成 tool。

## 四、工作流

### 4.1 触发与生成

```
每次 chat 请求：
  → 每 N/10 轮入队一次 DelayedTask（TaskType: "summary_generation"）
  → 入队前去重：查同 conv 的 pending task → 有则推迟 process_at（+10秒）
  → 无则新建，ProcessAt = now + 10s

cron_runner ticker（deliver_interval 周期）：
  → processSummaryTasks() 扫到期的 summary_generation 任务
  → 对每个任务：
      1. 查最新 active 摘要 → 取 cover_to_msg_id
      2. 查窗口边界（最新 N 条 user messages 中最老那条的 created_at）
      3. 数 cover_to_msg_id 之后、窗口边界之前的 user message 条数 K
      4. 若 K ≥ N/2 或 无摘要：
          a. 加载待覆盖 user messages（最多 M=N 条，role=user，按 created_at ASC）
          b. 加载上一段摘要文本（若有）
          c. 调 Flash 生成增量摘要（300 字以内）
          d. 旧摘要标记 superseded，新摘要写入 active
          e. DelayedTask 标记 done
      5. 否则：
          a. K < N/2，不到触发门槛，DelayedTask 标记 done（跳过本轮）
  失败处理：重试 3 次后标记 failed，下次触发自然补上
```

### 4.2 上下文注入

```
orchestrator.Run() 第 305 行之前：
  → summaryRepo.GetLatest(convID)
  → 若有 active 摘要：
      prefix := "<conversation_summary>摘要文本</conversation_summary>\n"
      systemPromptResult.UserMessagePrefix = prefix + systemPromptResult.UserMessagePrefix
  → 若无摘要：跳过
```

摘要注入到 UserMessagePrefix 最顶部，不破坏 system prompt 缓存。

### 4.3 增量合并 Prompt 核心约束

1. **导航级**："只记录话题流、分岔和结论方向，不记录具体事实细节"
2. **增量合并**："基于上一段摘要和新对话，生成更新后的完整摘要"
3. **300 字以内**
4. **旧话题淡出**："如果旧话题在新增对话中不再出现，可以在摘要中淡出或删除"
5. **输出格式**：纯文本叙事，附时间信息

### 4.4 跨天恢复

```
用户重新进入对话时：
  1. orchestrator 加载 active 摘要
  2. 注入 UserMessagePrefix 顶部
  3. 正常回复，摘要信息自然融入回应中，不刻意提醒
```

## 五、与现有系统的关系

### 5.1 不冲突的部分

- **Theme（主题抽象）系统**：互补——Theme 说"用户是谁"，摘要说"刚才聊了什么"
- **Note 系统**：继续负责长期事实记忆
- **Memory 系统**：继续负责对话中自动提取的碎片信息
- **Message search**：仍可用作精确查询，后续新增 `search_by_range(cover_from_msg_id, cover_to_msg_id)` 按摘要覆盖范围精准搜索

### 5.2 不参与后台检索

摘要只通过 orchestrator 主动加载，不像 note/theme 那样每轮对话后台向量检索，杜绝上下文污染。
