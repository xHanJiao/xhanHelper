# DeepSeek 上下文缓存命中率实验

**日期**: 2026-06-19  
**背景**: 切换 history_rounds 从 10 → 50 后，缓存命中率从 60% 暴跌到 1%，怀疑摘要系统干扰。  
**结论**: 命中率下降与摘要无关，由窗口大小 + DeepSeek chunk 缓存机制共同决定。

---

## 实验过程

### 1. 排除摘要嫌疑

- 将 N 从 50 改回 20，命中率恢复到 ~40%
- 在 N=20 下暂时关闭摘要注入（仅后台生成，不发送给 LLM），命中率不变
- **结论**：摘要不是命中率下降的原因

### 2. 分析 N=20 的时间序列

从数据库中提取 2026-06-19 的所有 assistant 消息，解析 `extra.Usage.prompt_cache_hit_tokens` 和 `request_json.messages` 中的 user 轮数。

关键 msg_id（N=21 组）：

|---|---|---|---|---|
| 01:41:07 | `135e5461` | 5248 | 40.5% | 首次高命中 |
| 01:41:11 | `d062c64e` | 768 | 5.4% | 邻接跌回 |
| 01:41:26 | `92caefe4` | 14464 | 93.6% | 极端高命中 |

### 3. 发现 Chunk 层级模式

所有 cache_hit 值集中在离散层级：

| cache_hit | 出现次数 | 说明 |
|---|---|---|
| 768 | 27 | 基线：仅 System Prompt（~2739 字符） |
| 1024 | 3 | +1 chunk |
| 1152 | 1 | +1.5 chunk |
| 1536 | 2 | +3 chunk |
| 6656 | 7 | **最稳定的高命中点** |
| 14464 | 1 | 接近全命中 |

### 4. 推导 Chunk 大小

关键观察：cache_hit 值之间的差值中，**256 反复出现**：

```
 768 → 1024: +256 (×1)
1536 → 1792: +256 (×1)
6400 → 6656: +256 (×1)
```

且两个最稳定的高点差值也落在 256 的整数倍：

```
6656 - 768 = 5888 = 23 × 256  ← 精确
6400 - 768 = 5632 = 22 × 256  ← 精确
1536 - 768 = 768  =  3 × 256  ← 精确
```

**推测：DeepSeek 上下文缓存的 chunk 大小 ≈ 256 tokens。**

### 5. 滑动窗口与缓存的关系

DeepSeek 缓存文档提到三种缓存落盘机制：

1. **请求结束位置落盘**：每个请求的起始和结束位置形成缓存前缀单元
2. **公共前缀检测落盘**：系统检测多次请求间的公共前缀并落盘
3. **按固定 token 间隔落盘**：长输入以固定间隔切分 chunk，每个 chunk 独立匹配

滑动窗口下，每轮推出最老 1 条消息、推入最新 1 条。缓存能否命中取决于 chunk 边界是否与消息对齐：

- 对齐时 → 大量 chunk 命中 → 6656
- 不对齐时 → 仅 System Prompt chunk 命中 → 768

这解释了 `768 ↔ 6656` 的**周期振荡**模式——两条连续请求绝不会同时命中 6656，因为边界偏移导致前缀不连续。

### 6. N=20 vs N=50

| | N=20 | N=50 |
|---|---|---|
| 平均 prompt_tok | ~15,000 | ~43,000 |
| 最大 cache_hit | 6656 | 6400 |
| 非 768 命中占比 | 27% | 22% |

N=50 时窗口更大，但绝对命中 token 数反而更低（6400 < 6656），可能因为 DeepSeek 缓存容量有上限，无法覆盖 43000 token 的长前缀。

### 7. Trade-off 总结

```
窗口大 → 上下文完整 → LLM 不丢信息
      → 缓存命中率低 → 费钱

窗口小 → 缓存命中率高 → 省钱  
      → LLM 丢失上下文 → 需要摘要补上
```

**当前策略**：三层架构（小窗口 + 摘要 + Theme）在二者间取平衡。N=20 给出 ~40% 命中率，摘要保证窗口外信息不丢。
